## Sesión 12.1 — Registro de imágenes

### Slide 1 — Contenedores en AWS

**Título en slide**

CONTENEDORES EN AWS

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Image** / **Imagen**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Un contenedor empaqueta la aplicación y sus dependencias para ejecutarlas de forma consistente entre distintos entornos.
- Una **imagen** es la plantilla inmutable utilizada para crear uno o varios contenedores con la misma configuración.
- Varios contenedores pueden compartir el sistema operativo del host y normalmente consumen menos recursos que una máquina virtual completa por aplicación.
- **Amazon ECS** y **Amazon EKS** orquestan contenedores, mientras **AWS Fargate** proporciona cómputo sin administrar instancias EC2.

> **Ejemplo**  
> Una aplicación HTTP puede almacenar su imagen en Amazon ECR y ejecutarse como varias tasks de Amazon ECS detrás de un Application Load Balancer.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Host EC2 con varios contenedores pequeños frente a varias máquinas virtuales completas. Flecha `misma aplicación → misma imagen`.

### Slide 2 — Amazon ECR

**Título en slide**

AMAZON ECR

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Push / Pull**

#### Conceptos

- **Amazon ECR** almacena y versiona imágenes de contenedores que después pueden utilizar ECS, EKS y AWS Batch.
- Los repositorios pueden ser privados y AWS también ofrece **Amazon ECR Public** para distribuir imágenes públicamente.
- IAM y las políticas del repositorio controlan quién puede realizar `push` o `pull`, junto con funciones como escaneo y políticas de ciclo de vida.
- **ECR almacena imágenes, pero no ejecuta contenedores** ni reemplaza a ECS o EKS.

> **Ejemplo**  
> Un pipeline CI construye una imagen, la sube a ECR y una task definition de ECS utiliza esa imagen durante el despliegue.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

## Sesión 12.2 — Amazon ECS

### Slide 1 — Amazon ECS

**Título en slide**

AMAZON ECS

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**  
> **Task**  
> **Service**

#### Conceptos

- **Amazon ECS** orquesta contenedores mediante un modelo propio de AWS sin necesidad de implementar Kubernetes.
- Un **ECS cluster** agrupa de forma lógica las tasks y puede utilizar capacidad EC2, AWS Fargate o diferentes capacity providers.
- El modelo habitual sigue la secuencia **ECR → task definition → task → service** cuando la aplicación debe permanecer en ejecución.
- Si el escenario exige específicamente **Kubernetes**, herramientas como Helm o compatibilidad con su API, Amazon EKS suele ser la opción adecuada.

> **Ejemplo**  
> Una API REST empaquetada en contenedores se ejecuta como un ECS service detrás de un Application Load Balancer.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Plano de control ECS administrado por AWS con varias tasks debajo y una flecha desde Amazon ECR.

### Slide 2 — Task definition y task

**Título en slide**

TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task**  
> **Container** / **Contenedor**

#### Conceptos

- Una **task definition** describe cómo ejecutar la aplicación e incluye imagen, CPU, memoria, red, variables, volúmenes, logging y roles IAM.
- Cada cambio genera una nueva revisión y una **task** representa una instancia en ejecución de una de esas revisiones.
- Una task puede contener varios contenedores que deben ejecutarse juntos, como una aplicación acompañada por un sidecar.
- La **task** es la unidad que se ejecuta, mientras el **service** mantiene la cantidad requerida de tasks funcionando.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `Task definition v3` → tres tasks idénticas distribuidas entre diferentes Availability Zones.

### Slide 3 — ECS Service

**Título en slide**

ECS SERVICE

#### Nombres en portal y examen

> **ECS service**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** mantiene una aplicación funcionando y sustituye las tasks que fallen.
- El **desired count** define cuántas tasks deben ejecutarse simultáneamente y ECS ajusta la cantidad para alcanzar ese valor.
- El service puede registrar sus tasks automáticamente en un target group de un Application Load Balancer o Network Load Balancer.
- Un service encaja en aplicaciones continuas, mientras un trabajo con inicio y fin puede ejecutarse como una task independiente o mediante AWS Batch.

> **Ejemplo**  
> Una tienda online utiliza un service con `desired count = 4` distribuido entre dos Availability Zones.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Service con varias tasks saludables y una task fallida siendo reemplazada automáticamente.

## Sesión 12.3 — Tipo de lanzamiento

### Slide 1 — ECS con EC2

**Título en slide**

ECS CON EC2

#### Nombres en portal y examen

> **EC2 launch type**  
> **ECS container agent**

#### Conceptos

- Con **EC2 launch type**, las tasks se ejecutan sobre instancias EC2 que forman parte del clúster.
- El **ECS container agent** conecta cada instancia con ECS, recibe las tasks que debe ejecutar y reporta su estado.
- La organización mantiene responsabilidad sobre el sistema operativo, parches, tipos de instancia y capacidad disponible.
- El escalado puede necesitar aumentar primero las tasks del service y después las instancias EC2 si ya no existe capacidad suficiente.

> **Ejemplo**  
> Un clúster puede utilizar instancias EC2 cuando la organización necesita mayor control del host o capacidad ya comprometida.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

### Slide 2 — ECS con Fargate

**Título en slide**

ECS CON FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Fargate launch type**

#### Conceptos

- **AWS Fargate** ejecuta tasks sin que tengas que aprovisionar ni parchear instancias EC2.
- Defines la CPU y memoria necesarias y AWS administra la infraestructura donde se ejecutan los contenedores.
- Las tasks Fargate utilizan `awsvpc`, reciben una interfaz de red propia y pueden tener security groups aplicados directamente.
- Fargate puede utilizarse con **Amazon ECS y Amazon EKS**, por lo que es una opción de cómputo y no un orquestador independiente.

> **Ejemplo**  
> Un equipo pequeño ejecuta una API en ECS con Fargate para reducir la administración de infraestructura.

### Slide 3 — Precio EC2 frente a Fargate

**Título en slide**

EC2 VS FARGATE

#### Nombres en portal y examen

> **EC2 launch type**  
> **Fargate launch type**  
> **Compute Savings Plans**

#### Conceptos

- Con **EC2 launch type** pagas las instancias EC2 del clúster y recursos asociados como EBS cuando corresponda.
- Con **Fargate** pagas principalmente la vCPU y memoria asignadas a las tasks durante su ejecución.
- Los **Compute Savings Plans** también pueden cubrir determinados usos de Fargate y no se limitan únicamente a EC2.
- EC2 puede convenir con cargas grandes y estables, mientras Fargate reduce operación. Ninguno es siempre más barato.

> **Caso Check yourself ES**  
> Comparación del modelo de precio de ECS con EC2 frente a ECS con Fargate, id 24.

> **Logo** `recursos/aws/compute/fargate.svg`

## Sesión 12.4 — Servicio en producción

### Slide 1 — Application Load Balancer y ECS

**Título en slide**

ALB CON AMAZON ECS

#### Nombres en portal y examen

> **Application Load Balancer**  
> **Dynamic port mapping** / **Mapeo dinámico de puertos**  
> **Target group** / **Grupo de destino**

#### Conceptos

- Un **Application Load Balancer** distribuye tráfico HTTP y HTTPS entre las tasks de un ECS service mediante un target group.
- Con ECS sobre EC2 en modo `bridge`, el **dynamic host port mapping** permite usar distintos puertos del host para contenedores que exponen el mismo puerto.
- Las tasks Fargate utilizan `awsvpc` y cada una dispone de su propia ENI e IP dentro de la VPC.
- Los health checks retiran destinos no saludables y permiten que el ALB mantenga tráfico únicamente hacia tasks disponibles.

> **Logo** `recursos/aws/networking/elb.svg`

> **Idea visual**  
> Application Load Balancer en 443 conectado a varias tasks ECS. Mostrar EC2 con puertos dinámicos y Fargate con ENI propia.

ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **AWS Application Auto Scaling**  
> **Target tracking**

#### Conceptos

- **ECS Service Auto Scaling** modifica automáticamente el desired count según cambia la demanda.

**Título en slide**

AMAZON ECS CON EFS

#### Nombres en portal y examen

> **Amazon Elastic File System (Amazon EFS)**  
> **EFS access point**

#### Conceptos

- **Amazon EFS** proporciona almacenamiento persistente y compartido para múltiples tasks, incluso entre diferentes Availability Zones.
- La task definition puede declarar un sistema EFS como volumen y montarlo dentro del contenedor.
- EFS puede utilizarse con ECS sobre EC2 o Fargate sin depender del almacenamiento efímero de una task.
- Cuando varios contenedores necesitan un filesystem compartido, EFS es el patrón natural frente a tratar S3 como un disco tradicional.

## Sesión 12.5 — IAM en ECS

### Slide 1 — Roles IAM en ECS

**Título en slide**

ROLES IAM EN ECS

#### Nombres en portal y examen

> **Task role**  
> **Task execution role**  
> **EC2 instance profile**

#### Conceptos

- El **task role** entrega permisos al código de la aplicación para acceder a servicios AWS como S3 o SQS.
- El **task execution role** permite realizar acciones necesarias al iniciar la task, como descargar imágenes de ECR o enviar logs.
- El **EC2 instance profile** se utiliza con ECS sobre EC2 y proporciona permisos al host y al ECS container agent.
- Para aplicar mínimo privilegio, la aplicación debe utilizar su propio task role en lugar de credenciales estáticas o permisos heredados del host.

> **Ejemplo**  
> Una task usa su task role para escribir en S3 y su execution role para descargar la imagen desde ECR.

> **Logo** `recursos/aws/otros/iam.svg`

> **Idea visual**  
> `Instance profile → EC2 host`, `Execution role → inicio de task`, `Task role → aplicación`.

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue**

#### Conceptos

- **AWS Batch** administra trabajos con inicio y fin como simulaciones, renderizado o procesamiento intensivo de datos.
- El workload se empaqueta como una imagen de contenedor y se envía como un job a una cola.
- Batch ajusta la capacidad necesaria y resulta útil cuando existen muchos trabajos independientes esperando procesamiento.
- A diferencia de un ECS service, un job termina después de completar su trabajo y no necesita permanecer siempre activo.

> **Ejemplo**  
> Miles de simulaciones nocturnas se envían a una job queue y AWS Batch ejecuta los contenedores según la capacidad disponible.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> Job queue → varios trabajos → contenedores → `exit`.

#### Nombres en portal y examen

> **Amazon EventBridge**

### Slide 1 — Amazon EKS

**Título en slide**

AMAZON EKS

#### Nombres en portal y examen

> **Amazon Elastic Kubernetes Service (Amazon EKS)**  
> **Kubernetes**

#### Conceptos

- **Amazon EKS** proporciona Kubernetes administrado y AWS opera el plano de control del clúster.
- Los workloads utilizan las APIs y herramientas estándar de Kubernetes, por lo que encaja cuando el escenario exige esta plataforma.
- Los pods pueden ejecutarse sobre nodos EC2 o mediante **AWS Fargate** según el nivel de control requerido.
- EKS permite integrar Kubernetes con servicios AWS de red, identidad, almacenamiento y observabilidad.

> **Ejemplo**  
> Una empresa que ya utiliza Kubernetes on premises puede migrar sus workloads a Amazon EKS manteniendo el mismo modelo.

> **Managed node group**  
> **Self-managed nodes**

- El almacenamiento persistente puede integrarse mediante controladores CSI con servicios como Amazon EBS y Amazon EFS.

EKS ANYWHERE Y EKS DISTRO

#### Nombres en portal y examen

> **Amazon EKS Anywhere**  
> **Amazon EKS Distro**

- **Amazon EKS Distro** es la distribución de Kubernetes basada en los componentes utilizados por Amazon EKS.

## Sesión 12.9 — Arquitecturas

### Slide 1 — Fargate detrás del ALB

**Título en slide**

FARGATE DETRÁS DEL ALB

#### Conceptos

- El **Application Load Balancer** distribuye tráfico hacia las tasks Fargate registradas en el target group del ECS service.
- Las tasks pueden distribuirse entre distintas Availability Zones sin que el usuario administre instancias EC2.
- Las imágenes se obtienen desde **Amazon ECR** y los permisos se separan mediante task execution role y task role.
- Si la aplicación necesita almacenamiento compartido, las tasks pueden montar **Amazon EFS**.

### Banco español

Una empresa líder en análisis de medios sociales se plantea trasladar su pila de aplicaciones dockerizadas a la nube de AWS. Todavía no tiene claro cómo se compara el precio de Elastic Container Service (ECS) con el tipo de lanzamiento EC2 frente a Elastic Container Service (ECS) con el tipo de lanzamiento Fargate.

¿Cuál de las siguientes opciones es correcta en relación con los precios de estos dos servicios?

A) ECS con tipo de lanzamiento EC2 se cobra según las instancias EC2 y los volúmenes EBS utilizados. ECS con tipo de lanzamiento Fargate se cobra según los recursos de vCPU y memoria que solicite la aplicación en contenedor

B) Tanto ECS con tipo de lanzamiento EC2 como ECS con tipo de lanzamiento Fargate se cobran únicamente según el Elastic Container Service utilizado por hora

C) Tanto ECS con tipo de lanzamiento EC2 como ECS con tipo de lanzamiento Fargate se cobran según los recursos de vCPU y memoria que solicita la aplicación en contenedor

D) Tanto ECS con tipo de lanzamiento EC2 como ECS con tipo de lanzamiento Fargate se cobran según las instancias EC2 y los volúmenes EBS utilizados

✅ **Respuesta** A

💡 **Explicación**  
ECS con EC2 se cobra según las instancias EC2 y los volúmenes EBS utilizados. ECS con Fargate se cobra según los recursos de vCPU y memoria solicitados por la aplicación.

### Banco inglés

A financial services company runs a containerized microservices architecture with Kubernetes in its on-premises data center. Strict industry regulations and internal security policies require that all application data and workloads remain physically inside the on-premises environment. The company’s infrastructure team wants to modernize the Kubernetes stack and take advantage of AWS-managed services and APIs — including automated Kubernetes upgrades, Amazon CloudWatch integration, and access to AWS IAM features — without migrating any data or compute resources to the cloud.

Which AWS solution best meets the company’s requirements for modernization while ensuring that all data remains on premises?

A) Set up a dedicated AWS Direct Connect connection between the on-premises environment and an AWS Region. Deploy Amazon EKS in the cloud and connect it to the local Kubernetes cluster. Use IAM roles and API Gateway to integrate authentication and traffic flow for the hybrid workloads

B) Deploy Amazon ECS with Fargate in a nearby AWS Local Zone. Forward events to the primary region with CloudWatch Logs. Connect the Local Zone to the company’s data center over a VPN. Configure the containers to pull data from on-premises storage through a mounted file share

C) Run the containers on Amazon ECS in a single Region and copy logs to Amazon S3 with AWS DataSync once a day

D) Install an AWS Outposts rack in the company’s data center. Use Amazon EKS Anywhere on Outposts to run the containerized workloads locally while integrating with AWS APIs

✅ **Respuesta** D
