# Módulo M12 — Contenedores

> Dominios 2 y 3.  
> **Ya sabes** una instancia EC2 es una máquina que tú parcheas. Un Application Load Balancer distribuye tráfico HTTP/HTTPS entre destinos.  
> **Aquí aprendes** dónde se guarda una imagen de contenedor, quién ejecuta y escala los contenedores y cuándo el enunciado pide Kubernetes en lugar de la API de ECS.  
> **No se asume** operar un clúster EKS desde consola. AWS App Runner aparece solo como reconocimiento.

## Sesión 12.1 — Registro de imágenes

### Slide 1 — Contenedores

**Título en slide**

CONTENEDORES — LA IDEA

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Container image** / **Imagen de contenedor**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Una imagen empaqueta la aplicación con las dependencias necesarias para ejecutarla.
- Un contenedor es un proceso aislado que comparte el kernel del sistema operativo del host.
- La misma imagen puede utilizarse en desarrollo y producción.
- Un registro almacena las imágenes y un orquestador decide dónde ejecutarlas.
- El orquestador también puede reiniciar contenedores, mantener réplicas y conectarlos con un balanceador.
- Una imagen almacenada en un registro **no se ejecuta sola**.

> **Nota**  
> En este módulo separaremos tres decisiones: dónde guardas la imagen, quién orquesta y dónde corre el cómputo.

> **Idea visual**  
> `Imagen → Registro → Orquestador → Contenedor`. Al lado, varios contenedores pequeños compartiendo un host frente a varias máquinas virtuales completas.

### Slide 2 — Amazon ECR

**Título en slide**

AMAZON ELASTIC CONTAINER REGISTRY

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Image** / **Imagen**

#### Conceptos

- **Amazon ECR** almacena, versiona y distribuye imágenes de contenedores.
- Los repositorios privados se protegen mediante IAM y políticas del repositorio.
- ECS, EKS y AWS Batch pueden hacer `pull` de imágenes almacenadas en ECR.
- También existe **Amazon ECR Public** y su galería pública `gallery.ecr.aws`.
- ECR admite escaneo de vulnerabilidades y políticas de lifecycle para limpiar imágenes antiguas.
- ECR almacena imágenes, pero **no ejecuta contenedores**.

> **Ejemplo**  
> CI construye `api:v3` → la publica en ECR → ECS utiliza esa URI en la task definition.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

> **Idea visual**  
> Icono oficial de **Amazon ECR** como estante de imágenes `v1`, `v2`, `v3`. Flecha `pull` hacia una task ECS.

## Sesión 12.2 — Amazon ECS

### Slide 1 — Amazon ECS

**Título en slide**

AMAZON ELASTIC CONTAINER SERVICE

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**

#### Conceptos

- **Amazon ECS** orquesta contenedores mediante una API nativa de AWS.
- Administra despliegues, reemplazo de tasks, escalado e integración con balanceadores e IAM.
- Un clúster es una agrupación lógica donde ECS ejecuta workloads.
- El cómputo puede provenir de EC2, AWS Fargate u otras capacidades compatibles.
- El modelo básico es **ECR → task definition → task → service**.
- Si el requisito explícito es Kubernetes, el servicio correspondiente es Amazon EKS.

> **Nota**  
> Una aplicación Docker no necesita Kubernetes por defecto. Si no existe ese requisito, ECS suele ser la opción más simple.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Icono oficial de **Amazon ECS** como plano de control. Debajo aparecen varias tasks y una flecha desde Amazon ECR.

### Slide 2 — Task definition y task

**Título en slide**

AMAZON ECS · TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task** / **Tarea**

#### Conceptos

- Una **task definition** describe imagen, CPU, memoria, red, variables, volúmenes, logs y roles IAM.
- Cada cambio genera una nueva revisión de la task definition.
- Una **task** es una instancia en ejecución de esa definición.
- Una task puede contener varios contenedores que deben ejecutarse juntos.
- El patrón sidecar permite añadir un proxy, agente de logs u otro contenedor auxiliar.
- En Fargate debes definir combinaciones compatibles de CPU y memoria.

> **Ejemplo**  
> Una task puede utilizar **0,5 vCPU y 1 GB** de memoria con una variable `ENV=staging`.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> `Task definition v3` → tres tasks idénticas. Dentro de una task aparecen `App + Sidecar`.

### Slide 3 — ECS Service

**Título en slide**

AMAZON ECS SERVICE

#### Nombres en portal y examen

> **ECS service** / **Servicio ECS**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** mantiene tasks de larga duración en ejecución.
- El desired count indica cuántas tasks simultáneas debe mantener.
- Si una task falla, el service intenta reemplazarla.
- Puede registrar sus tasks automáticamente en un target group.
- Application Load Balancer es el patrón habitual para aplicaciones HTTP/HTTPS.
- Un service es distinto de un batch job, que tiene un inicio y un final.

> **Ejemplo**  
> `desired count = 4` mantiene **4 tasks** distribuidas entre al menos **2 AZ** cuando la configuración lo permite.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `ECS Service · desired 4`. Cuatro tasks entre AZ-a y AZ-b. Una task falla y aparece otra reemplazándola.

## Sesión 12.3 — Tipo de lanzamiento

### Slide 1 — ECS con EC2

**Título en slide**

AMAZON ECS · EC2

#### Nombres en portal y examen

> **EC2 launch type** / **Tipo de lanzamiento EC2**  
> **ECS container agent** / **Agente de contenedor ECS**

#### Conceptos

- En EC2 tú proporcionas las instancias que forman la capacidad del clúster.
- El agente ECS registra cada instancia y recibe las tasks que debe ejecutar.
- Tú sigues siendo responsable del sistema operativo, parches y capacidad de los hosts.
- Encaja cuando necesitas control del host, tipos de instancia específicos o capacidad ya comprometida en EC2.
- El escalado tiene **2 niveles**: número de tasks y número de instancias del clúster.
- Un capacity provider puede conectar el crecimiento de tasks con un Auto Scaling group.

> **Nota**  
> Escalar el service no crea automáticamente espacio infinito dentro de las instancias EC2.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> AZ-a y AZ-b con varias instancias EC2. Cada instancia lleva `ECS Agent` y contiene varias tasks.

### Slide 2 — AWS Fargate

**Título en slide**

AWS FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Serverless compute for containers** / **Cómputo sin administrar servidores para contenedores**

#### Conceptos

- **AWS Fargate** ejecuta tasks o pods sin que administres instancias EC2.
- Defines CPU y memoria y AWS proporciona la infraestructura subyacente.
- Fargate funciona con Amazon ECS y Amazon EKS.
- En ECS, las tasks Fargate utilizan obligatoriamente el modo de red `awsvpc`.
- Cada task recibe su propia ENI y puede tener security groups.
- Escalar un ECS service en Fargate consiste principalmente en aumentar o reducir sus tasks.

> **Nota**  
> Fargate es una capa de cómputo. ECS y EKS siguen siendo los orquestadores.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Icono oficial de **AWS Fargate** sobre tasks distribuidas entre dos AZ. No aparece ninguna instancia EC2 administrada por el usuario.

### Slide 3 — Facturación EC2 y Fargate

**Título en slide**

AWS FARGATE · FACTURACIÓN

#### Conceptos

- Con ECS sobre EC2 pagas las instancias EC2, almacenamiento y demás recursos utilizados por el clúster.
- Con Fargate pagas la **vCPU, memoria y almacenamiento adicional** solicitados por la task o pod.
- La facturación de Linux se calcula por segundo con un mínimo de **1 minuto**.
- Para Windows el mínimo de facturación es de **5 minutos**.
- Fargate incluye **20 GB** de almacenamiento efímero y puede configurarse hasta **200 GiB** en ECS Linux compatible.
- Los **Compute Savings Plans** también pueden cubrir consumo de Fargate.

> **Nota**  
> EC2 puede resultar conveniente con uso estable y alta utilización. Fargate prioriza reducir la administración del host.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Dos recibos. `EC2 → instancia + almacenamiento`. `Fargate → vCPU + memoria + almacenamiento adicional`. Debajo `1 min Linux · 5 min Windows`.

## Sesión 12.4 — Servicio en producción

### Slide 1 — Application Load Balancer

**Título en slide**

APPLICATION LOAD BALANCER

#### Nombres en portal y examen

> **Application Load Balancer (ALB)**  
> **Target group** / **Grupo de destino**  
> **Dynamic host port mapping** / **Mapeo dinámico del puerto del host**

#### Conceptos

- ALB es el balanceador habitual para servicios ECS que exponen HTTP o HTTPS.
- En ECS sobre EC2 con modo `bridge`, puede utilizar **dynamic host port mapping**.
- Por ejemplo, varias tasks pueden escuchar internamente en `80` y usar puertos del host como `32768`, `32769` o `32770`.
- En Fargate se utiliza `awsvpc`, por lo que el target group registra la **IP de la task** y su container port.
- Las tasks Fargate requieren target type **`ip`**, no `instance`.
- Classic Load Balancer no está soportado para servicios Fargate.

> **Nota**  
> No describas Fargate como si utilizara puertos efímeros del host EC2. No existe un host tuyo que registrar en el target group.

> **Logo** `recursos/aws/networking/elb.svg`

> **Idea visual**  
> Dos mini diagramas. `ECS EC2 bridge → instance:32768 / :32769`. `Fargate awsvpc → IP-task:8080`.

### Slide 2 — ECS Service Auto Scaling

**Título en slide**

AMAZON ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **AWS Application Auto Scaling**  
> **Target tracking** / **Seguimiento de objetivo**

#### Conceptos

- Service Auto Scaling aumenta o reduce el **desired count** automáticamente.
- Amazon ECS utiliza **Application Auto Scaling** para aplicar estas políticas.
- Puede escalar mediante CPU media, memoria media o `ALBRequestCountPerTarget`.
- Target tracking intenta mantener la métrica cerca del valor objetivo.
- En EC2, escalar tasks y escalar las instancias del clúster son procesos distintos.
- En Fargate no necesitas un Auto Scaling group de hosts.

> **Ejemplo**  
> El service puede aumentar tasks cuando la CPU media intenta superar un objetivo de **70 %**.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Gráfico `CPU 70 %` → Application Auto Scaling → `desired count 2 → 5`. Al margen `ASG EC2 = otro nivel`.

### Slide 3 — Amazon EFS

**Título en slide**

AMAZON ELASTIC FILE SYSTEM

#### Nombres en portal y examen

> **Amazon Elastic File System (Amazon EFS)**  
> **EFS access point** / **Punto de acceso EFS**

#### Conceptos

- EFS proporciona almacenamiento de archivos persistente y compartido mediante NFS.
- Varias tasks pueden montar el mismo sistema de archivos desde diferentes Availability Zones.
- ECS admite EFS tanto con EC2 como con Fargate.
- EFS encaja cuando varias réplicas necesitan leer o escribir los mismos archivos.
- Fargate también puede utilizar EBS en escenarios compatibles, pero EBS es almacenamiento de bloques para una task y no sustituye un filesystem compartido Multi-AZ.
- Amazon S3 se consume normalmente mediante su API y no sustituye este patrón de filesystem compartido.

> **Nota**  
> Si el enunciado pide almacenamiento persistente **compartido** entre varias tasks, EFS es la pista principal.

> **Logo** `recursos/aws/storage/efs.svg`

> **Idea visual**  
> Amazon EFS en el centro. Tasks Fargate en AZ-a y AZ-b montan el mismo filesystem.

## Sesión 12.5 — IAM en ECS

### Slide 1 — AWS IAM

**Título en slide**

AWS IAM · ROLES PARA AMAZON ECS

#### Nombres en portal y examen

> **Task role** / **Rol de tarea**  
> **Task execution role** / **Rol de ejecución de tarea**  
> **Container instance role** / **Rol de instancia de contenedor**

#### Conceptos

- El **task role** entrega permisos AWS al código que se ejecuta dentro del contenedor.
- El **task execution role** permite a ECS o Fargate preparar la task, por ejemplo hacer pull desde ECR o enviar logs.
- También puede permitir leer secretos o parámetros referenciados durante el arranque.
- En ECS sobre EC2, el **container instance role** permite al agente del host comunicarse con ECS.
- En Fargate no existe una instancia EC2 tuya con instance profile.
- Separar los roles permite aplicar mínimo privilegio a cada aplicación.

> **Ejemplo**  
> La app necesita leer S3 → **task role**.  
> ECS necesita hacer pull de ECR y escribir logs → **task execution role**.

> **Logo** `recursos/aws/otros/iam.svg`

> **Idea visual**  
> Icono oficial de AWS IAM con tres flechas. `Task role → App`, `Execution role → arranque/logs`, `Container instance role → host EC2`.

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue** / **Cola de trabajos**

#### Conceptos

- **AWS Batch** ejecuta trabajos con inicio y fin a gran escala.
- Cada job puede utilizar una imagen de contenedor.
- Los compute environments pueden utilizar capacidad EC2, Spot, Fargate o integraciones compatibles con EKS.
- Batch administra la cola y coloca los trabajos según recursos y prioridad.
- Encaja en renderizado, simulaciones, genómica o procesamiento intensivo.
- No sustituye un ECS service que debe permanecer atendiendo tráfico continuamente.

> **Nota**  
> Miles de trabajos que deben esperar capacidad → Batch. Una sola task periódica → normalmente ECS RunTask con Scheduler.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> Icono oficial de **AWS Batch**. `Job Queue → Compute Environment → Containers`. Varias tasks terminan con `exit`.

### Slide 2 — Amazon EventBridge Scheduler

**Título en slide**

AMAZON EVENTBRIDGE SCHEDULER

#### Nombres en portal y examen

> **Amazon EventBridge Scheduler**  
> **Amazon ECS RunTask**  
> **Cron** / **Rate** / **One-time schedule**

#### Conceptos

- EventBridge Scheduler puede ejecutar una task ECS sin mantener un service encendido.
- Admite horarios basados en cron, rate y ejecuciones de una sola vez.
- El target puede ser la API **ECS `RunTask`**.
- Encaja en scripts dockerizados que se ejecutan cada hora o cada noche.
- Una task Fargate puede arrancar, procesar el trabajo y terminar sin EC2 permanente.
- Las antiguas scheduled rules siguen existiendo, pero para diseños nuevos AWS recomienda Scheduler.

> **Nota**  
> Step Functions coordina varios pasos. Scheduler resuelve la programación temporal de una ejecución.

> **Logo** `recursos/aws/integration/eventbridge.svg`

> **Idea visual**  
> Icono oficial de Amazon EventBridge. Reloj → Scheduler → `ECS RunTask` → task Fargate → termina.

## Sesión 12.7 — Amazon EKS

### Slide 1 — Amazon EKS

**Título en slide**

AMAZON ELASTIC KUBERNETES SERVICE

#### Nombres en portal y examen

> **Amazon Elastic Kubernetes Service (Amazon EKS)**  
> **Kubernetes**

#### Conceptos

- **Amazon EKS** permite ejecutar Kubernetes con un control plane administrado por AWS.
- Los workloads se ejecutan como pods sobre capacidad compatible.
- Puedes utilizar nodos EC2 o AWS Fargate según el diseño.
- EKS conserva la API y herramientas estándar de Kubernetes.
- Encaja cuando ya utilizas Kubernetes, Helm u otros componentes de su ecosistema.
- Si no existe un requisito Kubernetes, ECS suele implicar menos complejidad.

> **Nota**  
> ECS y EKS orquestan contenedores. La diferencia principal para el examen es la API y el ecosistema requerido.

AMAZON EKS · NODOS Y FARGATE

#### Nombres en portal y examen

> **Managed node group** / **Grupo de nodos administrado**  
> **Self-managed nodes** / **Nodos autogestionados**  
> **AWS Fargate**

- EKS puede utilizar drivers CSI para almacenamiento persistente como EBS o EFS.

IAM ROLES FOR SERVICE ACCOUNTS

#### Nombres en portal y examen

> **IAM Roles for Service Accounts (IRSA)**  
> **Service account** / **Cuenta de servicio**

## Sesión 12.8 — Variantes y reconocimiento

### Slide 1 — Amazon EKS Anywhere

**Título en slide**

AMAZON EKS ANYWHERE

#### Nombres en portal y examen

> **Amazon EKS Anywhere**

#### Conceptos

- **EKS Anywhere** permite crear y operar Kubernetes sobre infraestructura administrada por el cliente.
- Puede ejecutarse en entornos como bare metal, VMware vSphere y otras plataformas compatibles.
- Puede funcionar conectado a AWS o incluso en entornos desconectados.
- El control plane y los nodos permanecen en la infraestructura del cliente.
- Puede integrarse opcionalmente con servicios AWS para identidad y observabilidad.
- **EKS Anywhere no se ejecuta sobre EC2, Local Zones ni AWS Outposts.**

> **Nota**  
> EKS Anywhere significa Kubernetes administrado por ti fuera de la infraestructura regional de EKS. No lo mezcles con Amazon EKS on AWS Outposts.

### Slide 2 — Amazon EKS on AWS Outposts

**Título en slide**

AMAZON EKS ON AWS OUTPOSTS

#### Nombres en portal y examen

> **Amazon EKS on AWS Outposts**  
> **Extended cluster** / **Clúster extendido**  
> **Local cluster** / **Clúster local**

#### Conceptos

- Amazon EKS puede ejecutar workloads Kubernetes en infraestructura **AWS Outposts** instalada on-premises.
- En un extended cluster, el control plane permanece en una AWS Region y los nodos corren en Outposts.
- En un local cluster, el control plane y los nodos pueden ejecutarse localmente en el Outpost.
- En ambos diseños, el control plane forma parte del servicio Amazon EKS.
- Los local clusters son útiles cuando existen requisitos de residencia o continuidad local.
- Esto es diferente de **EKS Anywhere**.

> **Nota**  
> `Outposts + Kubernetes administrado mediante Amazon EKS` → **EKS on AWS Outposts**, no EKS Anywhere.

### Slide 5 — AWS App Runner

**Título en slide**

AWS APP RUNNER

#### Nombres en portal y examen

> **AWS App Runner**

#### Conceptos

- **AWS App Runner** despliega aplicaciones web desde código fuente o una imagen de contenedor.
- Administra despliegue, ejecución, HTTPS y auto scaling con poca configuración.
- No requiere crear un clúster ECS o EKS.
- En este módulo se utiliza como servicio de reconocimiento, no de profundidad.
- Si el enunciado exige task definitions, ALB o almacenamiento compartido entre tasks, piensa primero en ECS.
- Si exige Kubernetes, el servicio correspondiente es EKS.

> **Nota**  
> App Runner abstrae más infraestructura que ECS, pero también ofrece menos control sobre el modelo de orquestación.

> **Idea visual**  
> Repositorio o imagen → **AWS App Runner** → aplicación HTTPS. Nota `sin administrar clúster`.

## Sesión 12.9 — Arquitecturas

### Slide 1 — Fargate detrás del ALB

**Título en slide**

ARQUITECTURA · ECS FARGATE DETRÁS DEL ALB

#### Conceptos

- El usuario entra mediante un Application Load Balancer.
- El target group registra las **IP de las tasks Fargate**.
- El ECS service mantiene el desired count entre al menos **2 AZ**.
- ECR almacena la imagen utilizada por la task definition.
- El task execution role permite el pull y las operaciones de plataforma necesarias.
- El task role entrega a la aplicación sus permisos sobre otros servicios AWS.

> **Nota**  
> No hay Auto Scaling group de instancias EC2 porque el cómputo utiliza AWS Fargate.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**
>

A healthcare company has deployed its web application on Amazon Elastic Container Service (Amazon ECS) container instances that run behind an Application Load Balancer. The website slows down when traffic spikes, and website availability is also reduced. The development team has configured Amazon CloudWatch alarms so the team is notified whenever there is an availability constraint and can scale out resources. The company wants an automated solution that responds to these events.

Which of the following addresses the given use case?

A) Configure AWS Auto Scaling to scale out the Amazon ECS cluster when CPU utilization of the Application Load Balancer rises above a threshold

B) Configure AWS Auto Scaling to scale out the Amazon ECS cluster when CPU utilization of the Application Load Balancer's target group rises above a threshold

C) Configure AWS Auto Scaling to scale out the Amazon ECS cluster when CPU utilization of the ECS service rises above a threshold

D) Configure AWS Auto Scaling to scale out the Amazon ECS cluster when CPU utilization of the CloudWatch alarm rises above a threshold

✅ **Respuesta** C

💡 **Explanation**  
Amazon ECS Service Auto Scaling can use the **average CPU utilization of the ECS service** to increase the desired number of tasks when demand rises. CloudWatch provides the metric and alarms, while Application Auto Scaling changes the task count. If the service uses EC2 capacity and the cluster no longer has room for more tasks, the EC2 capacity must scale separately.

An enterprise hosts a microservices application on Amazon EKS, with the workload running on EC2 worker nodes. A frontend UI service talks to Amazon DynamoDB, while a data-processing service stores and retrieves files in Amazon S3. Least privilege must be enforced strictly: UI Pods may reach only DynamoDB, and data-processing Pods may reach only S3.

Which approach best applies these access controls inside the EKS cluster?

A) Attach an IAM policy to each Pod directly through Kubernetes annotations. Put the S3 policy on the data-service Pods and the DynamoDB policy on the UI Pods

B) Create IAM policies that grant DynamoDB and S3 access, then attach both policies to the EC2 instance profile of the EKS nodes. Rely on Kubernetes role-based access control (RBAC) to govern service-level permissions inside the cluster

C) Share one Kubernetes service account among all Pods. Bind a single IAM role to that account and include both the AmazonS3FullAccess and AmazonDynamoDBFullAccess policies

> Amazon EFS currently also offers **Elastic Throughput**, which AWS recommends for many spiky or unpredictable workloads. That mode is not present among the alternatives in this bank item.

An engineering team wants to orchestrate multiple Amazon ECS task types that run on Amazon EC2 instances belonging to the Amazon ECS cluster. Output and state data for every task need to be stored. Each task produces approximately 20 megabytes of data, and hundreds of tasks could be running at a time. Because old outputs are archived, the storage size is not expected to exceed 1 terabyte.

Which of the following would you recommend as a solutions architect as an optimized solution for high-frequency reading and writing?

A) Use an Amazon DynamoDB table that every instance in the ECS cluster can access

B) Use Amazon EFS with Bursting Throughput mode

C) Use Amazon EFS with Provisioned Throughput mode

D) Use an Amazon EBS volume mounted on the Amazon ECS cluster instances

✅ **Respuesta** C

💡 **Explanation**  
**Amazon EFS** provides shared file storage that all of the ECS tasks can access. With a relatively small file system of less than **1 TB** and sustained high-frequency reads and writes, **Provisioned Throughput** can provide throughput independently of the file system size and burst-credit balance. Current EFS also offers Elastic Throughput, but that option is not included in this bank question.
