## Sesión 12.1 — ECS

### Slide 1 — Amazon ECS

**Título en slide**

AMAZON ELASTIC CONTAINER SERVICE (AMAZON ECS)

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)** — **task** — **task definition** — **service**

#### Conceptos

- **Amazon ECS** es el servicio de orquestación de contenedores de AWS.
- Una **task definition** describe los contenedores, imágenes, CPU, memoria, puertos, roles y otros parámetros necesarios para ejecutar una task.
- Una **task** es una ejecución de esa definición y puede contener uno o varios contenedores que deben ejecutarse juntos.
- Un **service** mantiene el número deseado de tasks en ejecución y puede registrarlas detrás de un load balancer.
- **ECS Service Auto Scaling** puede aumentar o reducir el número de tasks según métricas como CPU, memoria o requests por target.

> **Nota**  
> ECS decide cómo mantener y orquestar las tasks. El cómputo donde se ejecutan puede provenir de EC2 o de AWS Fargate.

**Docs**  
[What is Amazon ECS?](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html)  
[Automatically scale your Amazon ECS service](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-auto-scaling.html)

**Logo** `recursos/aws/otros/elastic-container-service.svg`

**Idea visual**  
Icono oficial de **Amazon ECS** como elemento central. Una `Task Definition` genera varias `Tasks` dentro de un `Service`. El service mantiene `Desired 3` y reemplaza una task que desaparece.

### Slide 2 — Roles de ECS

**Título en slide**

TASK ROLE Y TASK EXECUTION ROLE

#### Nombres en portal y examen

> **Task role** — **task execution role** — **container instance role**

#### Conceptos

- El **task role** entrega permisos de AWS al código que se ejecuta dentro de los contenedores.
- Una aplicación que necesita leer Amazon S3 o escribir en DynamoDB utiliza los permisos de su task role.
- El **task execution role** permite que ECS realice acciones necesarias para iniciar la task, como descargar una imagen privada desde Amazon ECR o enviar logs mediante determinadas configuraciones.
- Cuando ECS utiliza instancias EC2, el **container instance role** permite que el ECS agent del host se comunique con el servicio ECS.

> **Nota**  
> El permiso de la aplicación pertenece al **task role**. No debe heredarse simplemente del rol de la instancia EC2 que ejecuta el contenedor.

**Docs**

### Slide 3 — AWS Fargate

**Título en slide**

AWS FARGATE

#### Nombres en portal y examen

> **AWS Fargate** — **serverless compute for containers**

#### Conceptos

- **AWS Fargate** ejecuta contenedores sin que tengas que aprovisionar ni administrar las instancias que forman la capacidad de cómputo.
- En ECS con Fargate defines los recursos de la task y AWS administra la infraestructura subyacente.
- Fargate cobra principalmente según los recursos de vCPU, memoria y almacenamiento utilizados por las tasks.
- Los **Compute Savings Plans** pueden reducir el coste de Fargate. Los EC2 Instance Savings Plans están orientados al uso de EC2 y no cubren Fargate.
- Las tasks de Fargate pueden utilizar almacenamiento persistente como **Amazon EFS** y, en configuraciones compatibles, Amazon EBS.

> **Nota**  
> Elegir EC2 para ejecutar ECS devuelve a tu equipo responsabilidades sobre las instancias. Elegir Fargate elimina la administración del host, pero no elimina la responsabilidad sobre la aplicación, imagen, configuración, IAM o datos.

**Docs**

[Amazon ECS task definition parameters for Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters.html)

### Slide 4 — Fargate y almacenamiento persistente

**Título en slide**

FARGATE CON AMAZON EFS

#### Conceptos

- Una task de Fargate puede montar un filesystem **Amazon EFS** cuando necesita conservar archivos más allá de la vida del contenedor.
- Varias tasks pueden acceder al mismo EFS cuando el workload necesita almacenamiento de archivos compartido.
- Un **EFS access point** puede definir la entrada y los permisos utilizados por la aplicación.
- Amazon S3 sigue siendo object storage y no sustituye directamente el comportamiento de un filesystem compartido como EFS.

> **Nota**  
> Si una aplicación containerizada debe mantener archivos persistentes y compartidos sin administrar servidores, la combinación **Fargate + EFS** es un patrón importante para el examen.

**Docs**

### Slide 5 — ECS detrás del ALB

**Título en slide**

ECS SERVICE Y APPLICATION LOAD BALANCER

#### Conceptos

- Un ECS service puede registrar automáticamente sus tasks en un target group.
- El **Application Load Balancer** reparte las solicitudes entre las tasks saludables.
- Con ECS sobre EC2, el ALB admite **dynamic host port mapping** para ejecutar varias tasks en una misma instancia utilizando puertos distintos.
- Las tasks Fargate utilizan networking `awsvpc` y se registran normalmente como targets de tipo `ip`.

> **Nota**  
> El ALB ya se estudió en M6. Aquí importa entender que el destino deja de ser necesariamente una instancia EC2 y pasa a ser una task del service.

### Slide 6 — Amazon ECR

**Título en slide**

AMAZON ELASTIC CONTAINER REGISTRY (AMAZON ECR)

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)** — **repository** — **container image**

#### Conceptos

- **Amazon ECR** almacena y distribuye container images y artefactos compatibles con OCI.
- Las imágenes se organizan dentro de repositories y pueden utilizar tags o digests.
- Amazon ECS y Amazon EKS pueden descargar imágenes desde ECR para iniciar sus workloads.
- ECR almacena imágenes, pero no ejecuta los contenedores.

> **Nota**  
> Piensa en ECR como el registro. ECS o EKS son quienes orquestan la ejecución.

### Slide 7 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch** — **job** — **job queue** — **compute environment**

#### Conceptos

- **AWS Batch** organiza trabajos containerizados que empiezan, procesan una tarea y terminan.
- Los jobs esperan en una **job queue** hasta que pueden ejecutarse en un compute environment.
- AWS Batch puede utilizar capacidad administrada basada en EC2 o AWS Fargate.
- Un workload batch no debe confundirse con un ECS service diseñado para permanecer disponible y recibir solicitudes continuamente.

> **Nota**  
> AWS Batch decide cuándo y dónde ejecutar jobs. Fargate puede ser la capacidad serverless utilizada por esos jobs. Para ejecutar jobs en un horario, Amazon EventBridge Scheduler puede enviar la ejecución a AWS Batch.

**Docs**  
[Components of AWS Batch](https://docs.aws.amazon.com/batch/latest/userguide/batch_components.html)  
[Fargate compute environments](https://docs.aws.amazon.com/batch/latest/userguide/fargate.html)

**Idea visual**  
Icono oficial de **AWS Batch**. Una `Job Queue` contiene tres trabajos. Una flecha lleva cada job hacia un compute environment con **AWS Fargate**. Cada contenedor termina después de completar su procesamiento.

AMAZON ELASTIC KUBERNETES SERVICE (AMAZON EKS)

#### Nombres en portal y examen

> **Amazon Elastic Kubernetes Service (Amazon EKS)** — **Kubernetes** — **pod**

#### Conceptos

- **Amazon EKS** es el servicio administrado de AWS para ejecutar Kubernetes.

### Slide 2 — EKS Pod Identity e IRSA

**Título en slide**

PERMISOS PARA LOS PODS

#### Nombres en portal y examen

> **EKS Pod Identity** — **IAM Roles for Service Accounts (IRSA)** — **service account**

#### Conceptos

- Los pods no deben guardar **access keys** estáticas para llamar a servicios AWS.
- **EKS Pod Identity** permite asociar permisos IAM a una Kubernetes service account y es la opción recomendada por AWS para nuevos workloads cuando el entorno la soporta.
- **IRSA** también asocia un IAM role con una Kubernetes service account mediante OIDC y continúa siendo una opción soportada.
- IRSA sigue siendo relevante en entornos donde EKS Pod Identity no está disponible, incluidos los pods de EKS que utilizan AWS Fargate.

> **Nota**  
> Tanto Pod Identity como IRSA buscan entregar credenciales temporales y permisos de mínimo privilegio a la aplicación sin reutilizar el IAM role completo del worker node.

## Sesión 12.3 — Arquitectura, Fargate detrás del ALB

### Slide 1 — Tasks sin instancia

**Título en slide**

ARQUITECTURA, TASKS SIN INSTANCIA

#### Conceptos

- El Application Load Balancer recibe las solicitudes de los usuarios y las distribuye entre las tasks saludables.
- Un ECS service mantiene varias tasks de **AWS Fargate** distribuidas entre Availability Zones.
- Las tasks descargan su container image desde **Amazon ECR** cuando se inician.
- Cada task Fargate obtiene networking propio y puede utilizar un security group.
- No existe una instancia EC2 del cluster que el equipo tenga que parchear.

> **Nota**  
> El ALB y los security groups ya se estudiaron. Aquí cambia el destino del tráfico, que ahora son tasks Fargate registradas mediante sus IP privadas.

6. Las tasks aparecen dentro de un **Amazon ECS Service**.
