## Sesión 12.1 — Registro de imágenes

### Slide 1 — Contenedores en AWS

**Título en slide**

CONTENEDORES EN AWS

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Image** / **Imagen**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Un contenedor empaqueta la aplicación y sus dependencias para ejecutarlas de forma consistente entre diferentes entornos.
- Una **imagen** es una plantilla inmutable utilizada para crear uno o varios contenedores con la misma configuración.
- Los contenedores permiten ejecutar aplicaciones de forma aislada sin necesitar una máquina virtual completa para cada workload.
- En AWS debes distinguir dónde se almacena la imagen, quién orquesta los contenedores y qué capacidad de cómputo utilizan.

> **Ejemplo**  
> Una aplicación puede guardar su imagen en un registro y después crear múltiples contenedores idénticos a partir de ella.

> **Idea visual**  
> `Imagen → contenedores`. A un lado varias VMs completas para mostrar la diferencia conceptual.

### Slide 2 — Amazon Elastic Container Registry

**Título en slide**

AMAZON ELASTIC CONTAINER REGISTRY

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Push / Pull**

#### Conceptos

- **Amazon ECR** es el registro administrado de AWS para almacenar imágenes Docker, imágenes OCI y otros artefactos compatibles.
- Los repositorios pueden ser privados y **Amazon ECR Public** permite distribuir imágenes públicamente.
- IAM y las repository policies controlan quién puede realizar `push` o `pull` sobre las imágenes.
- ECR ofrece image scanning y lifecycle policies, pero **no ejecuta ni orquesta contenedores**.

> **Nota**  
> El patrón habitual es `crear imagen → push a Amazon ECR → orquestador hace pull → ejecuta contenedor`.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

> **Idea visual**  
> Amazon ECR como estante de imágenes con flechas `push` y `pull`. No mostrar CPU ni contenedores ejecutándose dentro de ECR.

## Sesión 12.2 — Amazon ECS

### Slide 1 — Amazon Elastic Container Service

**Título en slide**

AMAZON ELASTIC CONTAINER SERVICE

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**  
> **Task**  
> **Service**

#### Conceptos

- **Amazon ECS** es el servicio completamente administrado de AWS para desplegar, administrar y escalar aplicaciones en contenedores.
- ECS utiliza su propio modelo de orquestación y no requiere instalar ni operar Kubernetes.
- Un cluster agrupa la capacidad donde se ejecutan los workloads y puede utilizar EC2, AWS Fargate o capacidad externa compatible.
- ECS se integra de forma nativa con servicios AWS de balanceo, identidad, observabilidad, almacenamiento y eventos.

> **Nota**  
> Si el escenario exige específicamente **Kubernetes**, la alternativa dentro de AWS es Amazon EKS.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Amazon ECS como plano de control con varias tasks debajo y Amazon ECR entregando la imagen.

### Slide 2 — Task definition y task

**Título en slide**

TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task**  
> **Container** / **Contenedor**

#### Conceptos

- Una **task definition** describe la imagen, CPU, memoria, red, variables, volúmenes, logging y roles necesarios para ejecutar la aplicación.
- Cada actualización crea una revisión y una **task** representa una instancia en ejecución de una revisión concreta.
- Una task puede incluir varios contenedores que necesitan ejecutarse juntos, como una aplicación y un sidecar.
- Varias tasks pueden utilizar la misma task definition para ejecutar réplicas idénticas de una aplicación.

> **Nota**  
> Una task definition es una plantilla. Una task es la ejecución real de esa plantilla.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `Task definition v3 → Task 1, Task 2, Task 3`.

### Slide 3 — ECS Service

**Título en slide**

ECS SERVICE

#### Nombres en portal y examen

> **ECS service**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** mantiene aplicaciones de larga duración funcionando y reemplaza las tasks que fallen.
- El **desired count** define cuántas tasks deben ejecutarse simultáneamente.
- El service puede registrar sus tasks en un target group para recibir tráfico desde un balanceador.
- Para trabajos con inicio y fin puedes utilizar una task independiente en lugar de mantener un service permanente.

> **Ejemplo**  
> Un service con `desired count = 4` intenta mantener cuatro tasks funcionando aunque alguna falle.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `Desired count 4`. Cuatro tasks y una de ellas siendo reemplazada.

### Slide 4 — ECS con capacidad EC2

**Título en slide**

ECS CON CAPACIDAD EC2

#### Nombres en portal y examen

> **EC2 capacity**  
> **ECS container agent**  
> **Capacity provider**

#### Conceptos

- Las tasks pueden ejecutarse sobre instancias EC2 registradas dentro del cluster de Amazon ECS.
- El **ECS container agent** conecta cada instancia con ECS, recibe las tasks y reporta su estado.
- La organización mantiene el sistema operativo, los parches, el tipo de instancia y la capacidad disponible.
- Si aumentan las tasks y ya no existe espacio suficiente, también debe aumentar la capacidad EC2 del cluster.

> **Nota**  
> Los capacity providers pueden integrar ECS con un Auto Scaling Group para administrar mejor la capacidad.

> **Idea visual**  
> Dos instancias EC2 con ECS agent y varias tasks distribuidas sobre ellas.

## Sesión 12.3 — AWS Fargate

### Slide 1 — AWS Fargate

**Título en slide**

AWS FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Serverless compute for containers**  
> **Fargate task**

#### Conceptos

- **AWS Fargate** proporciona capacidad de cómputo para contenedores sin aprovisionar ni administrar instancias EC2.
- Defines los recursos necesarios para el workload y AWS administra la infraestructura subyacente.
- Fargate puede utilizarse con **Amazon ECS** y **Amazon EKS**, por lo que no es un orquestador independiente.
- Encaja cuando el escenario prioriza contenedores con **mínima administración de servidores**.

> **Nota**  
> Fargate es un motor de cómputo serverless y pay as you go para contenedores.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Amazon ECS y Amazon EKS apuntando hacia AWS Fargate. Debajo, contenedores sin instancias EC2 visibles.

---

### Slide 2 — Networking en Fargate

**Título en slide**

FARGATE Y AWVPC

#### Conceptos

- Las tasks Fargate de Amazon ECS requieren el modo de red **`awsvpc`**.
- Cada task obtiene su propia interfaz de red dentro de la VPC y puede utilizar security groups.
- El aislamiento de cada task evita compartir la ENI, CPU o memoria con otra task Fargate.
- Un balanceador puede registrar directamente la IP y el puerto de las tasks cuando utiliza targets de tipo IP.

> **Idea visual**  
> Tres tasks Fargate con tres ENI independientes dentro de una VPC.

---

### Slide 3 — CPU, memoria y almacenamiento

**Título en slide**

FARGATE RECURSOS

#### Conceptos

- Las tasks Fargate utilizan combinaciones admitidas de **vCPU y memoria** definidas en la task definition.
- Una configuración de **0,25 vCPU** admite **512 MiB, 1 GB o 2 GB** de memoria.
- En Fargate Linux con platform version **1.4.0 o posterior**, cada task incluye **20 GiB** de almacenamiento efímero por defecto.
- El almacenamiento efímero puede configurarse hasta **200 GiB** cuando el workload necesita más espacio temporal.

> **Nota**  
> Estos valores describen recursos de la task y no sustituyen un filesystem persistente cuando los datos deben sobrevivir al ciclo de vida del contenedor.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Task con bloques `vCPU`, `RAM` y `20 GiB ephemeral`.

---

### Slide 4 — EC2 frente a Fargate

**Título en slide**

EC2 VS FARGATE

#### Conceptos

- Con capacidad EC2 pagas las instancias del cluster y los recursos asociados aunque parte de esa capacidad quede sin utilizar.
- Con Fargate pagas principalmente la vCPU y memoria configuradas para las tasks durante su ejecución.
- **Compute Savings Plans** pueden aplicar a determinados consumos tanto de EC2 como de Fargate.
- EC2 ofrece mayor control de la infraestructura y Fargate reduce operación, por lo que ninguno es siempre la opción más económica.

> **Caso Check yourself ES**  
> Comparación del modelo de precio de ECS sobre EC2 frente a ECS con Fargate, id 24.

> **Idea visual**  
> `EC2 → instancia + recursos` frente a `Fargate → vCPU + memoria`.

## Sesión 12.4 — ECS en producción

### Slide 1 — Balanceo de tasks

**Título en slide**

BALANCEO DE TASKS ECS

#### Conceptos

- Un ECS service puede registrar sus tasks en un target group para distribuir tráfico entre varias réplicas.
- Con tasks sobre EC2 en modo `bridge`, el **dynamic host port mapping** permite utilizar diferentes puertos del host.
- Con Fargate y `awsvpc`, cada task posee su propia IP y puede registrarse directamente como target.
- Los health checks evitan enviar solicitudes a tasks no saludables mientras ECS las reemplaza.

> **Nota**  
> Para HTTP y HTTPS suele utilizarse Application Load Balancer. Este servicio ya fue estudiado anteriormente y aquí solo se aplica al patrón ECS.

> **Idea visual**  
> ALB → target group → tres tasks ECS.

---

### Slide 2 — ECS Service Auto Scaling

**Título en slide**

ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **Target tracking**

#### Conceptos

- ECS Service Auto Scaling cambia automáticamente el **desired count** para responder a variaciones de carga.
- Las políticas pueden utilizar CPU promedio, memoria promedio o solicitudes por target como señales de escalado.
- Target tracking intenta mantener una métrica cerca del valor objetivo configurado.
- Con capacidad EC2 debes distinguir entre escalar las tasks y escalar las instancias que forman el cluster.

> **Ejemplo**  
> Un aumento sostenido de CPU puede incrementar el desired count de `2` a `5`.

> **Idea visual**  
> CPU ↑ → desired count `2 → 5`.

### Slide 3 — Almacenamiento compartido en ECS

**Título en slide**

ALMACENAMIENTO COMPARTIDO EN ECS

#### Conceptos

- Las tasks pueden montar **Amazon EFS** cuando varias réplicas necesitan acceder al mismo sistema de archivos persistente.
- EFS puede utilizarse con ECS sobre EC2 y con Fargate Linux desde platform version **1.4.0 o posterior**.
- Los EFS access points permiten restringir directorios y aplicar identidades específicas para distintas aplicaciones.
- Amazon S3 sigue siendo almacenamiento de objetos y no debe tratarse automáticamente como un filesystem NFS compartido.

> **Nota**  
> Amazon EFS ya fue estudiado en almacenamiento. Aquí solo se aplica al escenario de contenedores.

> **Caso Check yourself EN**  
> Aplicación dockerizada con almacenamiento persistente sin administrar instancias EC2, id 32.

> **Idea visual**  
> Varias tasks ECS en dos AZ conectadas al mismo Amazon EFS.

### Slide 4 — Throughput de EFS en contenedores

**Título en slide**

EFS Y ALTO THROUGHPUT

#### Conceptos

- **Elastic Throughput** ajusta automáticamente el rendimiento y encaja en cargas impredecibles o con picos.
- **Provisioned Throughput** permite definir rendimiento independientemente del tamaño almacenado.
- **Bursting Throughput** relaciona el rendimiento con el tamaño del filesystem y utiliza burst credits.
- El banco utiliza Provisioned Throughput para un filesystem pequeño que necesita lecturas y escrituras frecuentes y sostenidas.

> **Caso Check yourself EN**  
> Almacenamiento compartido para cientos de tasks con menos de **1 TB** y alta frecuencia de lectura y escritura, id 11.

## Sesión 12.5 — IAM en ECS

### Slide 1 — Identidad de las tasks

**Título en slide**

ROLES IAM EN ECS

#### Nombres en portal y examen

> **Task role**  
> **Task execution role**  
> **Container instance role**

#### Conceptos

- El **task role** proporciona permisos al código dentro del contenedor para acceder a servicios AWS.
- El **task execution role** permite realizar acciones de inicio como descargar imágenes privadas de ECR y enviar logs.
- El **container instance role** proporciona permisos a la instancia y al ECS container agent cuando utilizas capacidad EC2.
- Separar estos roles permite aplicar mínimo privilegio y evita almacenar access keys dentro del contenedor.

> **Nota**  
> IAM ya fue estudiado anteriormente. Aquí importa diferenciar qué identidad utiliza cada componente de Amazon ECS.

> **Idea visual**  
> `Instance role → host`, `Execution role → inicio`, `Task role → aplicación`.

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue**  
> **Compute environment**

#### Conceptos

- **AWS Batch** ejecuta workloads por lotes como simulaciones, renderizado, análisis científicos y procesamiento intensivo de datos.
- Los trabajos se envían a una **job queue** y AWS Batch los programa según prioridad y capacidad disponible.
- Los workloads pueden empaquetarse como imágenes de contenedor y ejecutarse utilizando diferentes compute environments.
- Un batch job tiene inicio y fin, por lo que no necesita mantenerse como un ECS service permanentemente disponible.

> **Ejemplo**  
> Miles de simulaciones nocturnas entran en una job queue y se ejecutan conforme existe capacidad.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> `Jobs → Job queue → Compute environment → contenedores`.

---

### Slide 2 — Tasks ECS programadas

**Título en slide**

TASKS ECS PROGRAMADAS

#### Conceptos

- `RunTask` permite iniciar una task puntual sin crear un ECS service permanente.
- Amazon EventBridge Scheduler puede iniciar la task mediante una fecha, una expresión cron o una frecuencia.
- La task puede ejecutarse sobre Fargate, procesar la información y finalizar cuando completa el trabajo.
- Si el proceso necesita varios pasos, decisiones y reintentos coordinados, AWS Step Functions puede orquestar el flujo.

> **Nota**  
> Amazon EventBridge y AWS Step Functions ya fueron estudiados en el M11 y aquí solo se reutilizan dentro del patrón de contenedores.

> **Ejemplo**  
> Un script Docker se ejecuta cada noche como una task Fargate y termina cuando finaliza el procesamiento.

> **Idea visual**  
> EventBridge Scheduler → ECS RunTask → Fargate → fin.

## Sesión 12.7 — Amazon EKS

### Slide 1 — Amazon Elastic Kubernetes Service

**Título en slide**

AMAZON ELASTIC KUBERNETES SERVICE

#### Nombres en portal y examen

> **Amazon Elastic Kubernetes Service (Amazon EKS)**  
> **Kubernetes**  
> **Control plane**

#### Conceptos

- **Amazon EKS** es el servicio administrado de AWS para ejecutar Kubernetes sin operar manualmente el plano de control.
- Los workloads utilizan las APIs y herramientas estándar de Kubernetes, por lo que aplicaciones compatibles pueden migrarse con menos cambios.
- Amazon EKS se integra con servicios AWS de red, identidad, almacenamiento, observabilidad y balanceo.
- Elige EKS cuando el escenario exige **Kubernetes**, herramientas de su ecosistema o portabilidad basada en esa plataforma.

> **Logo** `recursos/aws/otros/elastic-kubernetes-service.svg`

> **Idea visual**  
> Control plane de Amazon EKS administrado por AWS y varios pods debajo.

---

### Slide 2 — Nodos EC2 en Amazon EKS

**Título en slide**

EKS CON NODOS EC2

#### Nombres en portal y examen

> **Managed node group**  
> **Self-managed nodes**

#### Conceptos

- Los **managed node groups** ejecutan workers sobre EC2 y simplifican su aprovisionamiento y ciclo de vida.
- Cada managed node group utiliza un Auto Scaling Group para administrar las instancias que forman el grupo.
- Con self-managed nodes la organización mantiene mayor responsabilidad sobre configuración, actualización y escalado.
- Los nodos EC2 encajan cuando necesitas mayor control sobre tipos de instancia, GPU, AMI u otras características del host.

> **Idea visual**  
> Amazon EKS → managed node group → tres nodos EC2 → pods.

### Slide 3 — AWS Fargate con Amazon EKS

**Título en slide**

FARGATE EN AMAZON EKS

#### Conceptos

- Amazon EKS puede programar determinados pods sobre **AWS Fargate** mediante Fargate profiles.
- Cada pod Fargate dispone de su propio límite de cómputo y su propia interfaz de red.
- Application Load Balancer y Network Load Balancer utilizan targets de tipo **IP** para pods ejecutados en Fargate.
- EKS Fargate admite Amazon EFS para persistencia, pero no volúmenes Amazon EBS montados directamente en estos pods.

> **Nota**  
> AWS Fargate ya fue presentado como servicio en la sesión 12.3. Aquí solo se explica su integración con Amazon EKS.

> **Idea visual**  
> Amazon EKS → Fargate profile → varios pods Fargate sin nodos EC2 visibles.

### Slide 4 — Identidad de pods

**Título en slide**

IAM ROLES FOR SERVICE ACCOUNTS

#### Nombres en portal y examen

> **IAM Roles for Service Accounts (IRSA)**  
> **Kubernetes service account**  
> **OIDC**

#### Conceptos

- **IRSA** asocia un rol IAM con un Kubernetes service account para proporcionar permisos AWS a determinados pods.
- Los pods reciben credenciales temporales sin almacenar access keys de larga duración en las imágenes.
- Diferentes workloads pueden utilizar roles distintos y aplicar mínimo privilegio aunque compartan los mismos nodos.
- IRSA utiliza el proveedor OIDC del cluster y cumple un objetivo similar al task role de Amazon ECS.

> **Nota**  
> Amazon EKS también dispone de EKS Pod Identity. IRSA sigue siendo válido y es el mecanismo utilizado por las preguntas de este banco.

## Sesión 12.9 — Arquitecturas

### Slide 1 — Fargate detrás del ALB

**Título en slide**

FARGATE DETRÁS DEL ALB

#### Conceptos

- El Application Load Balancer distribuye las solicitudes hacia las tasks Fargate registradas en el target group del ECS service.
- Las tasks pueden distribuirse entre diferentes Availability Zones sin administrar instancias EC2.
- Las imágenes se obtienen desde Amazon ECR y los permisos se separan mediante task execution role y task role.
- Si el workload necesita almacenamiento compartido, las tasks pueden montar Amazon EFS.

> **Nota**  
> ECR participa cuando una task necesita obtener su imagen y no en cada solicitud HTTP enviada por los usuarios.

> **Idea visual**
>
> 1. Región con AZ-a y AZ-b separadas mediante líneas punteadas.
> 2. Usuario → Application Load Balancer → target group.
> 3. Tasks Fargate en subredes privadas de ambas AZ.
> 4. Amazon ECR conectado a las tasks mediante una flecha `imagen`.
> 5. Amazon EFS conectado cuando se necesite almacenamiento compartido.
> 6. Sin instancias EC2 asociadas a las tasks.

---

### Slide 2 — Cómo elegir el servicio

**Título en slide**

ECR, ECS, FARGATE, EKS O BATCH

#### Conceptos

| El enunciado pide | Elección |
|---|---|
| Guardar imágenes de contenedores | **Amazon ECR** |
| Orquestar contenedores sin Kubernetes | **Amazon ECS** |
| Ejecutar contenedores sin administrar hosts | **AWS Fargate** |
| Kubernetes administrado | **Amazon EKS** |
| Muchos jobs con inicio y fin | **AWS Batch** |
| Kubernetes en infraestructura propia | **Amazon EKS Anywhere** |
| ECS sobre servidores externos | **Amazon ECS Anywhere** |
| Publicar rápidamente una web desde código o imagen | **AWS App Runner** |

> **Nota**  
> Fargate no reemplaza ECS ni EKS. Proporciona la capacidad de cómputo donde ECS tasks o EKS pods pueden ejecutarse.
