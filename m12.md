## Sesión 12.1 — Registro de imágenes

### Slide 1 — Qué problema resuelve un contenedor

**Título en slide**

CONTENEDORES EN AWS

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Image** / **Imagen**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Un contenedor empaqueta la aplicación junto con sus dependencias para mantener un comportamiento consistente entre desarrollo y producción y se ejecuta como un proceso aislado sobre el kernel del host.

- Una **imagen** es una plantilla inmutable formada por capas que contiene lo necesario para crear uno o varios contenedores con la misma configuración.

- Varios contenedores pueden compartir el sistema operativo del host, por lo que normalmente requieren menos recursos que ejecutar una máquina virtual completa para cada aplicación.

- La orquestación decide dónde ejecutar los contenedores, mantiene la cantidad necesaria y reemplaza los que fallan. En AWS destacan **Amazon ECS** y **Amazon EKS**, mientras **AWS Fargate** proporciona capacidad de cómputo sin administrar instancias y no funciona como orquestador por sí solo.

> **Ejemplo**  
> Una aplicación HTTP empaquetada en Docker puede almacenar su imagen en Amazon ECR y ejecutarse como varias tasks de Amazon ECS detrás de un Application Load Balancer.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Host EC2 con varios contenedores pequeños frente a varias máquinas virtuales completas. Flecha `misma aplicación → misma imagen`.

### Slide 2 — Amazon ECR

**Título en slide**

AMAZON ECR

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Push / Pull**

#### Conceptos

- **Amazon ECR** almacena y versiona imágenes de contenedores que después pueden utilizar servicios como ECS, EKS y AWS Batch para iniciar workloads.

- Los repositorios pueden ser privados dentro de una cuenta y AWS también ofrece **Amazon ECR Public** para distribuir imágenes públicamente.

- ECR incorpora funciones como escaneo de vulnerabilidades, etiquetas y políticas de ciclo de vida, mientras IAM y las políticas del repositorio controlan quién puede realizar `push` o `pull`.

- **ECR no ejecuta contenedores ni balancea tráfico**. Guarda la imagen y otro servicio debe utilizarla para iniciar el workload.

> **Ejemplo**  
> Un pipeline CI construye una imagen, la sube a ECR y una task definition de ECS referencia esa imagen durante el despliegue.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

> **Idea visual**  
> Repositorio ECR con varias versiones de una imagen y una flecha `pull` hacia una task ECS.

## Sesión 12.2 — Amazon ECS

### Slide 1 — Qué problema resuelve ECS

**Título en slide**

AMAZON ECS

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**  
> **Task**  
> **Service**

#### Conceptos

- **Amazon ECS** orquesta contenedores utilizando un modelo propio de AWS y permite desplegar, mantener y escalar aplicaciones sin tener que implementar Kubernetes.

- Un **ECS cluster** es una agrupación lógica donde se ejecutan las tasks y puede utilizar capacidad EC2, AWS Fargate o diferentes capacity providers.

- El modelo básico sigue la secuencia **imagen en ECR → task definition → task → service** cuando la aplicación debe permanecer ejecutándose de forma continua.

- ECS se integra con servicios como Elastic Load Balancing, IAM, CloudWatch y EventBridge. Si el escenario exige específicamente **Kubernetes**, herramientas como Helm o compatibilidad con la API Kubernetes, Amazon EKS suele ser la alternativa adecuada.

> **Ejemplo**  
> Una API REST empaquetada en contenedores puede ejecutarse como un ECS service detrás de un Application Load Balancer.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Plano de control ECS administrado por AWS con varias tasks debajo y una flecha desde Amazon ECR.

### Slide 2 — Task definition y task

**Título en slide**

TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task**  
> **Container** / **Contenedor**

#### Conceptos

- Una **task definition** es la plantilla que describe cómo ejecutar una aplicación e incluye elementos como imagen, CPU, memoria, variables, red, volúmenes, logging y roles IAM.

- Cada modificación genera una nueva revisión de la task definition y una **task** representa una instancia en ejecución de una de esas revisiones.

- Una task puede contener uno o varios contenedores que deben ejecutarse juntos, por ejemplo una aplicación acompañada por un contenedor sidecar para logs o proxy.

- Una **task** es la unidad que se ejecuta, mientras un **service** mantiene la cantidad requerida de tasks funcionando y reemplaza las que fallen.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `Task definition v3` → tres tasks idénticas distribuidas entre diferentes Availability Zones.

### Slide 3 — ECS Service

**Título en slide**

ECS SERVICE

#### Nombres en portal y examen

> **ECS service**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** se utiliza para aplicaciones que deben permanecer ejecutándose, mantiene el número configurado de tasks y sustituye automáticamente las que fallen.

- El **desired count** determina cuántas tasks deben funcionar simultáneamente y ECS crea o elimina tasks para acercarse a ese número.

- El service puede registrar automáticamente sus tasks en un target group de un Application Load Balancer o Network Load Balancer para distribuir el tráfico entre ellas.

- Un service encaja en aplicaciones web, APIs o consumidores continuos. Un proceso con inicio y fin puede ejecutarse como una task independiente o mediante un servicio especializado como AWS Batch.

> **Ejemplo**  
> Una tienda online utiliza un ECS service con `desired count = 4` y distribuye sus tasks entre dos Availability Zones.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Service con varias tasks saludables y una task fallida siendo reemplazada automáticamente.

## Sesión 12.3 — Tipo de lanzamiento

### Slide 1 — ECS con EC2

**Título en slide**

ECS CON EC2

#### Nombres en portal y examen

> **EC2 launch type**  
> **ECS container agent**

#### Conceptos

- Con **EC2 launch type**, las tasks se ejecutan sobre instancias EC2 que forman parte del clúster y la organización mantiene la capacidad de cómputo necesaria.

- El **ECS container agent** conecta cada instancia con el plano de control de ECS, recibe las tasks que deben ejecutarse y reporta su estado.

- La organización mantiene responsabilidad sobre el sistema operativo, parches, tipos de instancia y capacidad disponible, a cambio de disponer de mayor control sobre los hosts.

- El escalado puede ocurrir en dos niveles porque primero aumenta la cantidad de tasks del service y, si ya no existe espacio para colocarlas, también debe aumentar la capacidad EC2 del clúster.

> **Ejemplo**  
> Un clúster puede utilizar instancias EC2 reservadas cuando la organización necesita mantener control sobre el tipo de host o aprovechar capacidad ya comprometida.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Instancias EC2 con ECS agent y varias tasks distribuidas entre dos AZ con líneas punteadas de fondo.

### Slide 2 — ECS con AWS Fargate

**Título en slide**

ECS CON FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Fargate launch type**

#### Conceptos

- **AWS Fargate** ejecuta tasks sin que tengas que aprovisionar, seleccionar o parchear instancias EC2 y AWS administra la infraestructura subyacente.

- Defines los recursos de CPU y memoria que necesita la task y, al escalar un service, aumentas o reduces la cantidad de tasks sin tener que administrar directamente los hosts.

- Las tasks Fargate utilizan el modo de red **`awsvpc`**, reciben una interfaz de red dentro de la VPC y pueden tener security groups aplicados directamente.

- Fargate puede utilizarse tanto con **Amazon ECS como con Amazon EKS**, por lo que representa una opción de cómputo y no un orquestador independiente.

> **Ejemplo**  
> Un equipo pequeño ejecuta una API en un ECS service con Fargate detrás de un Application Load Balancer para reducir la administración de infraestructura.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Tasks Fargate distribuidas entre dos Availability Zones sin mostrar instancias EC2.

### Slide 3 — Precio EC2 frente a Fargate

**Título en slide**

EC2 VS FARGATE

#### Nombres en portal y examen

> **EC2 launch type**  
> **Fargate launch type**  
> **Compute Savings Plans**

#### Conceptos

- Con **EC2 launch type** pagas las instancias EC2 utilizadas por el clúster y otros recursos asociados como los volúmenes EBS cuando corresponda.

- Con **Fargate** el costo depende principalmente de la vCPU y memoria asignadas a las tasks durante su ejecución, sin una factura de instancia EC2 para esas tasks.

- Los **Compute Savings Plans** también pueden cubrir determinados usos de Fargate y no se limitan únicamente a instancias EC2.

- EC2 puede resultar conveniente con workloads grandes y estables, mientras Fargate reduce la administración de infraestructura. Para el examen no existe una opción universalmente más barata y debes identificar el modelo de cobro y las necesidades del escenario.

> **Caso Check yourself ES**  
> Comparación del modelo de precio de ECS con EC2 frente a ECS con Fargate, id 24.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Recibo EC2 con `EC2 + EBS` frente a recibo Fargate con `vCPU + memoria`.

## Sesión 12.4 — Servicio en producción

### Slide 1 — Application Load Balancer y ECS

**Título en slide**

ALB CON AMAZON ECS

#### Nombres en portal y examen

> **Application Load Balancer**  
> **Dynamic port mapping** / **Mapeo dinámico de puertos**  
> **Target group** / **Grupo de destino**

#### Conceptos

- Un **Application Load Balancer** puede distribuir tráfico HTTP y HTTPS entre las múltiples tasks de un ECS service mediante un target group.

- Con tasks ECS sobre EC2 en modo `bridge`, el **dynamic host port mapping** permite asignar diferentes puertos del host a contenedores que exponen el mismo puerto.

- Las tasks Fargate utilizan `awsvpc` y cada task dispone de su propia ENI e IP dentro de la VPC, permitiendo que el ALB registre directamente su IP y puerto.

- Los health checks permiten retirar destinos que no respondan correctamente. Para tráfico HTTP o HTTPS el ALB suele ser la opción habitual, mientras NLB encaja en escenarios que requieren características de red de capa 4.

> **Logo** `recursos/aws/networking/elb.svg`

> **Idea visual**  
> Application Load Balancer en 443 conectado a varias tasks ECS. Mostrar EC2 con dynamic host ports y Fargate con ENI propia.

### Slide 2 — ECS Service Auto Scaling

**Título en slide**

ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **AWS Application Auto Scaling**  
> **Target tracking**

#### Conceptos

- **ECS Service Auto Scaling** modifica automáticamente el desired count para aumentar o reducir la cantidad de tasks según cambia la demanda.

- ECS utiliza **Application Auto Scaling** y las políticas pueden basarse en métricas como CPU promedio, memoria promedio o solicitudes por target del Application Load Balancer.

- Con ECS sobre EC2 existen dos niveles diferentes, el escalado de **tasks del service** y el escalado de **capacidad EC2 del clúster**.

- Con Fargate no administras hosts EC2, por lo que puedes centrar el escalado en aumentar o reducir directamente la cantidad de tasks del service.

> **Ejemplo**  
> Si el uso promedio de CPU del service supera el objetivo configurado, Application Auto Scaling puede aumentar el desired count.

### Slide 3 — EFS montado en tasks ECS

**Título en slide**

AMAZON ECS CON EFS

#### Nombres en portal y examen

> **Amazon Elastic File System (Amazon EFS)**  
> **EFS access point**

#### Conceptos

- **Amazon EFS** proporciona almacenamiento de archivos persistente y compartido que puede ser utilizado por múltiples tasks incluso cuando están distribuidas entre diferentes Availability Zones.

- La task definition puede declarar un sistema EFS como volumen para que el contenedor acceda a una ruta montada durante su ejecución.

- EFS puede utilizarse tanto con tasks sobre EC2 como con Fargate y permite conservar datos sin depender del almacenamiento efímero de una task concreta.

- Cuando el escenario necesita un sistema de archivos compartido entre contenedores, EFS representa el patrón natural. Amazon S3 normalmente se consume mediante su API y no como sustituto directo de un filesystem NFS.

## Sesión 12.5 — IAM en ECS

### Slide 1 — Roles IAM en ECS

**Título en slide**

ROLES IAM EN ECS

#### Nombres en portal y examen

> **Task role**  
> **Task execution role**  
> **EC2 instance profile**

#### Conceptos

- El **task role** entrega permisos al código de la aplicación dentro del contenedor para acceder a servicios AWS como S3 o SQS y permite que diferentes tasks utilicen permisos distintos.

- El **task execution role** permite que ECS realice acciones necesarias durante el inicio de la task, como descargar imágenes privadas de ECR, enviar logs o recuperar secretos utilizados por el contenedor.

- El **EC2 instance profile** se utiliza cuando ECS corre sobre EC2 y proporciona permisos al agente y al host. No sustituye los permisos que necesita la aplicación mediante su task role.

- Para aplicar mínimo privilegio, los permisos de la aplicación deben asociarse a su **task role** en lugar de colocar credenciales estáticas dentro del contenedor o depender innecesariamente del rol del host.

> **Ejemplo**  
> Una task utiliza su task role para escribir en S3 y su execution role para descargar la imagen desde ECR y publicar logs.

> **Logo** `recursos/aws/otros/iam.svg`

> **Idea visual**  
> `Instance profile → EC2 host`, `Execution role → inicio de task`, `Task role → aplicación`.

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue**

#### Conceptos

- **AWS Batch** administra trabajos con inicio y fin que necesitan ejecutar grandes cantidades de procesamiento, como simulaciones, renderizado, análisis científicos o procesamiento de datos.

- El workload se empaqueta como una imagen de contenedor y se envía como un job a una cola, mientras Batch programa la ejecución según los recursos y prioridades configurados.

- Batch puede utilizar diferentes opciones de cómputo según la configuración y resulta especialmente útil cuando existen muchos trabajos independientes o una cola de procesamiento.

- A diferencia de un ECS service, un job de Batch termina después de completar su trabajo y puede ejecutar procesos de larga duración sin mantener una aplicación permanentemente disponible detrás de un balanceador.

> **Ejemplo**  
> Miles de simulaciones nocturnas se envían a una job queue y AWS Batch ejecuta los contenedores conforme existe capacidad disponible.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> Job queue → varios trabajos → contenedores → `exit`.

### Slide 2 — Tareas ECS programadas

**Título en slide**

EVENTBRIDGE Y ECS RUN TASK

#### Nombres en portal y examen

> **Amazon EventBridge**  
> **EventBridge Scheduler**  
> **ECS RunTask**

#### Conceptos

- **ECS RunTask** permite ejecutar una task puntual sin crear un service que deba mantenerla funcionando permanentemente.

- **EventBridge Scheduler** puede iniciar tasks ECS en una fecha, mediante cron o de acuerdo con una frecuencia determinada, permitiendo ejecutar contenedores periódicos sin mantener servidores esperando.

- Una task puede ejecutarse sobre Fargate, procesar información, guardar el resultado y terminar cuando completa el trabajo.

- Si el proceso necesita coordinar múltiples pasos, decisiones, reintentos y estado entre diferentes servicios, **AWS Step Functions** puede ser una alternativa de orquestación más apropiada.

> **Ejemplo**  
> Un script empaquetado en Docker se ejecuta cada noche mediante EventBridge Scheduler y ECS RunTask sobre Fargate.

## Sesión 12.7 — Amazon EKS

### Slide 1 — Amazon EKS

**Título en slide**

AMAZON EKS

#### Nombres en portal y examen

> **Amazon Elastic Kubernetes Service (Amazon EKS)**  
> **Kubernetes**

#### Conceptos

- **Amazon EKS** proporciona Kubernetes administrado en AWS y AWS opera el plano de control mientras los workloads se despliegan utilizando las APIs y herramientas estándar de Kubernetes.

- ECS y EKS permiten ejecutar contenedores, pero utilizan modelos diferentes. EKS encaja cuando el escenario requiere explícitamente **Kubernetes**, herramientas existentes del ecosistema o compatibilidad con esa API.

- Los workloads pueden ejecutarse sobre nodos EC2 o mediante **AWS Fargate**, dependiendo del nivel de control y administración requerido.

- Los pods pueden distribuirse entre diferentes Availability Zones para aumentar disponibilidad y utilizar servicios AWS para red, almacenamiento, observabilidad e identidad.

> **Ejemplo**  
> Una empresa que ya utiliza Kubernetes on premises puede migrar sus workloads a Amazon EKS manteniendo el modelo Kubernetes.

> **Logo** `recursos/aws/otros/elastic-kubernetes-service.svg`

> Plano de control EKS administrado por AWS y workloads distribuidos entre varias AZ con líneas punteadas.

### Slide 2 — Nodos y Fargate

**Título en slide**

EKS NODOS Y FARGATE

#### Nombres en portal y examen

> **Managed node group**  
> **Self-managed nodes**  
> **Fargate**

#### Conceptos

- Un **managed node group** utiliza instancias EC2 como workers de Kubernetes y AWS simplifica operaciones relacionadas con la creación y actualización de esos nodos.

- Con **self-managed nodes**, la organización mantiene mayor responsabilidad sobre las instancias EC2 utilizadas como workers y sobre su ciclo de vida.

- **EKS con Fargate** permite ejecutar determinados pods sin administrar instancias EC2 subyacentes, priorizando una menor carga operativa.

- El almacenamiento persistente puede integrarse mediante controladores CSI con servicios como **Amazon EBS, Amazon EFS y determinados servicios Amazon FSx**, según los requisitos del workload.

> **Ejemplo**  
> Una migración desde Kubernetes on premises puede utilizar EKS con managed node groups cuando la empresa quiere mantener workers EC2 pero reducir su administración.

### Slide 3 — IAM Roles for Service Accounts

**Título en slide**

IAM ROLES FOR SERVICE ACCOUNTS

#### Nombres en portal y examen

> **IAM Roles for Service Accounts (IRSA)**  
> **Kubernetes service account**

#### Conceptos

- **IRSA** permite asociar un rol IAM a un Kubernetes service account para que los pods obtengan permisos AWS sin almacenar access keys de larga duración dentro de la imagen.

- Los pods obtienen credenciales temporales y únicamente pueden acceder a los servicios permitidos por el rol asociado a su identidad.

- Conceptualmente cumple una función similar al **task role de Amazon ECS**, pero utiliza identidades propias del entorno Kubernetes.

## Sesión 12.8 — Variantes y reconocimiento

### Slide 1 — EKS Anywhere y EKS Distro

**Título en slide**

EKS ANYWHERE Y EKS DISTRO

#### Nombres en portal y examen

> **Amazon EKS Anywhere**  
> **Amazon EKS Distro**

#### Conceptos

- **Amazon EKS** ejecuta Kubernetes administrado dentro de AWS, mientras **EKS Anywhere** permite crear y operar clústeres Kubernetes en infraestructura administrada por el cliente fuera de una Region AWS.

- EKS Anywhere está orientado a entornos como datacenters propios o edge cuando los workloads necesitan permanecer fuera de la nube pública manteniendo una experiencia Kubernetes alineada con AWS.

- **Amazon EKS Distro** es la distribución de Kubernetes basada en los mismos componentes utilizados por Amazon EKS y no constituye por sí misma un servicio que cree y administre el clúster.

- Para el examen recuerda la diferencia fundamental entre **EKS en AWS**, **EKS Anywhere fuera de AWS** y **EKS Distro como distribución Kubernetes**.

## Sesión 12.9 — Arquitecturas

### Slide 1 — Fargate detrás del ALB

**Título en slide**

FARGATE DETRÁS DEL ALB

#### Conceptos

- El tráfico entra mediante un **Application Load Balancer** y se distribuye hacia las tasks de un ECS service registradas en su target group.

- Las tasks utilizan **AWS Fargate**, por lo que no aparecen instancias EC2 administradas por el usuario y pueden distribuirse entre diferentes Availability Zones para mejorar disponibilidad.

- Las imágenes se obtienen desde **Amazon ECR** cuando se inicia una nueva task, mientras el task execution role permite las operaciones necesarias para arrancarla y el task role proporciona los permisos que necesita la aplicación.

- Si el workload requiere almacenamiento persistente y compartido, las tasks pueden montar **Amazon EFS** sin cambiar el modelo Fargate.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**
>
> 1. Región con AZ-a y AZ-b separadas mediante líneas punteadas.
> 2. Usuario → Application Load Balancer → target group.
> 3. Tasks Fargate en subredes privadas de ambas AZ.
