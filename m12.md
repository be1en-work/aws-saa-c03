> Dominios 2 y 3.

## Sesión 12.1: Registro de imágenes

### Slide: Qué problema resuelve un contenedor

**Título en slide:** CONTENEDORES EN AWS: LA IDEA

#### Nombres en portal y examen

> **contenedor Docker**, **imagen (*image*)**, **orquestación de contenedores**

#### Conceptos

- **Contenedor:** empaqueta la aplicación y sus dependencias para mantener un comportamiento consistente entre desarrollo y producción. Se ejecuta como un proceso aislado sobre el kernel del host.

- **Imagen:** plantilla inmutable formada por capas. Contiene lo necesario para crear uno o varios contenedores con la misma configuración.

- **Más ligero que una VM:** varios contenedores pueden compartir el sistema operativo del host, por lo que normalmente requieren menos recursos que ejecutar una máquina virtual completa por aplicación.

- **Orquestación:** decide dónde ejecutar los contenedores, mantiene la cantidad necesaria y reemplaza los que fallan. En AWS destacan **Amazon ECS** y **Amazon EKS**.

- **AWS Fargate:** proporciona capacidad de cómputo para ECS o EKS sin administrar instancias EC2. **Fargate no es un orquestador por sí mismo**.

> **Logo:** `recursos/aws/compute/fargate.svg`
>
> **Imagen sugerida:** Host EC2 con varios contenedores pequeños frente a varias VMs completas. Flecha indicando que diferentes entornos utilizan la misma imagen.

### Slide: Amazon ECR

**Título en slide:** AMAZON ECR

#### Nombres en portal y examen

> **Amazon ECR** (*Elastic Container Registry*)

#### Conceptos

- **Amazon ECR almacena imágenes de contenedores** que posteriormente pueden utilizar ECS, EKS, AWS Batch y otros servicios para iniciar workloads.

- Los repositorios pueden ser **privados** dentro de una cuenta. AWS también ofrece **Amazon ECR Public** para distribuir públicamente imágenes de contenedores.

- ECR admite características como **image scanning**, etiquetas y políticas de ciclo de vida para identificar vulnerabilidades y eliminar imágenes que ya no sean necesarias.

- El acceso para realizar `push` o `pull` se controla mediante **IAM** y políticas del repositorio. Si una task no puede descargar una imagen privada, los permisos forman parte de la revisión.

- **ECR no ejecuta contenedores.** Guarda la imagen. Un servicio como ECS, EKS o AWS Batch debe utilizarla para iniciar el workload.

> **Caso:** un pipeline CI crea una imagen y la sube a ECR. Una task definition de ECS referencia esa imagen durante el despliegue.
>
> **Logo:** `recursos/aws/otros/elastic-container-registry.svg`
>
> **Imagen sugerida:** Repositorio ECR con varias versiones de una imagen y una flecha `pull` hacia una task ECS.

## Sesión 12.2: Amazon ECS

### Slide: Qué problema resuelve ECS

**Título en slide:** AMAZON ECS: LA IDEA

#### Nombres en portal y examen

> **Amazon ECS** (*Elastic Container Service*)

#### Conceptos

- **Amazon ECS orquesta contenedores** utilizando un modelo propio de AWS. Permite desplegar, mantener y escalar aplicaciones sin tener que implementar Kubernetes.

- Un **ECS cluster** es una agrupación lógica donde se ejecutan las tasks. La capacidad puede proceder de EC2, Fargate o diferentes capacity providers.

- El modelo básico es **imagen en ECR → task definition → task → service**, cuando el workload debe permanecer funcionando de manera continua.

- ECS se integra de forma nativa con servicios como **Elastic Load Balancing, IAM, CloudWatch y EventBridge**.

- Si el escenario exige específicamente **Kubernetes**, compatibilidad con herramientas Kubernetes o una API común entre diferentes entornos, Amazon EKS suele ser la alternativa adecuada.

> **Caso:** una API REST empaquetada en contenedores se ejecuta como un ECS service detrás de un Application Load Balancer.
>
> **Logo:** `recursos/aws/otros/elastic-container-service.svg`
>
> **Imagen sugerida:** Plano de control ECS administrado por AWS con varias tasks debajo y una flecha desde Amazon ECR.

### Slide: Task definition y task

**Título en slide:** TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **task definition**, **task**, **container**

#### Conceptos

- Una **task definition** es la plantilla que describe cómo ejecutar una aplicación: imagen, CPU, memoria, variables, red, volúmenes, logging y roles IAM.

- Cada modificación importante genera una **nueva revisión** de la task definition, permitiendo desplegar versiones diferentes de una aplicación.

- Una **task** es una instancia en ejecución de una task definition. La misma definición puede utilizarse para iniciar varias tasks idénticas.

- Una task puede contener **uno o varios contenedores** que deben ejecutarse juntos, por ejemplo una aplicación acompañada de un contenedor sidecar.

- **Task y service no son equivalentes:** la task es la unidad que se ejecuta; el service mantiene la cantidad requerida de tasks funcionando.

> **Logo:** `recursos/aws/otros/elastic-container-service.svg`
>
> **Imagen sugerida:** `Task definition v3` conectada a tres tasks idénticas distribuidas entre diferentes AZ.

### Slide: ECS service

**Título en slide:** ECS SERVICE

#### Nombres en portal y examen

> **ECS service**, **desired count**

#### Conceptos

- Un **ECS service** se utiliza para aplicaciones que deben permanecer ejecutándose. Mantiene el número configurado de tasks y reemplaza automáticamente las que fallen.

- El **desired count** indica cuántas tasks debe mantener el service de forma simultánea. ECS inicia o elimina tasks para alcanzar ese valor.

- El service puede registrar las tasks automáticamente en un **target group** de un Application Load Balancer o Network Load Balancer.

- Un service es apropiado para aplicaciones web, APIs o consumidores continuos. Un proceso con inicio y fin puede ejecutarse como una task independiente o mediante AWS Batch.

- Si aumenta la demanda de la aplicación, puede escalarse el **número de tasks del service** sin que eso implique necesariamente aumentar manualmente todo el clúster.

> **Caso:** una tienda online utiliza un service con `desired count = 4` y tasks distribuidas entre dos zonas de disponibilidad.
>
> **Logo:** `recursos/aws/otros/elastic-container-service.svg`
>
> **Imagen sugerida:** ECS service con tres tasks saludables y una task fallida siendo reemplazada automáticamente.

## Sesión 12.3: Tipo de lanzamiento

### Slide: ECS sobre EC2

**Título en slide:** ECS CON EC2

#### Nombres en portal y examen

> **EC2 launch type**, **ECS container agent**

#### Conceptos

- Con **EC2 launch type**, las tasks se ejecutan sobre instancias EC2 que forman parte del clúster. La organización mantiene la capacidad de cómputo necesaria.

- El **ECS container agent** conecta las instancias con el plano de control de ECS, recibe instrucciones y reporta el estado de las tasks.

- La organización sigue siendo responsable del **sistema operativo, parches, tipos de instancia y capacidad disponible** en los hosts.

- Este modelo ofrece mayor control y puede ser apropiado cuando necesitas configuraciones específicas de instancia, GPU o capacidad EC2 ya comprometida.

- Existen **dos niveles de escalado:** primero pueden aumentar las tasks del service y después debe aumentar la capacidad EC2 si ya no existe espacio suficiente para colocarlas.

> **Logo:** `recursos/aws/otros/elastic-container-service.svg`
>
> **Imagen sugerida:** Instancias EC2 con ECS agent y varias tasks distribuidas entre dos AZ con líneas punteadas de fondo.

### Slide: ECS con AWS Fargate

**Título en slide:** ECS CON FARGATE

#### Nombres en portal y examen

> **AWS Fargate**, **Fargate launch type**

#### Conceptos

- **AWS Fargate ejecuta tasks sin administrar instancias EC2.** Defines los recursos necesarios para la task y AWS administra la infraestructura subyacente.

- No necesitas seleccionar hosts, instalar el ECS agent ni parchear el sistema operativo de las instancias que ejecutan los contenedores.

- Las tasks Fargate utilizan el modo de red **`awsvpc`** y reciben una interfaz de red dentro de la VPC. Los security groups pueden aplicarse directamente a las tasks.

- Fargate puede utilizarse tanto con **Amazon ECS como con Amazon EKS**, por lo que no debe confundirse con un orquestador independiente.

- Es una opción frecuente cuando el escenario prioriza **reducir administración de infraestructura** y mantener el modelo de contenedores.

> **Caso:** un equipo pequeño ejecuta una API en un ECS service con Fargate detrás de un Application Load Balancer.
>
> **Logo:** `recursos/aws/compute/fargate.svg`
>
> **Imagen sugerida:** Tasks Fargate distribuidas entre dos AZ, sin instancias EC2 visibles.

### Slide: Precio de EC2 frente a Fargate

**Título en slide:** EC2 VS FARGATE: FACTURACIÓN

#### Nombres en portal y examen

> **EC2 launch type**, **Fargate launch type**, **Compute Savings Plans**

#### Conceptos

- Con **EC2 launch type**, pagas la capacidad EC2 utilizada por el clúster y los recursos asociados, como volúmenes EBS cuando corresponda.

- Con **Fargate**, el costo se basa principalmente en los recursos de **vCPU y memoria** asignados a las tasks durante su ejecución.

- Los **Compute Savings Plans** pueden aplicar a determinados usos de Fargate además de EC2, por lo que no son exclusivos de instancias.

- EC2 puede ofrecer ventajas económicas con cargas grandes y estables, mientras que Fargate reduce la administración de infraestructura. Ninguno es automáticamente más barato en todos los escenarios.

- En el examen, identifica primero **qué modelo de facturación describe el escenario** y qué nivel de administración acepta la empresa.

> **Caso Check yourself ES:** comparación de precios entre ECS EC2 y ECS Fargate, id 24.
>
> **Logo:** `recursos/aws/compute/fargate.svg`
>
> **Imagen sugerida:** Recibo EC2 con instancia y EBS frente a recibo Fargate con vCPU y memoria.

## Sesión 12.4: Servicio en producción

### Slide: Application Load Balancer y ECS

**Título en slide:** ALB CON AMAZON ECS

#### Nombres en portal y examen

> **Application Load Balancer**, **dynamic port mapping**, **target group**

#### Conceptos

- Un **Application Load Balancer** puede distribuir tráfico HTTP y HTTPS entre múltiples tasks de un ECS service mediante un target group.

- Con tasks ECS sobre EC2 en modo **`bridge`**, ECS puede utilizar **dynamic host port mapping** para asignar diferentes puertos del host a contenedores que exponen el mismo puerto.

- Las tasks Fargate utilizan **`awsvpc`**. Cada task tiene su propia ENI e IP dentro de la VPC, por lo que el ALB puede registrar directamente la IP y el puerto de la task.

- Los **health checks** del target group permiten retirar temporalmente destinos que no respondan correctamente y mantener tráfico únicamente hacia tasks saludables.

- Para tráfico HTTP o HTTPS hacia contenedores, **ALB** suele ser la opción habitual. NLB encaja mejor cuando el escenario necesita características de red de capa 4.

> **Logo:** `recursos/aws/networking/elb.svg`
>
> **Imagen sugerida:** ALB en 443 conectado a varias tasks ECS. Diferenciar visualmente EC2 con dynamic host ports y Fargate con ENI propia.

### Slide: Auto scaling del service ECS

**Título en slide:** ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**, **Application Auto Scaling**, **target tracking**

#### Conceptos

- **ECS Service Auto Scaling** modifica automáticamente el desired count para aumentar o reducir la cantidad de tasks según la demanda.

- ECS utiliza **Application Auto Scaling** para aplicar las políticas de escalado al service.

- Las políticas pueden utilizar métricas como **CPU promedio, memoria promedio o solicitudes por target** de un Application Load Balancer.

- Con ECS sobre EC2 existen dos escalados diferentes: **tasks del service** y **capacidad EC2 del clúster**. Aumentar uno no garantiza que el otro tenga capacidad suficiente.

- Con Fargate no administras hosts EC2, por lo que el escalado del service se centra directamente en aumentar o reducir tasks.

> **Caso:** cuando aumenta el uso de CPU del ECS service, Application Auto Scaling incrementa el desired count.
>
> **Logo:** `recursos/aws/otros/elastic-container-service.svg`
>
> **Imagen sugerida:** Gráfico de CPU del service conectado a un cambio de `desired count 2 → 5`.

### Slide: EFS montado en tasks ECS

**Título en slide:** AMAZON ECS CON EFS

#### Nombres en portal y examen

> **Amazon EFS** (*Elastic File System*), **EFS access point**

#### Conceptos

- **Amazon EFS proporciona almacenamiento de archivos persistente y compartido** que puede utilizarse desde múltiples tasks.

- La task definition puede declarar un sistema de archivos EFS como volumen para que el contenedor acceda a una ruta montada durante su ejecución.

- EFS puede utilizarse con **tasks ECS sobre EC2 o Fargate**, evitando que los datos dependan del almacenamiento efímero de una task.

- Varias tasks distribuidas entre diferentes AZ pueden acceder al mismo sistema de archivos, lo que resulta útil cuando la aplicación necesita datos compartidos.

- **S3 no debe tratarse simplemente como un reemplazo de un filesystem NFS.** Si el escenario pide un sistema de archivos compartido para contenedores, EFS es una opción natural.

> **Caso Check yourself EN:** aplicación dockerizada que necesita almacenamiento persistente sin administrar EC2, id 32.
>
> **Logo:** `recursos/aws/storage/efs.svg`
>
> **Imagen sugerida:** EFS central conectado a tasks Fargate ubicadas en dos AZ con líneas punteadas de fondo.

## Sesión 12.5: IAM en ECS

### Slide: Roles IAM de ECS

**Título en slide:** ROLES IAM EN ECS

#### Nombres en portal y examen

> **task role**, **task execution role**, **EC2 instance profile**

#### Conceptos

- **Task role:** entrega permisos al **código de la aplicación dentro del contenedor**. Por ejemplo, una aplicación que necesita leer S3 utiliza permisos mediante su task role.

- **Task execution role:** permite que ECS o Fargate realicen acciones necesarias para iniciar determinadas tasks, como obtener imágenes privadas de ECR, enviar logs o recuperar secretos.

- **EC2 instance profile:** en ECS sobre EC2 proporciona permisos al **ECS container agent y al host**. No sustituye los permisos específicos que necesita el código de una aplicación.

- Diferentes aplicaciones pueden utilizar **task roles distintos**, permitiendo aplicar mínimo privilegio aunque compartan el mismo clúster ECS.

- Si el código de una task necesita acceder a S3, SQS u otra API AWS, el permiso debe asociarse normalmente al **task role**, no entregarse mediante credenciales estáticas dentro del contenedor.

> **Caso:** una task escribe datos en S3 mediante su task role, mientras su execution role permite descargar la imagen privada desde ECR y enviar logs.
>
> **Logo:** `recursos/aws/otros/iam.svg`
>
> **Imagen sugerida:** Tres roles IAM separados: instance profile hacia EC2, execution role hacia el arranque de la task y task role hacia la aplicación.

## Sesión 12.6: Lotes y programación

### Slide: AWS Batch

**Título en slide:** AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**, **batch job**, **job queue**

#### Conceptos

- **AWS Batch administra trabajos con inicio y fin** que necesitan ejecutar grandes cantidades de procesamiento, como simulaciones, renderizado, análisis científicos o procesamiento de datos.

- El workload se empaqueta como una **imagen de contenedor** y se envía como un job a una cola. Batch programa los trabajos según los recursos y prioridades configurados.

- Batch puede utilizar distintos entornos de cómputo administrados por AWS, incluidos **EC2, Spot y Fargate**, según la configuración y el workload.

- Es especialmente útil cuando existen **muchos trabajos independientes o una cola de procesamiento**, en lugar de una aplicación que debe permanecer siempre disponible detrás de un balanceador.

- Un job de Batch puede ejecutarse durante más tiempo que una función Lambda y no necesita mantenerse como un ECS service permanente.

> **Caso:** miles de simulaciones financieras nocturnas se colocan en una job queue y AWS Batch ejecuta contenedores según capacidad disponible.
>
> **Logo:** `recursos/aws/compute/batch.svg`
>
> **Imagen sugerida:** Job queue con varios trabajos que pasan a contenedores y finalizan al terminar el procesamiento.

### Slide: Tareas ECS con EventBridge

**Título en slide:** EVENTBRIDGE CON ECS RUN TASK

#### Nombres en portal y examen

> **Amazon EventBridge**, **EventBridge Scheduler**, **ECS RunTask**

#### Conceptos

- **ECS RunTask** permite iniciar una task puntual sin crear un service que deba mantenerla funcionando de forma permanente.

- **EventBridge Scheduler** puede iniciar tasks ECS de acuerdo con un horario, por ejemplo cada hora, cada noche o mediante una expresión cron.

- También pueden utilizarse eventos para iniciar procesamiento cuando ocurre una acción determinada, dependiendo de la integración y del patrón arquitectónico.

- Una task programada puede ejecutarse sobre **Fargate**, procesar información, escribir resultados y finalizar sin mantener servidores EC2 encendidos.

- Si el proceso necesita coordinar varios pasos, decisiones, reintentos y estado entre diferentes servicios, **AWS Step Functions** puede ser una alternativa de orquestación más apropiada.

> **Caso:** un script empaquetado en Docker se ejecuta cada noche mediante EventBridge Scheduler y ECS RunTask sobre Fargate.
>
> **Logo:** `recursos/aws/integration/eventbridge.svg`
>
> **Imagen sugerida:** Reloj cron conectado a EventBridge Scheduler, luego a una task Fargate que procesa información y termina.

## Sesión 12.7: Amazon EKS

### Slide: Qué problema resuelve EKS

**Título en slide:** AMAZON EKS: LA IDEA

#### Nombres en portal y examen

> **Amazon EKS** (*Elastic Kubernetes Service*), **Kubernetes**

#### Conceptos

- **Amazon EKS proporciona Kubernetes administrado en AWS.** AWS opera el plano de control del clúster y el usuario despliega workloads utilizando las APIs y herramientas estándar de Kubernetes.

- ECS y EKS permiten ejecutar contenedores, pero utilizan **modelos y APIs diferentes**. EKS encaja cuando el escenario requiere explícitamente Kubernetes.

- EKS permite aprovechar herramientas existentes del ecosistema Kubernetes, como manifiestos, Helm y otros componentes compatibles con la plataforma.

- Los workloads pueden ejecutarse sobre **nodos EC2** o mediante **AWS Fargate**, dependiendo del nivel de control y administración requerido.

- Para alta disponibilidad, los workloads pueden distribuirse entre diferentes zonas de disponibilidad utilizando la arquitectura del clúster y los recursos de red correspondientes.

> **Caso:** una empresa que ya opera Kubernetes on premises migra sus workloads a Amazon EKS manteniendo el modelo Kubernetes.
>
> **Logo:** `recursos/aws/otros/elastic-kubernetes-service.svg`
>
> **Imagen sugerida:** Plano de control EKS administrado por AWS y workloads distribuidos entre varias AZ con líneas punteadas de fondo.

### Slide: Nodos EC2 y Fargate en EKS

**Título en slide:** EKS: NODOS Y FARGATE

#### Nombres en portal y examen

> **managed node group**, **self managed nodes**, **Fargate**

#### Conceptos

- Un **managed node group** utiliza instancias EC2 como workers de Kubernetes, mientras AWS simplifica operaciones como creación y actualización de los nodos.

- Con **self managed nodes**, la organización administra con mayor detalle las instancias EC2 utilizadas como workers y su ciclo de vida.

- **EKS con Fargate** permite ejecutar determinados pods sin administrar instancias EC2 subyacentes.

- Cuando se utilizan nodos EC2 pueden existir mayores posibilidades de personalización, mientras Fargate prioriza reducir la administración del cómputo.

- El almacenamiento persistente puede integrarse mediante controladores CSI con servicios como **Amazon EBS, Amazon EFS y determinados servicios FSx**, según las necesidades del workload.

> **Caso:** una empresa migra Kubernetes desde on premises hacia EKS utilizando managed node groups para conservar control sobre los workers.
>
> **Logo:** `recursos/aws/otros/elastic-kubernetes-service.svg`
>

### Slide: IAM Roles for Service Accounts

**Título en slide:** IAM ROLES FOR SERVICE ACCOUNTS

#### Nombres en portal y examen

> **IRSA** (*IAM Roles for Service Accounts*), **Kubernetes service account**

#### Conceptos

- **IRSA permite asociar permisos IAM a un Kubernetes service account**, evitando entregar las mismas credenciales AWS a todos los pods que comparten un nodo.

- Los pods vinculados a ese service account pueden obtener **credenciales temporales** para acceder a los servicios AWS autorizados por el rol.

- Esto permite aplicar **mínimo privilegio por workload**, por ejemplo un frontend con permisos para DynamoDB y un procesador con permisos únicamente para S3.

- Conceptualmente cumple un objetivo parecido al **task role de ECS**, pero utilizando identidades y service accounts del entorno Kubernetes.

- Evita almacenar **access keys de larga duración dentro de las imágenes o variables del contenedor** para acceder a recursos AWS.

> **Caso Check yourself EN:** separar los permisos de pods que acceden a DynamoDB y S3 utilizando distintos service accounts, id 5.

## Sesión 12.8: Variantes y reconocimiento

### Slide: EKS Anywhere y EKS Distro

**Título en slide:** EKS ANYWHERE Y EKS DISTRO

#### Nombres en portal y examen

> **Amazon EKS Anywhere**, **Amazon EKS Distro**

#### Conceptos

- **Amazon EKS** ejecuta Kubernetes administrado dentro de AWS, mientras **EKS Anywhere** está orientado a crear y operar clústeres Kubernetes en infraestructura administrada por el cliente fuera de una región AWS.

- EKS Anywhere permite utilizar una experiencia Kubernetes consistente en entornos como **datacenters propios o edge**, cuando los workloads deben permanecer fuera de la nube pública.

- **Amazon EKS Distro** es la distribución de Kubernetes basada en los mismos componentes utilizados por Amazon EKS. No es por sí misma un servicio administrado que cree un clúster.

- **EKS Anywhere y EKS Distro no son equivalentes:** Anywhere proporciona herramientas para operar clústeres, mientras Distro proporciona la distribución Kubernetes.

- Si un escenario exige ejecutar Kubernetes sobre **AWS Outposts**, debe distinguirse de EKS Anywhere y evaluarse la opción de **Amazon EKS sobre AWS Outposts**.

> **Logo:** `recursos/aws/otros/elastic-kubernetes-service.svg`
>
> **Imagen sugerida:** Tres bloques separados: EKS en AWS, EKS Anywhere en datacenter propio y EKS Distro como distribución Kubernetes.

### Slide: ECS Anywhere

**Título en slide:** AMAZON ECS ANYWHERE

#### Nombres en portal y examen

> **Amazon ECS Anywhere**

#### Conceptos

- **ECS Anywhere permite utilizar servidores externos a AWS como capacidad para Amazon ECS**, incluidos determinados servidores on premises o máquinas virtuales.

- Los sistemas externos se registran para ejecutar workloads administrados mediante el **plano de control de Amazon ECS**.

- Las aplicaciones siguen utilizando conceptos propios de ECS, como **task definitions**, por lo que ECS Anywhere no convierte el entorno en Kubernetes.

- Puede resultar útil cuando una organización ya utiliza ECS pero necesita ejecutar determinados workloads sobre infraestructura ubicada fuera de AWS.

- **ECS Anywhere y EKS Anywhere no son equivalentes:** ECS Anywhere utiliza el modelo ECS; EKS Anywhere utiliza Kubernetes.

> **Logo:** `recursos/aws/containers/ecs-anywhere.svg`
>

### Slide: AWS App Runner

**Título en slide:** AWS APP RUNNER: RECONOCIMIENTO

#### Nombres en portal y examen

> **AWS App Runner**

#### Conceptos

- **AWS App Runner** es un servicio administrado para desplegar aplicaciones web y APIs desde código fuente o una imagen de contenedor sin administrar directamente un clúster ECS o EKS.

- El servicio administra infraestructura, despliegue y escalado de la aplicación, reduciendo la cantidad de configuración necesaria para publicar un servicio web.

- En este módulo aparece principalmente como **servicio de reconocimiento**. ECS, EKS, ECR y Fargate tienen mayor profundidad para las decisiones de arquitectura estudiadas.

- Si el escenario necesita control explícito sobre **task definitions, services ECS, ALB o configuraciones específicas del orquestador**, App Runner no sustituye automáticamente esos componentes.

## Sesión 12.9: Arquitecturas

### Slide: Fargate detrás de un ALB

**Título en slide:** FARGATE DETRÁS DEL ALB

#### Conceptos

- El tráfico entra mediante un **Application Load Balancer**, que distribuye las solicitudes hacia las tasks de un ECS service registradas en su target group.

- Las tasks utilizan **AWS Fargate**, por lo que no aparecen instancias EC2 administradas por el usuario. Pueden distribuirse entre diferentes AZ para mejorar disponibilidad.

- La imagen utilizada por las tasks se obtiene desde **Amazon ECR** durante el despliegue o inicio de nuevas tasks. ECR no forma parte del camino normal de cada solicitud HTTP.

- El **task execution role** permite realizar acciones necesarias para iniciar la task, mientras el **task role** proporciona los permisos AWS que necesita la aplicación.

- Si la aplicación requiere almacenamiento de archivos persistente y compartido, puede montarse **Amazon EFS** en las tasks.
