## Sesión 12.1 — Registro de imágenes

### Slide 1 — Contenedores en AWS

**Título en slide**

CONTENEDORES EN AWS

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Image** / **Imagen**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Un contenedor empaqueta la aplicación y sus dependencias para ejecutarlas de forma consistente entre desarrollo y producción.
- Una **imagen** es la plantilla inmutable utilizada para crear uno o varios contenedores con la misma configuración.
- Varios contenedores pueden compartir el sistema operativo del host y normalmente consumen menos recursos que una máquina virtual completa por aplicación.
- **Amazon ECS** y **Amazon EKS** orquestan contenedores, mientras **AWS Fargate** proporciona capacidad de cómputo sin administrar instancias EC2.

> **Nota**  
> Fargate no es un orquestador independiente. Puede utilizarse como capacidad de cómputo para ECS o EKS.

> **Idea visual**  
> Host con varios contenedores pequeños frente a varias máquinas virtuales completas. Flecha `misma aplicación → misma imagen`.

### Slide 2 — Amazon Elastic Container Registry

**Título en slide**

AMAZON ELASTIC CONTAINER REGISTRY (AMAZON ECR)

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Push / Pull**

#### Conceptos

- **Amazon ECR** es el registro administrado de AWS para almacenar, administrar y versionar imágenes de contenedores.
- Los repositorios pueden ser privados y **Amazon ECR Public** permite distribuir imágenes públicamente.
- IAM y las políticas del repositorio controlan `push` y `pull`, mientras el image scanning ayuda a detectar vulnerabilidades.
- Las lifecycle policies pueden eliminar imágenes antiguas, pero **ECR almacena imágenes y no ejecuta contenedores**.

> **Nota**  
> ECR admite imágenes Docker, imágenes OCI y artefactos compatibles con OCI.

> **Ejemplo**  
> Un pipeline CI construye una imagen, la sube a ECR y posteriormente Amazon ECS utiliza esa imagen para iniciar una task.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

> **Idea visual**

## Sesión 12.2 — Amazon ECS

### Slide 1 — Amazon Elastic Container Service

**Título en slide**

AMAZON ELASTIC CONTAINER SERVICE (AMAZON ECS)

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**  
> **Container orchestration**

#### Conceptos

- **Amazon ECS** es un servicio totalmente administrado para desplegar, administrar y escalar aplicaciones en contenedores.
- Un **ECS cluster** agrupa de forma lógica la capacidad donde se ejecutan las tasks.
- ECS utiliza un modelo propio de AWS y no requiere instalar ni administrar Kubernetes.
- Puede ejecutar workloads utilizando capacidad de Amazon EC2, AWS Fargate o diferentes capacity providers.

> **Nota**  
> Si el escenario exige específicamente Kubernetes, sus APIs o herramientas como Helm, la alternativa habitual es Amazon EKS.

> **Ejemplo**  
> Una API REST puede ejecutarse mediante Amazon ECS y mantener varias réplicas disponibles detrás de un Application Load Balancer.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Plano de control ECS administrado por AWS con varias tasks debajo.

### Slide 2 — Task definition y task

**Título en slide**

TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task**  
> **Container** / **Contenedor**

#### Conceptos

- Una **task definition** describe imagen, CPU, memoria, red, variables, volúmenes, logging y roles IAM necesarios para ejecutar la aplicación.
- Cada modificación genera una nueva revisión y una **task** representa una instancia en ejecución de esa definición.
- Una task puede contener uno o varios contenedores que necesitan ejecutarse juntos, por ejemplo una aplicación y un sidecar.
- La misma task definition puede utilizarse para iniciar múltiples tasks con una configuración equivalente.

> **Nota**  
> En Fargate deben utilizarse combinaciones admitidas de CPU y memoria. Por ejemplo **0,25 vCPU** admite **512 MiB, 1 GB o 2 GB** de memoria.

### Slide 3 — ECS Service

**Título en slide**

ECS SERVICE

#### Nombres en portal y examen

> **ECS service**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** mantiene aplicaciones de larga duración funcionando y reemplaza automáticamente las tasks que fallen.
- El **desired count** indica cuántas tasks debe mantener el service simultáneamente.
- El service puede registrar sus tasks en un target group para recibir tráfico desde un balanceador.
- Una task tiene un ciclo de ejecución, mientras un service mantiene continuamente la cantidad deseada de tasks.

> **Ejemplo**  
> Una tienda online utiliza un service con `desired count = 4` y mantiene cuatro tasks disponibles.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

## Sesión 12.3 — Cómputo para contenedores

### Slide 1 — Amazon Elastic Compute Cloud

**Título en slide**

AMAZON ELASTIC COMPUTE CLOUD (AMAZON EC2)

#### Nombres en portal y examen

> **Amazon Elastic Compute Cloud (Amazon EC2)**  
> **EC2 launch type**  
> **ECS container agent**

#### Conceptos

- ECS puede ejecutar tasks sobre **instancias Amazon EC2** que forman parte de la capacidad del clúster.
- El **ECS container agent** conecta las instancias con Amazon ECS, recibe las tasks y reporta su estado.
- Tú administras sistema operativo, parches, tipo de instancia y capacidad disponible en los hosts.
- EC2 encaja cuando necesitas mayor control del host, GPU, tipos de instancia específicos o capacidad ya comprometida.

> **Nota**  
> Si aumentan las tasks y ya no caben en el clúster, también debe aumentar la capacidad EC2 disponible.

> **Logo** `recursos/aws/compute/ec2.svg`

> **Idea visual**  
> Dos instancias EC2 con ECS agent y varias tasks ejecutándose sobre ellas.

### Slide 2 — AWS Fargate

**Título en slide**

AWS FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Fargate launch type**  
> **awsvpc**

#### Conceptos

- **AWS Fargate** ejecuta contenedores sin que tengas que aprovisionar, administrar ni parchear instancias EC2.
- Defines CPU y memoria para el workload y AWS administra la infraestructura subyacente.
- Las tasks Fargate utilizan `awsvpc`, reciben una ENI propia y pueden utilizar security groups directamente.
- Fargate funciona con **Amazon ECS y Amazon EKS**, por lo que proporciona cómputo y no reemplaza al orquestador.

> **Datos de certificación**  
> En ECS Fargate sobre Linux con platform version **1.4.0 o posterior**, cada task recibe **20 GiB** de almacenamiento efímero por defecto.

### Slide 3 — EC2 frente a Fargate

**Título en slide**

EC2 VS FARGATE

#### Conceptos

| Característica | Amazon EC2 | AWS Fargate |
|---|---|---|
| Host | Lo administras | AWS lo administra |
| Parches del host | Tu responsabilidad | AWS |
| Capacidad | Instancias EC2 | CPU y memoria por workload |
| Control del host | Mayor | Menor |
| Operación | Mayor | Menor |

- Con Amazon EC2 pagas las instancias y recursos asociados como Amazon EBS cuando corresponda.
- Con Fargate pagas principalmente la **vCPU y memoria** configuradas durante la ejecución.
- Los **Compute Savings Plans** pueden aplicar tanto a determinados usos de EC2 como de Fargate.
- EC2 puede convenir con utilización estable, mientras Fargate prioriza reducir administración.

## Sesión 12.4 — Servicio en producción

### Slide 1 — Application Load Balancer con ECS

**Título en slide**

ALB CON AMAZON ECS

#### Conceptos

- Un **Application Load Balancer** distribuye tráfico HTTP y HTTPS entre las tasks de un ECS service mediante un target group.
- Con ECS sobre EC2 en modo `bridge`, el dynamic host port mapping permite utilizar puertos distintos del host.
- Con Fargate cada task utiliza `awsvpc` y dispone de su propia dirección IP dentro de la VPC.
- Los health checks permiten retirar tasks no saludables mientras ECS puede iniciar reemplazos.

> **Nota**  
> ALB suele utilizarse para HTTP y HTTPS. Network Load Balancer encaja mejor cuando el escenario requiere características de capa 4.

> **Idea visual**  
> ALB en 443 → target group → varias tasks ECS.

### Slide 2 — ECS Service Auto Scaling

**Título en slide**

ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **Target tracking**

#### Conceptos

- ECS Service Auto Scaling modifica automáticamente el **desired count** cuando cambia la demanda.
- Puede utilizar métricas como CPU promedio, memoria promedio o `ALBRequestCountPerTarget`.
- Target tracking intenta mantener una métrica cerca del valor objetivo configurado.
- Con ECS sobre EC2 debes distinguir el escalado de las tasks del escalado de la capacidad EC2.

> **Ejemplo**  
> Si aumenta la CPU promedio del service, el desired count puede cambiar de `2 → 5`.

**Título en slide**

AMAZON ELASTIC FILE SYSTEM (AMAZON EFS)

#### Nombres en portal y examen

> **Amazon Elastic File System (Amazon EFS)**  
> **EFS access point**  
> **Shared file storage**

#### Conceptos

- **Amazon EFS** proporciona almacenamiento de archivos persistente que puede compartirse entre múltiples tasks.

- En ECS con Fargate sobre Linux se admite EFS desde platform version **1.4.0 o posterior**.

> **Nota**  
> Un EFS access point puede limitar el directorio visible y aplicar una identidad determinada al acceder al filesystem.

### Slide 4 — Throughput de Amazon EFS

**Título en slide**

AMAZON EFS Y THROUGHPUT

#### Nombres en portal y examen

> **Elastic Throughput**  
> **Provisioned Throughput**  
> **Bursting Throughput**

#### Conceptos

- **Elastic Throughput** ajusta automáticamente el rendimiento y encaja con cargas impredecibles o variables.
- **Provisioned Throughput** permite configurar rendimiento independientemente del tamaño almacenado.
- **Bursting Throughput** relaciona el rendimiento con el tamaño del filesystem y utiliza burst credits para superar el baseline.
- Provisioned puede ser útil cuando un filesystem relativamente pequeño necesita lecturas y escrituras sostenidas de alto rendimiento.

> **Caso Check yourself EN**

### Slide 1 — Roles IAM en Amazon ECS

**Título en slide**

ROLES IAM EN AMAZON ECS

#### Nombres en portal y examen

> **Task role**  
> **Task execution role**  
> **Container instance role**

#### Conceptos

- El **task role** proporciona permisos AWS al código que se ejecuta dentro del contenedor.
- El **task execution role** permite acciones de arranque como descargar imágenes privadas de ECR y enviar logs.

> **Nota**  
> Los permisos del task execution role no están disponibles automáticamente para el código de la aplicación.

> **Ejemplo**

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue**  
> **Compute environment**

#### Conceptos

- **AWS Batch** ejecuta trabajos con inicio y fin como simulaciones, renderizado o procesamiento intensivo de datos.
- Los workloads se empaquetan como imágenes de contenedor y los jobs esperan en una **job queue**.
- Batch programa los trabajos utilizando compute environments configurados para proporcionar capacidad.
- Encaja cuando existen muchos trabajos independientes que deben ejecutarse y terminar, no un servicio permanente.

> **Nota**  
> Los compute environments pueden utilizar diferentes opciones de cómputo como Amazon EC2, Spot o AWS Fargate según la configuración.

> **Ejemplo**  
> Miles de simulaciones nocturnas esperan en una cola y AWS Batch las ejecuta conforme dispone de capacidad.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> Job queue → compute environment → contenedores → fin.

AMAZON EVENTBRIDGE SCHEDULER

#### Nombres en portal y examen

> **Amazon EventBridge Scheduler**  
> **Cron expression**  
> **Rate expression**  
> **One-time schedule**

#### Conceptos

- **Amazon EventBridge Scheduler** ejecuta tareas en una fecha concreta, mediante cron o con una frecuencia determinada.

> **Nota**

### Slide 3 — Service, RunTask o AWS Batch

**Título en slide**

SERVICE, RUN TASK O BATCH

#### Conceptos

| El escenario necesita | Patrón |
|---|---|
| Aplicación siempre disponible | **ECS service** |
| Contenedor puntual | **ECS RunTask** |
| Ejecución por horario | **EventBridge Scheduler + RunTask** |
| Cola de muchos trabajos | **AWS Batch** |

- Un service mantiene desired count y reemplaza tasks de larga duración.
- RunTask ejecuta una task puntual sin mantener un service.
- AWS Batch añade scheduling de jobs y capacidad orientada al procesamiento por lotes.

## Sesión 12.9 — Arquitecturas

### Slide 1 — Fargate detrás del ALB

**Título en slide**

FARGATE DETRÁS DEL ALB

#### Conceptos

- El Application Load Balancer distribuye tráfico hacia las tasks Fargate registradas en el target group del ECS service.
- Las tasks pueden distribuirse entre distintas Availability Zones sin administrar instancias EC2.
- Las imágenes proceden de Amazon ECR y los permisos se separan mediante task execution role y task role.
- Si la aplicación necesita almacenamiento compartido, las tasks pueden montar Amazon EFS.

> **Nota**  
> Amazon ECR participa cuando se inicia o actualiza una task y no forma parte del recorrido de cada solicitud HTTP.

> **Idea visual**
>
> 1. Región con AZ-a y AZ-b separadas mediante líneas punteadas.
> 2. Usuario → Application Load Balancer → target group.
> 3. Tasks Fargate en subredes privadas de ambas AZ.
> 4. Amazon ECR conectado hacia las tasks mediante una flecha `imagen`.
