## Sesión 12.1 — Registro de imágenes

### Slide 1 — Contenedores en AWS

**Título en slide**

CONTENEDORES EN AWS

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Image** / **Imagen**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Un contenedor empaqueta la aplicación y sus dependencias para ejecutarlas de forma consistente entre desarrollo y producción.
- Una **imagen** es la plantilla inmutable utilizada para crear uno o varios contenedores con la misma configuración.
- Varios contenedores pueden compartir el sistema operativo del host y normalmente consumen menos recursos que una máquina virtual completa por aplicación.
- La orquestación coloca los contenedores, mantiene la capacidad necesaria y reemplaza aquellos que fallan.

> **Idea visual**  
> Host con varios contenedores pequeños frente a varias máquinas virtuales completas. Flecha `misma aplicación → misma imagen`.

### Slide 2 — Amazon Elastic Container Registry

**Título en slide**

AMAZON ELASTIC CONTAINER REGISTRY

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Push / Pull**

#### Conceptos

- **Amazon ECR** es un registro administrado para almacenar, compartir y versionar imágenes de contenedores.
- Los repositorios pueden ser privados y **Amazon ECR Public** permite distribuir imágenes públicamente.
- IAM y las políticas del repositorio controlan `push` y `pull`, mientras el image scanning ayuda a identificar vulnerabilidades.
- Las lifecycle policies permiten expirar imágenes antiguas, pero **ECR almacena imágenes y no ejecuta contenedores**.

> **Nota**  
> Amazon ECR ofrece escaneo básico y escaneo mejorado integrado con Amazon Inspector.

> **Ejemplo**  
> Un pipeline CI construye una imagen, la sube a ECR y posteriormente el orquestador la utiliza para iniciar contenedores.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

> **Idea visual**  
> Repositorio ECR con varias versiones de una imagen y una flecha `pull` hacia un contenedor.

## Sesión 12.2 — Amazon ECS

### Slide 1 — Amazon Elastic Container Service

**Título en slide**

AMAZON ELASTIC CONTAINER SERVICE

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**  
> **Task**  
> **Service**

#### Conceptos

- **Amazon ECS** es un servicio administrado de orquestación que permite desplegar y escalar aplicaciones en contenedores.
- Un **ECS cluster** agrupa de forma lógica las tasks y puede utilizar diferentes opciones de capacidad.
- ECS utiliza un modelo propio de AWS y no requiere implementar ni administrar Kubernetes.
- El flujo habitual sigue **imagen → task definition → task → service** cuando la aplicación debe permanecer en ejecución.

> **Ejemplo**  
> Una API REST empaquetada en contenedores puede ejecutarse como un ECS service detrás de un balanceador.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Plano de control ECS administrado por AWS con varias tasks debajo.

### Slide 2 — Task definition y task

**Título en slide**

TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task**  
> **Container** / **Contenedor**

#### Conceptos

- Una **task definition** describe cómo ejecutar la aplicación e incluye imagen, CPU, memoria, red, variables, volúmenes, logging y roles IAM.
- Cada cambio genera una nueva revisión y una **task** representa una instancia en ejecución de una de esas revisiones.
- Una task puede contener varios contenedores que deben ejecutarse juntos, por ejemplo una aplicación acompañada por un sidecar.
- La **task** es la unidad de ejecución, mientras el **service** mantiene la cantidad requerida de tasks funcionando.

> **Nota**  
> En Fargate deben utilizarse combinaciones admitidas de CPU y memoria. Por ejemplo, **0,25 vCPU** admite **512 MiB, 1 GB o 2 GB**.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `Task definition v3` → tres tasks idénticas.

### Slide 3 — ECS Service

**Título en slide**

ECS SERVICE

#### Nombres en portal y examen

> **ECS service**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** mantiene aplicaciones de larga duración funcionando y reemplaza automáticamente las tasks que fallen.
- El **desired count** define cuántas tasks deben ejecutarse simultáneamente y ECS intenta mantener ese número.
- El service puede registrar sus tasks en un target group para distribuir tráfico entre las instancias de la aplicación.
- Un service encaja en aplicaciones continuas, mientras un proceso con inicio y fin puede utilizar una task independiente.

> **Ejemplo**  
> Una tienda online utiliza un service con `desired count = 4` distribuido entre dos Availability Zones.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Service con cuatro tasks y una task fallida siendo reemplazada.

## Sesión 12.3 — Cómputo de contenedores

### Slide 1 — AWS Fargate

**Título en slide**

AWS FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Serverless compute for containers**  
> **awsvpc**

#### Conceptos

- **AWS Fargate** ejecuta contenedores sin que tengas que aprovisionar, administrar ni parchear instancias EC2.
- Defines la CPU y memoria necesarias y AWS administra la infraestructura subyacente.
- Las tasks de ECS sobre Fargate utilizan `awsvpc`, reciben su propia ENI y pueden tener security groups aplicados directamente.
- Fargate puede utilizarse con **Amazon ECS y Amazon EKS**, por lo que proporciona cómputo y no reemplaza al orquestador.

> **Nota**  
> En ECS Fargate sobre Linux, platform version **1.4.0 o posterior** incluye **20 GiB** de almacenamiento efímero por defecto y permite configurarlo hasta **200 GiB**.

> **Logo** `recursos/aws/compute/fargate.svg`

### Slide 2 — ECS con EC2

**Título en slide**

ECS CON EC2

#### Nombres en portal y examen

> **EC2 launch type**  
> **ECS container agent**  
> **Capacity provider**

#### Conceptos

- Con **EC2 launch type**, las tasks de ECS se ejecutan sobre instancias EC2 que forman parte del clúster.
- El **ECS container agent** conecta cada instancia con ECS, recibe las tasks y reporta su estado.
- La organización administra sistema operativo, parches, tipos de instancia y capacidad disponible en los hosts.
- El escalado puede ocurrir en dos niveles porque deben existir suficientes tasks y también suficiente capacidad EC2 para ejecutarlas.

> **Nota**  
> Un capacity provider puede asociar el clúster con un Auto Scaling Group para administrar la capacidad EC2.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Instancias EC2 con ECS agent y varias tasks distribuidas entre dos AZ.

### Slide 3 — EC2 frente a Fargate

**Título en slide**

EC2 VS FARGATE

#### Conceptos

- Con EC2 pagas las instancias utilizadas por el clúster y recursos asociados como EBS cuando corresponda.
- Con Fargate pagas principalmente la vCPU y memoria configuradas para las tasks durante su ejecución.
- Los **Compute Savings Plans** pueden aplicar tanto a determinados usos de EC2 como de Fargate.
- EC2 puede convenir con cargas estables y alta utilización, mientras Fargate reduce la carga operativa.

> **Nota**  
> Ninguna opción es siempre más barata. El examen suele combinar **costo, control y operación** para decidir.

> **Caso Check yourself ES**  
> Comparación del modelo de precio de ECS con EC2 frente a ECS con Fargate, id 24.

> **Idea visual**  
> Recibo `EC2 + EBS` frente a recibo `vCPU + memoria`.

## Sesión 12.4 — Servicio en producción

### Slide 1 — Elastic Load Balancing

**Título en slide**

ELASTIC LOAD BALANCING

#### Nombres en portal y examen

> **Elastic Load Balancing (ELB)**  
> **Application Load Balancer (ALB)**  
> **Network Load Balancer (NLB)**  
> **Target group**

#### Conceptos

- **Elastic Load Balancing** distribuye tráfico entre múltiples destinos saludables y puede utilizar contenedores como targets.
- **Application Load Balancer** es habitual para tráfico HTTP y HTTPS, mientras NLB trabaja en escenarios de red de capa 4.
- Los health checks permiten dejar de enviar tráfico a destinos no saludables.
- En workloads de contenedores, el target group puede registrar instancias, direcciones IP u otros destinos según el diseño.

> **Nota**  
> Con ECS sobre EC2 en modo `bridge` puede utilizarse dynamic host port mapping. Con Fargate se utiliza `awsvpc` y cada task dispone de su propia IP.

> **Logo** `recursos/aws/networking/elb.svg`

> **Idea visual**  
> ALB → target group → varias tasks saludables.

### Slide 2 — ECS Service Auto Scaling

**Título en slide**

ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **Target tracking**  
> **Desired count**

#### Conceptos

- ECS Service Auto Scaling aumenta o reduce automáticamente el **desired count** según cambia la demanda.
- Las políticas pueden utilizar CPU promedio, memoria promedio o **ALBRequestCountPerTarget**.
- Target tracking intenta mantener una métrica cerca de un valor objetivo definido.
- Con ECS sobre EC2 debes distinguir el escalado de las tasks del escalado de la capacidad EC2 del clúster.

> **Ejemplo**  
> Si aumenta la CPU promedio del service, el desired count puede pasar de `2` a `5`.

### Slide 3 — Amazon Elastic File System

**Título en slide**

AMAZON ELASTIC FILE SYSTEM

#### Nombres en portal y examen

> **Amazon Elastic File System (Amazon EFS)**  
> **EFS access point**  
> **Persistent shared storage**

#### Conceptos

- **Amazon EFS** proporciona almacenamiento de archivos persistente y compartido que puede utilizarse desde múltiples clientes.
- Las tasks ECS pueden montar EFS y compartir los mismos datos aunque se ejecuten en hosts o Availability Zones diferentes.
- EFS funciona con ECS sobre EC2 y con Fargate Linux desde platform version **1.4.0 o posterior**.
- Los access points permiten controlar el directorio visible y aplicar una identidad determinada para cada aplicación.

> **Nota**  
> Cuando varios contenedores necesitan un filesystem compartido, EFS es el patrón habitual frente a utilizar S3 como un disco tradicional.

> **Caso Check yourself EN**

### Slide 4 — Throughput de Amazon EFS

**Título en slide**

EFS Y THROUGHPUT

#### Nombres en portal y examen

> **Elastic Throughput**  
> **Provisioned Throughput**  
> **Bursting Throughput**

#### Conceptos

- **Elastic Throughput** adapta automáticamente el rendimiento y encaja en workloads impredecibles o variables.
- **Provisioned Throughput** permite configurar rendimiento independientemente del tamaño almacenado.
- **Bursting Throughput** relaciona el rendimiento con el tamaño del filesystem y utiliza burst credits.
- El modo correcto depende del patrón de acceso y no existe un único throughput mode adecuado para todos los workloads.

> **Nota**  
> El banco contiene una pregunta donde **Provisioned Throughput** resuelve un filesystem relativamente pequeño con alta frecuencia de lecturas y escrituras.

> **Logo** `recursos/aws/storage/efs.svg`

> Tres tarjetas `Elastic`, `Provisioned`, `Bursting`.

**Título en slide**

AWS IDENTITY AND ACCESS MANAGEMENT

#### Nombres en portal y examen

> **AWS Identity and Access Management (IAM)**  
> **Task role**  
> **Task execution role**  
> **Container instance role**

#### Conceptos

- El **task role** entrega permisos al código dentro del contenedor para acceder a servicios AWS como S3 o SQS.

- Diferentes aplicaciones pueden utilizar task roles distintos para aplicar mínimo privilegio dentro del mismo clúster.

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue**  
> **Compute environment**

#### Conceptos

- **AWS Batch** administra trabajos con inicio y fin como simulaciones, renderizado, procesamiento científico o ETL intensivo.
- El workload se empaqueta como una imagen de contenedor y se envía como un job a una **job queue**.
- La cola se conecta con compute environments que pueden utilizar opciones como EC2, Spot o Fargate.
- Un job termina cuando completa su procesamiento y no necesita permanecer activo como un servicio continuo.

> **Nota**  
> Una job queue que utiliza Fargate no mezcla compute environments EC2 y Fargate dentro de la misma cola.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> Job queue → compute environment → varios contenedores → `exit`.

### Slide 3 — ECS RunTask

**Título en slide**

ECS RUN TASK

#### Conceptos

- `RunTask` inicia una o varias tasks ECS sin crear un service que deba mantenerlas permanentemente.

- Si el proceso requiere una gran cola de jobs y planificación de capacidad, AWS Batch suele proporcionar un modelo más especializado.

> **Ejemplo**

### Slide 1 — Amazon Elastic Kubernetes Service

**Título en slide**

AMAZON ELASTIC KUBERNETES SERVICE

#### Nombres en portal y examen

> **Amazon Elastic Kubernetes Service (Amazon EKS)**  
> **Kubernetes**  
> **Control plane**

#### Conceptos

- **Amazon EKS** es un servicio administrado para ejecutar Kubernetes sin operar manualmente el plano de control.
- Los workloads utilizan las APIs y herramientas estándar de Kubernetes, por lo que EKS encaja cuando el escenario exige esta plataforma.
- AWS administra la disponibilidad y escalabilidad del plano de control en múltiples Availability Zones.
- Los workloads pueden utilizar diferentes opciones de cómputo según el nivel de control y operación requerido.

> **Ejemplo**  
> Una empresa que ya utiliza Kubernetes on premises puede migrar aplicaciones a Amazon EKS manteniendo las mismas APIs y herramientas.

NODOS DE AMAZON EKS

#### Nombres en portal y examen

> **Managed node group**  
> **Self-managed nodes**  
> **Auto Scaling Group**

## Sesión 12.9 — Arquitecturas

### Slide 1 — Arquitectura con Amazon ECS y AWS Fargate

**Título en slide**

ARQUITECTURA CON ECS Y FARGATE

#### Conceptos

- El Application Load Balancer distribuye tráfico hacia las tasks Fargate registradas en el target group del ECS service.
- Las tasks se distribuyen entre Availability Zones sin que el usuario administre instancias EC2.
- Las imágenes proceden de Amazon ECR y los permisos se separan mediante task execution role y task role.
- Si la aplicación necesita almacenamiento compartido, las tasks pueden montar Amazon EFS.

> **Nota**  
> Esta es una slide de arquitectura y por eso integra varios servicios ya explicados individualmente.

> **Idea visual**
>
> 1. Región con AZ-a y AZ-b separadas mediante líneas punteadas.
> 2. Usuario → Application Load Balancer → target group.
> 3. ECS service con tasks Fargate en subredes privadas de ambas AZ.
> 4. Amazon ECR conectado hacia las tasks mediante una flecha `imagen`.
> 5. Amazon EFS conectado a ambas AZ cuando se necesite almacenamiento compartido.
