# Módulo M12 — Contenedores

> Dominios 2 y 3.  
> **Ya sabes** una instancia EC2 es una máquina que tú parcheas y un Application Load Balancer reparte tráfico HTTP entre destinos.  
> **Aquí aprendes** dónde se guarda una imagen Docker, quién inicia y escala los contenedores, cómo elegir entre EC2 y Fargate y cuándo el escenario necesita Kubernetes.  
> **No se asume** operar un clúster EKS desde consola. AWS App Runner aparece únicamente como servicio de reconocimiento.

## Sesión 12.1 — Registro de imágenes

### Slide 1 — Contenedores en AWS

**Título en slide**

CONTENEDORES EN AWS

#### Nombres en portal y examen

> **Container** / **Contenedor**  
> **Image** / **Imagen**  
> **Container orchestration** / **Orquestación de contenedores**

#### Conceptos

- Un contenedor empaqueta la aplicación y sus dependencias para ejecutarlas de forma consistente entre desarrollo y producción.
- Una **imagen** es la plantilla inmutable utilizada para crear uno o varios contenedores con la misma configuración.
- Varios contenedores pueden compartir el sistema operativo del host y normalmente consumen menos recursos que una máquina virtual completa por aplicación.
- **Amazon ECS** y **Amazon EKS** orquestan contenedores, mientras **AWS Fargate** aporta cómputo sin administrar instancias EC2.

> **Nota**  
> Fargate no es un orquestador independiente. Se utiliza junto con ECS o EKS.

> **Ejemplo**  
> Una aplicación HTTP almacena su imagen en Amazon ECR y se ejecuta como varias tasks de Amazon ECS detrás de un Application Load Balancer.

> **Logo** `recursos/aws/compute/fargate.svg`

> **Idea visual**  
> Host EC2 con varios contenedores pequeños frente a varias máquinas virtuales completas. Flecha `misma aplicación → misma imagen`.

### Slide 2 — Amazon ECR

**Título en slide**

AMAZON ECR

#### Nombres en portal y examen

> **Amazon Elastic Container Registry (Amazon ECR)**  
> **Repository** / **Repositorio**  
> **Push / Pull**

#### Conceptos

- **Amazon ECR** almacena y versiona imágenes de contenedores que después pueden utilizar ECS, EKS, AWS Batch y otros servicios.
- Los repositorios pueden ser privados y **Amazon ECR Public** permite distribuir imágenes públicamente.
- IAM y las políticas del repositorio controlan `push` y `pull`, mientras el image scanning ayuda a identificar vulnerabilidades.
- Las lifecycle policies permiten expirar imágenes antiguas, pero **ECR no ejecuta contenedores** ni sustituye a ECS o EKS.

> **Nota**  
> ECR ofrece escaneo básico y escaneo mejorado integrado con Amazon Inspector.

> **Ejemplo**  
> Un pipeline CI construye una imagen, la sube a ECR y una task definition de ECS utiliza esa imagen durante el despliegue.

> **Logo** `recursos/aws/otros/elastic-container-registry.svg`

> **Idea visual**  
> Repositorio ECR con varias versiones de una imagen y una flecha `pull` hacia una task ECS.

## Sesión 12.2 — Amazon ECS

### Slide 1 — Amazon ECS

**Título en slide**

AMAZON ECS

#### Nombres en portal y examen

> **Amazon Elastic Container Service (Amazon ECS)**  
> **Cluster** / **Clúster**  
> **Task**  
> **Service**

#### Conceptos

- **Amazon ECS** orquesta contenedores mediante un modelo propio de AWS sin necesidad de implementar Kubernetes.
- Un **ECS cluster** agrupa de forma lógica las tasks y puede utilizar EC2, AWS Fargate o diferentes capacity providers.
- El modelo habitual sigue **ECR → task definition → task → service** cuando la aplicación debe permanecer en ejecución.
- Si el escenario exige **Kubernetes**, Helm o compatibilidad con sus APIs y herramientas, Amazon EKS suele ser la opción adecuada.

> **Ejemplo**  
> Una API REST empaquetada en contenedores se ejecuta como un ECS service detrás de un Application Load Balancer.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Plano de control ECS administrado por AWS con varias tasks debajo y una flecha desde Amazon ECR.

### Slide 2 — Task definition y task

**Título en slide**

TASK DEFINITION Y TASK

#### Nombres en portal y examen

> **Task definition** / **Definición de tarea**  
> **Task**  
> **Container** / **Contenedor**

#### Conceptos

- Una **task definition** describe cómo ejecutar la aplicación e incluye imagen, CPU, memoria, red, variables, volúmenes, logging y roles IAM.
- Cada cambio genera una nueva revisión y una **task** representa una instancia en ejecución de una de esas revisiones.
- Una task puede contener varios contenedores que deben ejecutarse juntos, por ejemplo una aplicación acompañada por un sidecar.
- La **task** es la unidad que se ejecuta, mientras el **service** mantiene una cantidad determinada de tasks funcionando.

> **Nota**  
> En Fargate debes utilizar combinaciones admitidas de CPU y memoria. Por ejemplo, **0,25 vCPU** admite **512 MiB, 1 GB o 2 GB** de memoria.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> `Task definition v3` → tres tasks idénticas distribuidas entre diferentes Availability Zones.

### Slide 3 — ECS Service

**Título en slide**

ECS SERVICE

#### Nombres en portal y examen

> **ECS service**  
> **Desired count** / **Número deseado**

#### Conceptos

- Un **ECS service** mantiene aplicaciones de larga duración funcionando y reemplaza automáticamente las tasks que fallen.
- El **desired count** define cuántas tasks deben ejecutarse simultáneamente y ECS trabaja para mantener ese número.
- El service puede registrar sus tasks en un target group de un Application Load Balancer o Network Load Balancer.
- Un service encaja en aplicaciones continuas, mientras un proceso con inicio y fin puede utilizar una task independiente o AWS Batch.

> **Ejemplo**  
> Una tienda online utiliza un service con `desired count = 4` distribuido entre dos Availability Zones.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

> **Idea visual**  
> Service con varias tasks saludables y una task fallida siendo reemplazada automáticamente.

## Sesión 12.3 — Tipo de lanzamiento

### Slide 1 — ECS con EC2

**Título en slide**

ECS CON EC2

#### Nombres en portal y examen

> **EC2 launch type**  
> **ECS container agent**  
> **Capacity provider**

#### Conceptos

- Con **EC2 launch type**, las tasks se ejecutan sobre instancias EC2 que forman parte del clúster.
- El **ECS container agent** conecta cada instancia con ECS, recibe las tasks y reporta su estado.
- La organización administra sistema operativo, parches, tipos de instancia y capacidad disponible en los hosts.
- El escalado puede ocurrir en dos niveles porque pueden aumentar las tasks y también las instancias EC2 cuando falta capacidad.

> **Nota**  
> Un capacity provider puede asociar el clúster con un Auto Scaling Group para gestionar mejor la capacidad EC2.

> **Ejemplo**  
> ECS sobre EC2 encaja cuando necesitas mayor control del host, tipos de instancia específicos o capacidad EC2 ya comprometida.

> **Logo** `recursos/aws/otros/elastic-container-service.svg`

### Slide 2 — ECS con Fargate

**Título en slide**

ECS CON FARGATE

#### Nombres en portal y examen

> **AWS Fargate**  
> **Fargate launch type**  
> **awsvpc**

#### Conceptos

- **AWS Fargate** ejecuta tasks sin que tengas que aprovisionar, administrar ni parchear instancias EC2.
- Defines CPU y memoria para la task y AWS administra la infraestructura subyacente donde se ejecutan los contenedores.
- Las tasks Fargate requieren `awsvpc`, reciben su propia ENI y pueden tener security groups aplicados directamente.
- Fargate puede utilizarse con **Amazon ECS y Amazon EKS**, por lo que representa una opción de cómputo y no un orquestador.

> **Nota**  
> En ECS Fargate sobre Linux, platform version **1.4.0 o posterior** incluye **20 GiB** de almacenamiento efímero por defecto y puede ampliarse hasta **200 GiB**.

> **Ejemplo**  
> Un equipo pequeño ejecuta una API en ECS con Fargate cuando su prioridad es reducir la administración de infraestructura.

> **Idea visual**

### Slide 3 — Precio EC2 frente a Fargate

**Título en slide**

EC2 VS FARGATE

#### Nombres en portal y examen

> **EC2 launch type**  
> **Fargate launch type**  
> **Compute Savings Plans**

#### Conceptos

- Con **EC2 launch type** pagas las instancias EC2 utilizadas por el clúster y recursos asociados como EBS cuando corresponda.
- Con **Fargate** pagas principalmente la vCPU y memoria configuradas para las tasks durante su ejecución.
- Los **Compute Savings Plans** pueden aplicar tanto a determinados usos de EC2 como de Fargate.
- EC2 puede resultar conveniente con cargas estables y alta utilización, mientras Fargate reduce operación. Ninguno es siempre más barato.

## Sesión 12.4 — Servicio en producción

### Slide 1 — Application Load Balancer y ECS

**Título en slide**

ALB CON AMAZON ECS

#### Nombres en portal y examen

> **Application Load Balancer**  
> **Dynamic port mapping** / **Mapeo dinámico de puertos**  
> **Target group** / **Grupo de destino**

#### Conceptos

- Un **Application Load Balancer** distribuye tráfico HTTP y HTTPS entre las tasks de un ECS service mediante un target group.
- Con ECS sobre EC2 en modo `bridge`, el dynamic host port mapping permite utilizar distintos puertos del host para contenedores iguales.
- Las tasks Fargate utilizan `awsvpc` y cada una dispone de su propia ENI e IP dentro de la VPC.
- Los health checks permiten dejar de enviar tráfico a tasks no saludables mientras ECS puede reemplazarlas.

> **Nota**  
> Para HTTP y HTTPS el ALB suele ser la opción habitual. NLB encaja cuando el escenario requiere características de capa 4.

> **Logo** `recursos/aws/networking/elb.svg`

> **Idea visual**  
> Application Load Balancer en 443 conectado a varias tasks ECS. Mostrar EC2 con puertos dinámicos y Fargate con ENI propia.

### Slide 2 — ECS Service Auto Scaling

**Título en slide**

ECS SERVICE AUTO SCALING

#### Nombres en portal y examen

> **ECS Service Auto Scaling**  
> **AWS Application Auto Scaling**  
> **Target tracking**

#### Conceptos

- **ECS Service Auto Scaling** aumenta o reduce automáticamente el desired count cuando cambia la demanda.
- Las políticas pueden utilizar métricas como CPU promedio, memoria promedio o **ALBRequestCountPerTarget**.
- **Target tracking** mantiene una métrica cerca de un objetivo y suele ser la política más sencilla para escalar un service.
- Con ECS sobre EC2 debes distinguir el escalado de las **tasks** del escalado de las **instancias EC2** del clúster.

> **Nota**  
> Amazon ECS publica métricas de CPU y memoria promedio del service en CloudWatch.

> **Ejemplo**  
> Si aumenta la CPU promedio del service, Application Auto Scaling puede incrementar el desired count.

### Slide 3 — Amazon ECS con EFS

**Título en slide**

AMAZON ECS CON EFS

#### Nombres en portal y examen

> **Amazon Elastic File System (Amazon EFS)**  
> **EFS access point**  
> **Persistent shared storage**

#### Conceptos

- **Amazon EFS** proporciona almacenamiento de archivos persistente y compartido para múltiples tasks.
- La task definition puede declarar EFS como volumen y las tasks pueden acceder a los mismos datos aunque se ejecuten en hosts distintos.
- EFS funciona con ECS sobre EC2 y con Fargate Linux desde platform version **1.4.0 o posterior**.
- Los EFS access points pueden limitar el directorio visible y aplicar identidades específicas para cada aplicación.

> **Nota**  
> Cuando varios contenedores necesitan un filesystem compartido, EFS es el patrón natural frente a tratar S3 como un disco tradicional.

### Slide 4 — Throughput de Amazon EFS

**Título en slide**

EFS Y THROUGHPUT

#### Nombres en portal y examen

> **Elastic Throughput**  
> **Provisioned Throughput**  
> **Bursting Throughput**

#### Conceptos

- **Elastic Throughput** se adapta automáticamente y AWS lo recomienda para workloads impredecibles o con picos.
- **Provisioned Throughput** permite configurar rendimiento independientemente del tamaño almacenado cuando conoces la necesidad de throughput.
- **Bursting Throughput** vincula el rendimiento al tamaño del sistema de archivos y utiliza burst credits cuando supera su baseline.
- El modo adecuado depende del patrón de acceso, por lo que no existe un único throughput mode correcto para todos los workloads.

> **Nota**  
> El banco incluye una pregunta donde **Provisioned Throughput** es la respuesta para alto volumen de lecturas y escrituras con un filesystem relativamente pequeño.

> **Logo** `recursos/aws/storage/efs.svg`

> **Idea visual**  
> Tres tarjetas `Elastic`, `Provisioned`, `Bursting` con diferentes patrones de carga.

## Sesión 12.5 — IAM en ECS

### Slide 1 — Roles IAM en ECS

**Título en slide**

ROLES IAM EN ECS

#### Nombres en portal y examen

> **Task role**  
> **Task execution role**  
> **Container instance role**

#### Conceptos

- El **task role** entrega permisos al código dentro del contenedor para acceder a servicios AWS como S3 o SQS.
- El **task execution role** permite a ECS realizar acciones de inicio como descargar imágenes privadas de ECR, enviar logs o recuperar secretos.
- El **container instance role** se utiliza con ECS sobre EC2 para que la instancia y el ECS container agent interactúen con AWS.
- Para aplicar mínimo privilegio, cada aplicación puede recibir su propio task role sin depender de credenciales estáticas o del rol del host.

> **Nota**  
> Los permisos del task execution role no están disponibles directamente para la aplicación dentro del contenedor.

> **Ejemplo**  
> Una task utiliza su task role para escribir en S3 y su execution role para descargar una imagen privada desde ECR.

> **Logo** `recursos/aws/otros/iam.svg`

> **Idea visual**  
> `Container instance role → EC2`, `Execution role → arranque`, `Task role → aplicación`.

## Sesión 12.6 — Lotes y programación

### Slide 1 — AWS Batch

**Título en slide**

AWS BATCH

#### Nombres en portal y examen

> **AWS Batch**  
> **Batch job** / **Trabajo por lotes**  
> **Job queue**  
> **Compute environment**

#### Conceptos

- **AWS Batch** administra trabajos con inicio y fin como simulaciones, renderizado, procesamiento científico o ETL intensivo.
- El workload se empaqueta como una imagen de contenedor y se envía como un job a una **job queue**.
- La cola se conecta con compute environments que pueden utilizar opciones como EC2, Spot o Fargate según el diseño.
- A diferencia de un ECS service, un job termina cuando completa su procesamiento y no necesita permanecer activo permanentemente.

> **Nota**  
> En una job queue Fargate no puedes mezclar compute environments EC2 y Fargate dentro de la misma cola.

> **Ejemplo**  
> Miles de simulaciones nocturnas se envían a una job queue y AWS Batch ejecuta los contenedores conforme existe capacidad.

> **Logo** `recursos/aws/compute/batch.svg`

> **Idea visual**  
> Job queue → compute environment → varios contenedores → `exit`.

> **Amazon EKS Anywhere**  
> **Amazon EKS Distro**

#### Conceptos

- **Amazon EKS** ejecuta Kubernetes administrado en AWS, mientras **EKS Anywhere** permite operar clústeres Kubernetes sobre infraestructura propia.

## Sesión 12.9 — Arquitecturas

### Slide 1 — Fargate detrás del ALB

**Título en slide**

FARGATE DETRÁS DEL ALB

#### Conceptos

- El **Application Load Balancer** distribuye tráfico hacia las tasks Fargate registradas en el target group del ECS service.
- Las tasks se distribuyen entre diferentes Availability Zones sin que el usuario tenga que administrar instancias EC2.
- Las imágenes proceden de **Amazon ECR** y los permisos se separan mediante task execution role y task role.
- Si la aplicación necesita archivos persistentes y compartidos, las tasks pueden montar **Amazon EFS**.

> **Nota**  
> ECR participa cuando se inicia o actualiza una task, pero no está en el camino de cada solicitud HTTP del usuario.
