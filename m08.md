## Sesión 8.1 — Registros y zonas

### Slide 1 — Amazon Route 53

**Título en slide**

AMAZON ROUTE 53

#### Nombres en portal y examen

> **Amazon Route 53** — **Domain Name System (DNS)** — **authoritative DNS**

#### Conceptos

- **Amazon Route 53** traduce nombres como `www.tienda.com` hacia los destinos donde realmente vive una aplicación.
- Actúa como DNS autoritativo cuando los name servers del dominio delegan esa zona hacia Route 53.
- Puede responder con direcciones IP o con destinos AWS mediante registros Alias.
- También ofrece routing policies y health checks para decidir qué respuesta DNS entregar.
- Route 53 responde consultas DNS, pero no transporta las solicitudes HTTP como lo hace un load balancer.

> **Nota**  
> El `53` del nombre hace referencia al puerto tradicional utilizado por DNS. El data plane de Route 53 Authoritative DNS dispone de un SLA de disponibilidad del 100 %.

**Docs**  
[What is Amazon Route 53?](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/Welcome.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Usuario escribe `www.tienda.com` → resolver DNS → icono oficial de **Amazon Route 53** → respuesta con una IP o un destino AWS. Después el cliente conecta directamente con ese destino.

### Slide 2 — Hosted Zone

**Título en slide**

HOSTED ZONE

#### Nombres en portal y examen

> **Hosted zone** — **public hosted zone** — **private hosted zone**

#### Conceptos

- Una **hosted zone** contiene los registros DNS de un dominio y sus subdominios.
- Una **public hosted zone** responde consultas desde Internet.
- Una **private hosted zone** responde únicamente dentro de las VPC asociadas.
- Una private hosted zone puede asociarse a más de una VPC.
- Puedes utilizar el mismo dominio en una zona pública y otra privada para implementar **split-view DNS**.

> **Ejemplo**  
> Desde Internet, `api.empresa.com` puede resolver hacia un endpoint público. Dentro de una VPC, el mismo nombre puede resolver hacia una dirección privada si existe una private hosted zone correspondiente.

> **Nota**  
> Las public y private hosted zones siguen siendo zonas distintas aunque utilicen el mismo namespace.

**Docs**  
[Working with public hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/AboutHZWorkingWith.html)  
[Working with private hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zones-private.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Dos cajas con el mismo dominio. `Public Hosted Zone` responde desde Internet. `Private Hosted Zone` responde dentro de una VPC. El segundo camino termina en una IP privada.

### Slide 3 — Registro DNS

**Título en slide**

REGISTRO DNS

#### Nombres en portal y examen

> **DNS record** — **routing policy** — **TTL**

#### Conceptos

- El **record name** identifica el dominio o subdominio que quieres resolver.
- El **record type** define qué clase de información entrega el registro.
- El valor contiene la dirección o destino correspondiente.
- La **routing policy** determina cómo Route 53 selecciona una respuesta cuando existen varios destinos.
- El **TTL** controla cuánto tiempo puede conservarse una respuesta en caché antes de volver a consultar DNS.

> **Nota**  
> Route 53 decide qué respuesta DNS entregar. Un load balancer decide posteriormente a qué target enviar una conexión o solicitud.

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Una ficha visual contiene `Name`, `Type`, `Value`, `Routing Policy` y `TTL`. Al lado, una comparación pequeña muestra `Route 53 → respuesta DNS` y `ELB → tráfico`.

### Slide 4 — A, AAAA y CNAME

**Título en slide**

A — AAAA — CNAME

#### Nombres en portal y examen

> **A record** — **AAAA record** — **CNAME record**

#### Conceptos

- Un registro **A** resuelve un nombre hacia una dirección **IPv4**.
- Un registro **AAAA** resuelve un nombre hacia una dirección **IPv6**.
- Un **CNAME** hace que un nombre resuelva mediante otro hostname.
- Un CNAME puede utilizarse en un subdominio como `www.tienda.com`, pero no en el **zone apex** `tienda.com`.
- El nombre al que apunta el CNAME puede estar en Route 53 o en otro proveedor DNS.

> **Nota**  
> Un subdominio puede utilizar CNAME hacia el DNS público de una EC2, pero ese hostname puede cambiar cuando cambia la IPv4 pública. Para un endpoint estable suele ser preferible una Elastic IP con registro A o un load balancer con Alias.

**Docs**  
[Supported DNS record types](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/ResourceRecordTypes.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `api.example.com → A → IPv4`.  
> `api6.example.com → AAAA → IPv6`.  
> `www.example.com → CNAME → app.proveedor.com`.  
> `example.com → CNAME` aparece tachado.

### Slide 5 — TTL

**Título en slide**

TTL

#### Nombres en portal y examen

> **Time to Live (TTL)**

#### Conceptos

- El **TTL** indica durante cuánto tiempo un resolver puede reutilizar una respuesta DNS almacenada en caché.
- Un TTL alto reduce la frecuencia con la que los resolvers vuelven a consultar Route 53.
- A cambio, un cambio de destino puede tardar más en ser visible para clientes que todavía conservan la respuesta anterior.
- Un TTL bajo permite que los cambios se reflejen antes, pero aumenta el número potencial de consultas DNS.
- Antes de una migración planificada puede reducirse el TTL con anticipación para disminuir el tiempo que permanece una respuesta antigua en caché.

> **Nota**  
> En un Alias hacia determinados recursos AWS no defines manualmente el TTL. Route 53 utiliza el comportamiento del recurso Alias target.

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `TTL 86400` muestra una respuesta almacenada durante mucho tiempo. `TTL 60` muestra al resolver consultando Route 53 con mayor frecuencia.

### Slide 6 — Alias Record

**Título en slide**

ALIAS RECORD

#### Nombres en portal y examen

> **Alias record** — **zone apex**

#### Conceptos

- Un **Alias record** es una extensión de Route 53 que puede apuntar hacia determinados recursos AWS o hacia otro registro de la misma hosted zone.
- A diferencia de CNAME, un Alias puede utilizarse en el **zone apex**.
- Un Alias hacia un recurso AWS sigue el destino aunque AWS cambie las direcciones IP que existen detrás de él.
- Las consultas Alias dirigidas a recursos AWS compatibles no generan el cargo estándar por consulta Alias.
- Para recursos AWS como ALB, CloudFront o API Gateway, el Alias se crea normalmente como registro A y, cuando corresponde, también AAAA.

> **Nota**  
> Un Alias no está limitado universalmente a A o AAAA. Cuando apunta hacia otro registro de la misma hosted zone debe utilizar un tipo compatible con ese registro. Un Alias en el zone apex no puede apuntar hacia un registro CNAME.

**Docs**  
[Choosing between alias and non-alias records](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-choosing-alias-non-alias.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `example.com` → **Alias** → ALB aparece con ✓.  
> `example.com` → CNAME aparece con ✗.

### Slide 7 — Destinos de Alias

**Título en slide**

DESTINOS DE ALIAS

#### Conceptos

- Un Alias puede apuntar hacia **Elastic Load Balancing**, Amazon CloudFront, Amazon API Gateway y otros recursos AWS compatibles.
- También puede apuntar hacia un bucket Amazon S3 configurado como **website endpoint**.
- AWS Global Accelerator, determinados VPC interface endpoints y otros servicios también pueden utilizarse como Alias targets.
- Otro registro dentro de la misma Route 53 hosted zone también puede funcionar como destino.
- El DNS público de una instancia EC2 no es un Alias target válido.

> **Nota**  
> Si el requisito dice “dominio hacia un ALB”, piensa en Alias. Si necesitas una IP fija para una EC2, una Elastic IP permite utilizar un registro A estable.

**Docs**  
[Routing traffic to AWS resources](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-to-aws-resources.html)

> Route 53 Alias apunta con ✓ hacia ALB, CloudFront, API Gateway, S3 website y Global Accelerator. El DNS público de EC2 aparece con ✗.

## Sesión 8.2 — Políticas de enrutamiento

### Slide 1 — Simple Routing

**Título en slide**

SIMPLE ROUTING

#### Nombres en portal y examen

> **Simple routing policy**

#### Conceptos

- **Simple routing** se utiliza cuando no necesitas una lógica especial para seleccionar entre destinos.
- Normalmente se utiliza para enviar un nombre hacia un único recurso.
- Un registro no Alias puede contener varios valores, como varias direcciones IP.
- Si existen varios valores, Route 53 los devuelve al resolver en orden aleatorio.
- Simple routing no realiza health checking individual de esos valores.

> **Nota**  
> Un Alias con simple routing solo puede apuntar hacia un recurso AWS o hacia un registro compatible de la hosted zone.

**Docs**  
[Simple routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-simple.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Un nombre → un ALB. En pequeño, un registro A contiene tres IP y Route 53 devuelve las tres sin health checking individual.

### Slide 2 — Weighted Routing

**Título en slide**

WEIGHTED ROUTING

#### Nombres en portal y examen

> **Weighted routing policy** — **weight**

#### Conceptos

- **Weighted routing** reparte respuestas DNS entre varios recursos según pesos relativos.
- El porcentaje aproximado depende del peso de un registro dividido entre la suma de todos los pesos.
- Los pesos no necesitan sumar 100.
- Un registro con peso `0` queda fuera del reparto normal mientras existan registros con peso mayor que cero disponibles.
- Puede combinarse con health checks para evitar seleccionar recursos unhealthy.

> **Ejemplo**  
> Pesos `70`, `20` y `10` producen aproximadamente una distribución 70 %, 20 % y 10 %.

> **Nota**  
> Es útil para canary releases, blue-green y migraciones graduales. El reparto ocurre mediante DNS y no tiene la precisión por conexión de un load balancer.

**Docs**  
[Weighted routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-weighted.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Un dominio se divide hacia tres destinos marcados `70`, `20` y `10`.

### Slide 3 — Latency Routing

**Título en slide**

LATENCY ROUTING

#### Nombres en portal y examen

> **Latency-based routing policy**

#### Conceptos

- **Latency routing** dirige al usuario hacia la AWS Region que Route 53 estima que ofrece menor latencia.
- Debes tener recursos y latency records en más de una Region para que pueda comparar destinos.
- Las mediciones se basan en datos de latencia entre usuarios y la infraestructura AWS y pueden cambiar con el tiempo.
- Puede combinarse con health checks para evitar una Region cuyo destino está unhealthy.
- No utiliza fronteras políticas de países para tomar la decisión.

> **Nota**  
> Si el escenario pide **menor latencia**, piensa en Latency Routing. Si exige una regla según país o continente, piensa en Geolocation.

**Docs**  
[Latency-based routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-latency.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Usuario en Europa. Dos caminos llegan a `us-east-1` y `eu-west-1`. Route 53 elige el que muestra menor latencia.

### Slide 4 — Failover Routing

**Título en slide**

FAILOVER ROUTING

#### Nombres en portal y examen

> **Failover routing policy** — **primary** — **secondary**

#### Conceptos

- **Failover routing** implementa un patrón DNS activo-pasivo mediante un registro primary y otro secondary.
- Mientras el primary se considera healthy, Route 53 responde con ese destino.
- Cuando la señal de salud del primary falla, Route 53 puede empezar a responder con el secondary.
- Un registro no Alias puede asociarse a un Route 53 health check.
- En Alias targets compatibles como Elastic Load Balancing también puede utilizarse **Evaluate Target Health** para heredar la salud del recurso.

> **Nota**  
> Failover necesita una señal que permita conocer la salud del primary, pero no siempre requiere crear un health check de Route 53 independiente.

**Docs**  
[Failover routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-failover.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `Primary` recibe el tráfico normalmente. Cuando su health signal falla, Route 53 comienza a responder con `Secondary`.

### Slide 5 — Geolocation Routing

**Título en slide**

GEOLOCATION ROUTING

#### Nombres en portal y examen

> **Geolocation routing policy**

#### Conceptos

- **Geolocation routing** decide la respuesta según la ubicación geográfica de la consulta.
- Puedes crear reglas para continentes, países y estados de Estados Unidos.
- Cuando varias reglas coinciden, gana la ubicación más específica.
- Puedes crear un registro **Default** para consultas provenientes de lugares sin una regla correspondiente o cuya ubicación Route 53 no pueda identificar.
- Si no existe un Default y ninguna regla coincide, Route 53 puede responder sin ningún destino.

> **Nota**  
> AWS recomienda utilizar un Default salvo que quieras deliberadamente que determinados usuarios no obtengan respuesta.

**Docs**  
[Geolocation routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-geo.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> España → destino A. México → destino B. Los demás usuarios → `Default`.

### Slide 6 — Geoproximity Routing

**Título en slide**

GEOPROXIMITY ROUTING

#### Nombres en portal y examen

> **Geoproximity routing policy** — **bias**

#### Conceptos

- **Geoproximity routing** utiliza la ubicación de los usuarios y de los recursos para dirigir tráfico hacia el recurso geográficamente más cercano.
- Un **bias** positivo amplía la zona desde la que Route 53 dirige tráfico hacia un recurso.
- Un bias negativo reduce esa zona y desplaza tráfico hacia recursos vecinos.
- Los valores de bias van de `+1` a `+99` o de `-1` a `-99`.
- Para recursos que no están en AWS puedes indicar su posición mediante latitud y longitud.

> **Nota**  
> **Traffic Flow no es obligatorio para utilizar Geoproximity Routing.** Traffic Flow ofrece herramientas visuales, incluido el mapa para observar las regiones de influencia.

**Docs**  
[Geoproximity routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-geoproximity.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Dos recursos con áreas geográficas alrededor. Un `Bias +50` amplía una de las áreas y desplaza su frontera.

### Slide 7 — Multivalue Answer Routing

**Título en slide**

MULTIVALUE ANSWER ROUTING

#### Nombres en portal y examen

> **Multivalue answer routing policy**

#### Conceptos

- **Multivalue answer routing** permite que Route 53 devuelva hasta **8 registros** en una respuesta DNS.
- Cada registro puede asociarse a su propio health check.
- Route 53 devuelve únicamente registros healthy mientras exista al menos uno saludable.
- Diferentes resolvers pueden recibir diferentes conjuntos de respuestas.
- No sustituye a Elastic Load Balancing porque el cliente continúa eligiendo entre las direcciones recibidas.

> **Nota**  
> Si todos los registros están unhealthy, Route 53 entra en comportamiento fail-open y puede devolver hasta ocho registros unhealthy.

**Docs**  
[Multivalue answer routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-multivalue.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Ocho IP como máximo aparecen dentro de la respuesta. Una dirección unhealthy queda excluida mientras existan destinos healthy.

### Slide 8 — IP-Based Routing

**Título en slide**

IP-BASED ROUTING

#### Nombres en portal y examen

> **IP-based routing policy** — **CIDR collection** — **CIDR location**

#### Conceptos

- **IP-based routing** permite mapear rangos CIDR conocidos hacia destinos específicos.
- Las CIDR locations agrupan uno o varios rangos y se organizan dentro de una **CIDR collection**.
- Encaja cuando conoces los rangos de clientes, oficinas o ISPs y quieres controlar explícitamente hacia dónde enviarlos.
- Puede utilizarse para optimizar rendimiento o costes de tránsito de red.
- IP-based routing no está soportado para registros de una private hosted zone.

> **Nota**  
> Route 53 utiliza la información IP disponible en la consulta DNS. Si el resolver soporta EDNS Client Subnet puede utilizar una parte de la IP del usuario; en caso contrario, la decisión puede basarse en la IP del resolver DNS.

**Docs**  
[IP-based routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-ipbased.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `203.0.113.0/24 → Endpoint A`  
> `198.51.100.0/24 → Endpoint B`  
> Ambos rangos aparecen dentro de una `CIDR Collection`.

## Sesión 8.3 — Health Checks

### Slide 1 — Route 53 Health Check

**Título en slide**

ROUTE 53 HEALTH CHECK

#### Nombres en portal y examen

> **Route 53 health check** — **health checker**

#### Conceptos

- Route 53 puede comprobar directamente endpoints públicos mediante **HTTP, HTTPS o TCP**.
- Para HTTP y HTTPS, una respuesta `2xx` o `3xx` indica éxito en una comprobación básica.
- El intervalo puede configurarse normalmente en **30 segundos** o, con coste adicional, **10 segundos**.
- El failure threshold predeterminado es de **3 comprobaciones consecutivas**.
- Route 53 combina los resultados de health checkers distribuidos globalmente para decidir el estado final.

> **Nota**  
> Un endpoint que solo utiliza una dirección privada dentro de una VPC no puede recibir directamente estos health checks desde Internet.

**Docs**  
[Creating and updating health checks](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-creating-values.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Varios health checkers globales envían solicitudes hacia un endpoint público. El resultado agregado termina en `Healthy` o `Unhealthy`.

### Slide 2 — Health Check con CloudWatch

**Título en slide**

HEALTH CHECK PARA RECURSOS PRIVADOS

#### Nombres en portal y examen

> **CloudWatch alarm health check**

#### Conceptos

- Los health checkers públicos de Route 53 no pueden comprobar directamente una IP privada.
- Para un recurso privado puedes crear una métrica que represente su salud y evaluarla mediante una **CloudWatch alarm**.
- Route 53 puede crear un health check cuyo estado depende directamente de esa alarma.
- Este patrón permite utilizar señales como errores, conexiones o métricas personalizadas para influir en routing policies.

> **Ejemplo**  
> Una base de datos privada genera una métrica de aplicación. CloudWatch evalúa esa métrica y Route 53 utiliza el estado de la alarma como señal de salud.

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Recurso privado dentro de una VPC → métrica → CloudWatch Alarm → Route 53 Health Check. El health checker público directo hacia la IP privada aparece tachado.

---

### Slide 3 — Calculated Health Check

**Título en slide**

CALCULATED HEALTH CHECK

#### Nombres en portal y examen

> **Calculated health check** — **child health checks**

#### Conceptos

- Un **calculated health check** determina su estado utilizando otros health checks como hijos.
- Puedes definir cuántos child health checks deben estar healthy para considerar healthy al check calculado.
- Permite representar la salud agregada de varios componentes mediante una sola señal.
- Puede utilizarse para evitar que el fallo de un único componente marque como unhealthy a todo un sistema.

> **Nota**  
> Un calculated health check y un health check basado en una CloudWatch alarm son tipos distintos. Pueden formar parte del mismo diseño, pero uno no sustituye automáticamente al otro.

**Docs**  
[Creating and updating health checks](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-creating-values.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Tres child health checks llegan a una caja `Calculated Health Check`. Dos están healthy y uno unhealthy. La regla indica `2 of 3 = Healthy`.

## Sesión 8.4 — Zona privada y Resolver

### Slide 1 — Private Hosted Zone

**Título en slide**

PRIVATE HOSTED ZONE

#### Nombres en portal y examen

> **Private hosted zone** — **DNS resolution** — **DNS hostnames**

#### Conceptos

- Una **private hosted zone** permite resolver nombres únicamente desde las VPC asociadas.
- Puede utilizar nombres como `db.empresa.internal` o incluso el mismo dominio que utiliza una public hosted zone.
- La VPC debe tener `enableDnsSupport` y `enableDnsHostnames` habilitados.
- **Route 53 VPC Resolver** responde las consultas realizadas desde los recursos de la VPC.
- Los registros privados no se publican hacia Internet.

> **Nota**  
> Public y private hosted zones con el mismo dominio permiten implementar split-view DNS. Desde la VPC se utiliza la información privada correspondiente al namespace asociado.

**Docs**  
[Considerations when working with private hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zone-private-considerations.html)

> **Idea visual**  
> Una EC2 dentro de una VPC consulta `db.empresa.internal` y Route 53 VPC Resolver responde con `10.0.2.25`. Desde Internet el mismo registro no existe.

### Slide 2 — DNS híbrido

**Título en slide**

DNS HÍBRIDO

#### Nombres en portal y examen

> **Route 53 VPC Resolver** — **hybrid DNS**

#### Conceptos

- Route 53 VPC Resolver permite integrar la resolución DNS de AWS con servidores DNS de una red on-premises.
- Una conexión privada como AWS Site-to-Site VPN o AWS Direct Connect transporta las consultas entre ambas redes.
- Un **inbound endpoint** permite que consultas DNS de tu red entren hacia Resolver.
- Un **outbound endpoint** permite que Resolver envíe determinadas consultas hacia servidores DNS de tu red.
- La dirección se determina pensando en hacia dónde viaja la consulta desde la perspectiva de AWS.

> **Nota**  
> On-premises quiere resolver nombres de AWS → **Inbound**.  
> AWS quiere resolver nombres on-premises → **Outbound**.

**Docs**  
[What is Route 53 VPC Resolver?](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> VPC ↔ VPN o Direct Connect ↔ datacenter. Dos flechas muestran `Inbound` y `Outbound` en sentidos opuestos.

### Slide 3 — Resolver Inbound Endpoint

**Título en slide**

RESOLVER INBOUND ENDPOINT

#### Conceptos

- Un **inbound endpoint** recibe consultas provenientes de DNS resolvers que están fuera de la VPC.
- El DNS on-premises puede reenviar hacia él consultas sobre private hosted zones o nombres resolubles desde AWS.
- El endpoint utiliza interfaces de red dentro de la VPC.
- La respuesta vuelve hacia la red on-premises mediante la conectividad privada existente.

> **Ejemplo**  
> Un servidor on-premises necesita resolver `api.aws.private` que existe en una Route 53 private hosted zone.

### Slide 4 — Resolver Outbound Endpoint

**Título en slide**

RESOLVER OUTBOUND ENDPOINT

#### Nombres en portal y examen

> **Resolver outbound endpoint** — **forwarding rule**

#### Conceptos

- Un **outbound endpoint** permite que Route 53 VPC Resolver envíe consultas hacia servidores DNS de otra red.
- Una **forwarding rule** indica qué dominio debe reenviarse y cuáles son las IP de los DNS que conocen ese namespace.
- La regla se asocia a las VPC desde las que debe aplicarse.
- Las demás consultas continúan resolviéndose normalmente mediante Route 53 VPC Resolver.

> **Ejemplo**  
> Una EC2 consulta `legacy.empresa.local`. La forwarding rule envía esa consulta mediante el outbound endpoint hacia el DNS del datacenter.

**Docs**  
[Forwarding outbound DNS queries](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver-forwarding-outbound-queries.html)

### Slide 5 — Registrar y DNS

**Título en slide**

REGISTRAR VS DNS

#### Nombres en portal y examen

> **Domain registrar** — **authoritative DNS**

#### Conceptos

- El **registrar** administra el registro y renovación del nombre de dominio.
- El servicio DNS autoritativo administra los registros que determinan cómo ese dominio se resuelve.
- Puedes registrar un dominio fuera de AWS y utilizar Route 53 como DNS.

- No necesitas transferir la propiedad del dominio hacia AWS para utilizar Route 53.

## Sesión 8.5 — Arquitecturas

### Slide 1 — Failover DNS

**Título en slide**

ARQUITECTURA, FAILOVER DNS

#### Conceptos

- Un nombre público utiliza **Failover Routing** con un destino primary y otro secondary.
- El primary apunta mediante Alias al Application Load Balancer de la Region principal.
- El secondary apunta hacia un stack preparado en otra AWS Region.
- Para un ALB, **Evaluate Target Health** puede permitir que Route 53 utilice la salud del load balancer como señal.
- Cuando el primary deja de considerarse healthy, Route 53 empieza a responder con el secondary.

> **Nota**  
> Route 53 cambia la respuesta DNS. No crea automáticamente la infraestructura secundaria ni replica sus datos.

> **Idea visual**
>
> 1. Fondo con líneas punteadas `Primary Region | Secondary Region`.
> 2. Usuario consulta el icono oficial de **Amazon Route 53**.
> 3. `Primary Alias` apunta al ALB de la Region primaria.
> 4. Sobre el primary aparece `Evaluate Target Health`.
> 5. `Secondary Alias` apunta al ALB de la Region secundaria.
> 6. Con primary healthy, la flecha sólida termina allí.
> 7. Con primary unhealthy, la flecha sólida cambia hacia secondary.
