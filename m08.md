## Sesión 8.1 — Registros y zonas

### Slide 1 — Amazon Route 53

**Título en slide**

AMAZON ROUTE 53

#### Nombres en portal y examen

> **Amazon Route 53**  
> **Domain Name System (DNS)** / **Sistema de nombres de dominio**  
> **Authoritative DNS** / **DNS autoritativo**

#### Conceptos

- **Amazon Route 53** traduce nombres como `www.tienda.com` hacia direcciones IP o destinos de una aplicación.
- Es un servicio DNS autoritativo, altamente disponible y escalable.
- Es la fuente de verdad del dominio cuando los registros NS delegan la zona hacia Route 53.
- También puede registrar dominios, aunque registrador y servicio DNS cumplen funciones distintas.
- Route 53 Authoritative DNS tiene un compromiso de disponibilidad mensual del **100 %**.
- El nombre Route 53 hace referencia al **puerto 53** utilizado por DNS.

> **Nota**  
> Route 53 responde consultas DNS. No distribuye solicitudes HTTP como un Application Load Balancer.

**Docs**  
[What is Amazon Route 53?](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/Welcome.html)  
[Amazon Route 53 SLA](https://aws.amazon.com/route53/sla/)

> Usuario escribe `www.tienda.com` → Resolver DNS → Amazon Route 53 → respuesta con IP o recurso AWS. Añadir una etiqueta pequeña `DNS · puerto 53`.

### Slide 2 — Hosted Zone

**Título en slide**

HOSTED ZONE

#### Nombres en portal y examen

> **Hosted zone** / **Zona alojada**  
> **Public hosted zone** / **Zona alojada pública**  
> **Private hosted zone** / **Zona alojada privada**

#### Conceptos

- Una **hosted zone** contiene los registros DNS de un dominio y sus subdominios.
- Una **public hosted zone** responde consultas desde internet.
- Una **private hosted zone** responde dentro de las VPC asociadas.
- Puedes tener una zona pública y otra privada con el mismo dominio para implementar **split-view DNS**.
- Las primeras **25 hosted zones** cuestan actualmente **0,50 USD al mes cada una**. Las adicionales cuestan **0,10 USD al mes**.
- Cada hosted zone incluye hasta **10 000 registros** antes del cargo adicional por registro.

> **Nota**  
> Los precios pueden cambiar. Contrastarlos nuevamente antes de publicar o grabar el curso.

**Docs**  
[Working with public hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/AboutHZWorkingWith.html)  
[Working with private hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zones-private.html)  
[Amazon Route 53 pricing](https://aws.amazon.com/route53/pricing/)

### Slide 3 — Registro DNS

**Título en slide**

REGISTRO DNS

#### Nombres en portal y examen

> **DNS record** / **Registro DNS**  
> **Routing policy** / **Política de enrutamiento**  
> **Time to Live (TTL)** / **Tiempo de vida**

#### Conceptos

- El **nombre** identifica el dominio o subdominio, por ejemplo `api.tienda.com`.
- El **tipo** define la información entregada, como A, AAAA, CNAME o NS.
- El **valor** contiene la dirección IP, hostname o información correspondiente.
- La **routing policy** decide qué respuesta entregar cuando existen varios destinos.
- El **TTL** indica cuántos segundos un resolver conserva la respuesta en caché.
- **Alias** no es un tipo DNS independiente, sino una extensión de Route 53.

> **Nota**  
> Route 53 selecciona respuestas DNS. Elastic Load Balancing distribuye el tráfico después.

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Ficha con `Name`, `Type`, `Value`, `Routing Policy` y `TTL`. Al lado `Route 53 → DNS` frente a `ELB → tráfico`.

### Slide 4 — A, AAAA y CNAME

**Título en slide**

A, AAAA Y CNAME

#### Nombres en portal y examen

> **A record** / **Registro A**  
> **AAAA record** / **Registro AAAA**  
> **CNAME record** / **Registro CNAME**

#### Conceptos

- Un registro **A** resuelve un nombre hacia una dirección **IPv4**.
- Un registro **AAAA** resuelve un nombre hacia una dirección **IPv6**.
- Un **CNAME** hace que un nombre resuelva mediante otro hostname.
- CNAME puede utilizarse en `www.tienda.com`, pero no en el **zone apex** `tienda.com`.
- El hostname de destino puede pertenecer a AWS o a otro proveedor.
- Un subdominio puede usar CNAME hacia el DNS público de una EC2.

> **Nota**  
> Si una EC2 necesita una dirección pública estable, utiliza una Elastic IP o coloca un load balancer delante cuando corresponda.

**Docs**  
[Supported DNS record types](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/ResourceRecordTypes.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `api.example.com → A → IPv4`  
> `api6.example.com → AAAA → IPv6`  
> `www.example.com → CNAME → app.proveedor.com`  
> `example.com → CNAME` aparece tachado.

### Slide 5 — TTL

**Título en slide**

TTL

#### Nombres en portal y examen

> **Time to Live (TTL)** / **Tiempo de vida**

#### Conceptos

- El **TTL** indica cuánto tiempo puede reutilizarse una respuesta DNS almacenada en caché.
- Un TTL de **86 400 s, 24 horas**, reduce consultas, pero conserva respuestas antiguas durante más tiempo.
- Un TTL de **60 s** permite observar cambios antes, a cambio de más consultas DNS.
- Antes de una migración planificada puedes reducir el TTL con anticipación.
- En determinados registros Alias no defines manualmente el TTL.

> **Nota**  
> Un TTL bajo no garantiza un cambio instantáneo. Los resolvers conservan la respuesta hasta que expire.

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `TTL 86 400 s → menos consultas, caché más larga`  
> `TTL 60 s → más consultas, cambios más rápidos`

### Slide 6 — Alias Record

**Título en slide**

ALIAS RECORD

#### Nombres en portal y examen

> **Alias record** / **Registro Alias**  
> **Zone apex** / **Ápice de la zona**

#### Conceptos

- Un **Alias record** puede apuntar hacia determinados recursos AWS.
- También puede apuntar hacia otro registro compatible de la misma hosted zone.
- A diferencia de CNAME, Alias puede utilizarse en el **zone apex**.
- Para recursos AWS habituales se crea normalmente como **A** y, cuando corresponde, también **AAAA**.
- Las consultas Alias hacia recursos AWS compatibles no tienen el cargo estándar por consulta.
- Un Alias en el zone apex no puede apuntar hacia un registro CNAME.

> **Nota**  
> Alias no permite utilizar cualquier hostname como destino. El recurso debe ser compatible con Route 53.

**Docs**  
[Choosing between alias and non-alias records](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-choosing-alias-non-alias.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `example.com → Alias → ALB` aparece con ✓.  
> `example.com → CNAME` aparece con ✗.

### Slide 7 — Destinos de Alias

**Título en slide**

DESTINOS DE ALIAS

#### Nombres en portal y examen

> **Alias target** / **Destino de Alias**

#### Conceptos

- Alias puede apuntar hacia **Elastic Load Balancing**, Amazon CloudFront y Amazon API Gateway.
- También admite buckets Amazon S3 configurados como **website endpoint**.
- Otros destinos incluyen Global Accelerator, VPC interface endpoints y Elastic Beanstalk.
- Puede apuntar hacia otro registro compatible dentro de la misma hosted zone.
- El DNS público de una instancia EC2 no es un Alias target válido.
- Route 53 sigue el recurso AWS aunque cambien sus direcciones IP.

> **Nota**  
> Si el enunciado dice “dominio hacia un ALB”, piensa en Alias.

## Sesión 8.2 — Políticas de enrutamiento

### Slide 1 — Simple Routing

**Título en slide**

SIMPLE ROUTING

#### Nombres en portal y examen

> **Simple routing policy** / **Política de enrutamiento simple**

#### Conceptos

- **Simple routing** se utiliza cuando no necesitas lógica especial para elegir destinos.
- Normalmente envía un nombre hacia un único recurso.
- Un registro no Alias puede contener varias direcciones IP.
- Si existen varios valores, Route 53 los devuelve en orden aleatorio.
- Un Alias con simple routing solo puede apuntar hacia **1 destino**.
- No realiza health checking individual de los valores.

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Un nombre → un ALB. En pequeño, un registro A con varias IP y la nota `sin health check individual`.

### Slide 2 — Weighted Routing

**Título en slide**

WEIGHTED ROUTING

#### Nombres en portal y examen

> **Weighted routing policy** / **Política de enrutamiento ponderada**  
> **Weight** / **Peso**

#### Conceptos

- **Weighted routing** reparte respuestas DNS según pesos relativos.
- El peso admite valores enteros entre **0 y 255**.
- El porcentaje aproximado depende del peso dividido entre la suma de todos los pesos.
- Los pesos no necesitan sumar **100**.
- Un peso `0` queda fuera mientras existan registros elegibles con peso mayor que cero.
- Puede combinarse con health checks.

> **Ejemplo**  
> Pesos `70`, `20` y `10` producen aproximadamente **70 %**, **20 %** y **10 %**.

> **Nota**  
> Útil para canary releases, blue-green y migraciones graduales.

**Docs**  
[Weighted routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-weighted.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Un dominio se divide hacia tres destinos marcados `70`, `20` y `10`.

### Slide 3 — Latency Routing

**Título en slide**

LATENCY ROUTING

#### Nombres en portal y examen

> **Latency-based routing policy** / **Política de enrutamiento basada en latencia**

#### Conceptos

- **Latency routing** dirige hacia la AWS Region que Route 53 estima con menor latencia.
- Necesitas registros para recursos en **2 o más Regions** si quieres comparar destinos.
- Route 53 solo elige entre las Regions para las que creaste registros.
- La decisión utiliza datos de latencia observados por AWS.
- Puede combinarse con comprobaciones de estado.
- No utiliza fronteras políticas de países.

> **Nota**  
> Menor latencia apunta a Latency Routing. Reglas por país o continente apuntan a Geolocation.

**Docs**  
[Latency-based routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-latency.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Usuario en Europa. `us-east-1` y `eu-west-1`. Route 53 elige el destino con menor latencia.

### Slide 4 — Failover Routing

**Título en slide**

FAILOVER ROUTING

#### Nombres en portal y examen

> **Failover routing policy** / **Política de conmutación por error**  
> **Primary** / **Primario**  
> **Secondary** / **Secundario**

#### Conceptos

- **Failover routing** implementa un patrón activo-pasivo con un primary y un secondary.
- Mientras el primary está sano, Route 53 responde con ese destino.
- Si deja de estar sano, Route 53 puede responder con el secondary.
- Un registro no Alias puede utilizar un **Route 53 health check**.
- Un Alias compatible puede usar **Evaluate Target Health**.
- El health check del secondary es opcional.

> **Nota**  
> Si primary y secondary tienen health checks y ambos están unhealthy, Route 53 devuelve el primary.

**Docs**  
[Failover routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-failover.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> `Primary` recibe tráfico normalmente. Si falla la señal de salud, Route 53 responde con `Secondary`.

### Slide 5 — Geolocation Routing

**Título en slide**

GEOLOCATION ROUTING

#### Nombres en portal y examen

> **Geolocation routing policy** / **Política de enrutamiento por geolocalización**

#### Conceptos

- **Geolocation routing** responde según la ubicación geográfica de la consulta.
- Puedes crear reglas para continentes, países y estados de Estados Unidos.
- Si varias reglas coinciden, gana la ubicación más específica.
- AWS recomienda un registro **Default** para ubicaciones no cubiertas.
- Sin Default y sin coincidencia, Route 53 puede responder sin destino.
- Puede combinarse con health checks.

> **Nota**  
> Geolocation usa ubicación. Latency Routing busca la Region con menor latencia.

**Docs**  
[Geolocation routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-geo.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> España → destino A. México → destino B. Resto → `Default`.

### Slide 6 — Geoproximity Routing

**Título en slide**

GEOPROXIMITY ROUTING

#### Nombres en portal y examen

> **Geoproximity routing policy** / **Política de enrutamiento por geoproximidad**  
> **Bias** / **Sesgo**

#### Conceptos

- **Geoproximity routing** utiliza la ubicación de usuarios y recursos para elegir el destino más cercano.
- Un bias entre **+1 y +99** amplía el área de influencia.
- Un bias entre **-1 y -99** reduce esa área.
- Un bias de `0` no modifica la distancia geográfica.
- Para recursos externos a AWS puedes indicar latitud y longitud.
- **Traffic Flow no es obligatorio** para crear registros geoproximity.

> **Nota**  
> “Modificar el tamaño del área” apunta a Geoproximity. “Enviar por país” apunta a Geolocation.

**Docs**  
[Geoproximity routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-geoproximity.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Dos recursos con áreas geográficas. `Bias +50` amplía una de ellas.

### Slide 7 — Multivalue Answer Routing

**Título en slide**

MULTIVALUE ANSWER ROUTING

#### Nombres en portal y examen

> **Multivalue answer routing policy** / **Política de respuesta multivalor**

#### Conceptos

- **Multivalue Answer Routing** puede devolver hasta **8 registros sanos** por respuesta.
- Cada registro puede tener su propio health check.
- Si existen **8 o menos** registros sanos, Route 53 devuelve todos.
- Si existen más de **8**, puede devolver diferentes combinaciones.
- Si todos están unhealthy, puede devolver hasta **8 registros unhealthy**.
- No sustituye a Elastic Load Balancing.

> **Nota**  
> El cliente sigue seleccionando entre las direcciones recibidas.

**Docs**  
[Multivalue answer routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-multivalue.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Hasta 8 IP sanas dentro de la respuesta. Una unhealthy queda fuera mientras existan destinos sanos.

### Slide 8 — IP-Based Routing

**Título en slide**

IP-BASED ROUTING

#### Nombres en portal y examen

> **IP-based routing policy** / **Política de enrutamiento basada en IP**  
> **CIDR collection** / **Colección CIDR**

#### Conceptos

- **IP-based routing** permite mapear rangos CIDR conocidos hacia destinos concretos.
- Una CIDR location contiene uno o varios bloques IPv4 o IPv6.
- Varias ubicaciones se agrupan dentro de una **CIDR collection**.
- Encaja cuando conoces los rangos de clientes, oficinas o proveedores.
- Route 53 puede utilizar **EDNS Client Subnet** cuando el resolver lo soporta.
- No está soportado para registros de una private hosted zone.

> **Nota**  
> Geolocation usa ubicación geográfica. IP-based utiliza rangos CIDR que tú defines.

**Docs**  
[IP-based routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-ipbased.html)

## Sesión 8.3 — Comprobaciones de estado

### Slide 1 — Route 53 Health Check

**Título en slide**

ROUTE 53 HEALTH CHECK

#### Nombres en portal y examen

> **Route 53 health check** / **Comprobación de estado**  
> **Health checker** / **Comprobador de estado**

#### Conceptos

- Route 53 puede comprobar endpoints públicos mediante **HTTP, HTTPS o TCP**.
- En HTTP y HTTPS, respuestas `2xx` y `3xx` se consideran correctas.
- El intervalo normal es **30 s** y puede reducirse a **10 s** con coste adicional.
- El failure threshold predeterminado es **3** y admite valores entre **1 y 10**.
- Los checks con búsqueda de texto inspeccionan los primeros **5 120 bytes**.
- El endpoint se considera sano cuando más del **18 %** de los health checkers reportan éxito.

> **Nota**  
> Una IP privada dentro de una VPC no puede recibir directamente estos health checks públicos.

**Docs**  
[How Route 53 determines health](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover-determining-health-of-endpoints.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Health checkers globales → endpoint público. Mostrar `30 s / 10 s`, `Threshold 3` y `Healthy / Unhealthy`.

### Slide 2 — Health Check con Amazon CloudWatch

**Título en slide**

HEALTH CHECK CON AMAZON CLOUDWATCH

#### Nombres en portal y examen

> **CloudWatch alarm health check** / **Health check basado en alarma**

#### Conceptos

- Los health checkers públicos no pueden comprobar directamente una dirección privada.
- Una métrica de **Amazon CloudWatch** puede representar la salud del recurso privado.
- Route 53 puede utilizar el estado de una **CloudWatch alarm** como health check.
- `OK` se interpreta como sano y `ALARM` como unhealthy.
- `INSUFFICIENT_DATA` puede configurarse como Healthy, Unhealthy o LastKnownStatus.

> **Nota**  
> Este patrón permite incorporar recursos privados a decisiones de failover sin exponerlos a internet.

**Docs**  
[HealthCheckConfig](https://docs.aws.amazon.com/Route53/latest/APIReference/API_HealthCheckConfig.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Recurso privado → métrica → Amazon CloudWatch Alarm → Route 53 Health Check.

### Slide 3 — Calculated Health Check

**Título en slide**

CALCULATED HEALTH CHECK

#### Nombres en portal y examen

> **Calculated health check** / **Comprobación de estado calculada**  
> **Child health check** / **Health check hijo**

#### Conceptos

- Un **calculated health check** calcula su estado a partir de otros health checks.
- Puede combinar hasta **256 child health checks**.
- Defines cuántos hijos deben estar sanos para considerar sano el resultado.
- Un threshold de `0` hace que siempre se considere healthy.
- Un threshold superior al número de hijos hace que siempre se considere unhealthy.
- Permite representar la salud conjunta de varios componentes.

> **Nota**  
> Un calculated health check y uno basado en CloudWatch son tipos distintos.

**Docs**  
[Values for Route 53 health checks](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-creating-values.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**  
> Tres child health checks → `Calculated Health Check`. Regla `2 de 3 = Healthy`.

## Sesión 8.4 — Zona privada y Resolver

### Slide 1 — Private Hosted Zone

**Título en slide**

PRIVATE HOSTED ZONE

#### Nombres en portal y examen

> **Private hosted zone** / **Zona alojada privada**  
> **DNS resolution** / **Resolución DNS**  
> **DNS hostnames** / **Nombres DNS de host**

#### Conceptos

- Una **private hosted zone** resuelve nombres únicamente desde las VPC asociadas.
- Puede utilizar nombres internos como `db.empresa.internal`.
- También puede compartir dominio con una public hosted zone para **split-view DNS**.
- La VPC debe tener `enableDnsSupport = true`.
- También necesita `enableDnsHostnames = true`.
- **Route 53 VPC Resolver** responde las consultas dentro de la VPC.

> **Nota**  
> Los registros privados no se publican hacia internet.

**Docs**  
[Considerations when working with private hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zone-private-considerations.html)

> **Logo** `recursos/aws/networking/route53.svg`

> **Idea visual**

### Slide 2 — DNS híbrido

**Título en slide**

DNS HÍBRIDO

#### Nombres en portal y examen

> **Route 53 VPC Resolver**  
> **Hybrid DNS** / **DNS híbrido**

#### Conceptos

- Route 53 VPC Resolver integra DNS de AWS con servidores DNS on-premises.
- AWS Site-to-Site VPN o Direct Connect proporcionan la conectividad.
- Un **inbound endpoint** permite que consultas on-premises entren hacia Resolver.
- Un **outbound endpoint** permite que Resolver envíe consultas hacia DNS on-premises.
- La dirección se interpreta desde la perspectiva de AWS.

> **Nota**  
> On-premises resuelve AWS → **Inbound**.  
> AWS resuelve on-premises → **Outbound**.

**Docs**  
[What is Route 53 VPC Resolver?](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver.html)

> **Idea visual**

### Slide 3 — Resolver Inbound Endpoint

**Título en slide**

RESOLVER INBOUND ENDPOINT

#### Nombres en portal y examen

> **Route 53 Resolver inbound endpoint** / **Endpoint entrante del Resolver**

#### Conceptos

- Un **inbound endpoint** recibe consultas DNS provenientes de fuera de la VPC.
- El DNS on-premises puede consultar private hosted zones y otros nombres resolubles desde AWS.
- Cada endpoint necesita al menos **2 direcciones IP privadas**.
- AWS recomienda distribuirlas entre al menos **2 Availability Zones**.
- Route 53 crea una interfaz de red por cada subnet e IP configurada.
- Las direcciones privadas permanecen estables durante la vida del endpoint.

> **Nota**  
> On-premises quiere resolver un nombre privado de AWS → Inbound Endpoint.

**Docs**  
[Forwarding inbound DNS queries](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver-forwarding-inbound-queries.html)

> **Idea visual**

### Slide 4 — Resolver Outbound Endpoint

**Título en slide**

RESOLVER OUTBOUND ENDPOINT

#### Nombres en portal y examen

> **Route 53 Resolver outbound endpoint** / **Endpoint saliente del Resolver**  
> **Forwarding rule** / **Regla de reenvío**

#### Conceptos

- Un **outbound endpoint** envía consultas de Resolver hacia servidores DNS externos.
- Una forwarding rule define qué dominio se reenvía y hacia qué servidores.
- Cada endpoint necesita al menos **2 direcciones IP privadas**.
- AWS recomienda distribuirlas entre al menos **2 Availability Zones**.
- La regla se asocia a las VPC donde debe utilizarse.
- Las demás consultas siguen resolviéndose normalmente.

> **Ejemplo**  
> `legacy.empresa.local` → forwarding rule → Outbound Endpoint → DNS on-premises.

### Slide 5 — Registrar y DNS

**Título en slide**

REGISTRAR Y DNS

#### Nombres en portal y examen

> **Domain registrar** / **Registrador de dominios**  
> **Authoritative DNS service** / **Servicio DNS autoritativo**

#### Conceptos

- El **registrar** administra el registro y renovación del dominio.
- El servicio DNS autoritativo administra los registros que resuelven ese dominio.
- Puedes registrar un dominio fuera de AWS y utilizar Route 53 como DNS.
- Creas la hosted zone y configuras en el registrar los registros **NS** entregados por Route 53.
- No necesitas transferir el dominio a AWS para utilizar Route 53.
- El precio de registro depende del **TLD**.

> **Idea visual**  
> `Registrar externo` conserva el dominio. Sus registros NS apuntan hacia Route 53.

## Sesión 8.5 — Arquitecturas

### Slide 1 — Failover DNS

**Título en slide**

ARQUITECTURA, FAILOVER DNS

#### Conceptos

- Un nombre público utiliza **Failover Routing** con un primary y un secondary.
- El primary apunta mediante Alias al ALB de la Region principal.
- El secondary apunta hacia un stack preparado en otra AWS Region.
- Para un ALB, **Evaluate Target Health** permite utilizar la salud del load balancer.
- Si el primary deja de estar sano, Route 53 responde con el secondary.
- Route 53 cambia DNS, pero no crea ni replica la infraestructura secundaria.

> **Nota**  
> En un Alias hacia ALB no configuras manualmente el TTL.

> **Idea visual**
>
> 1. Fondo con líneas punteadas `Region primaria | Region secundaria`.
> 2. Usuario consulta Amazon Route 53.
> 3. `Primary Alias` → ALB de la Region primaria.
> 4. Etiqueta `Evaluate Target Health`.
> 5. `Secondary Alias` → ALB de la Region secundaria.
> 6. Si primary falla, la respuesta cambia al secondary.
