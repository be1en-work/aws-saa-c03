## Sesión 8.1 — Registros

### Slide 1 — Amazon Route 53

**Título en slide —** AMAZON ROUTE 53

#### Nombres en portal y examen

> **Amazon Route 53** — **TTL (*time to live*)**

#### Conceptos

- **Amazon Route 53 —** servicio DNS administrado y altamente disponible de AWS.
- **Resolución —** relaciona un nombre con un destino, como una IP, un load balancer u otro nombre.
- **TTL —** indica cuántos segundos puede un DNS resolver guardar una respuesta en caché.
- **TTL bajo —** los cambios se reflejan antes, pero aumentan las consultas DNS.
- **TTL alto —** reduce consultas, pero una respuesta anterior permanece más tiempo en caché.

> **Nota —** Aquí no repetimos el funcionamiento completo de DNS ni todos sus record types. El foco es elegir la configuración correcta para un escenario de arquitectura.

**Docs —**  
[Amazon Route 53](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/Welcome.html)

**Idea visual —** icono oficial de **Amazon Route 53** como elemento central. `app.ejemplo.com` llega a Route 53 y sale hacia un destino. Al lado, un reloj `TTL — 60 s`.

### Slide 2 — Alias y CNAME

**Título en slide —** ALIAS EN EL ZONE APEX

#### Nombres en portal y examen

> **Alias record** — **CNAME** — **zone apex**

#### Conceptos

- **CNAME —** hace que un nombre DNS apunte hacia otro nombre.
- **Zone apex —** un CNAME no puede crearse en el nombre raíz de la hosted zone, como `ejemplo.com`.
- **Alias —** extensión de Route 53 que sí puede utilizarse en el zone apex.
- **Destinos AWS —** puede apuntar a recursos compatibles como ELB, CloudFront, API Gateway, S3 website y Global Accelerator.
- **Otra record —** también puede apuntar a otro record dentro de la misma hosted zone.

> **Nota —** Route 53 no cobra las consultas Alias dirigidas hacia recursos AWS compatibles. El DNS público de una EC2 no es un Alias target; para una dirección IP de EC2 utiliza un record `A` o `AAAA` según corresponda.

**Docs —**  
[Choosing between alias and non-alias records](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-choosing-alias-non-alias.html)

**Idea visual —** icono oficial de **Amazon Route 53**. `ejemplo.com` utiliza un `Alias` hacia un **Application Load Balancer**. Al lado, `www.ejemplo.com` utiliza `CNAME`. Un `CNAME` colocado en `ejemplo.com` aparece tachado.

### Slide 3 — Private Hosted Zone

**Título en slide —** PRIVATE HOSTED ZONE

#### Nombres en portal y examen

> **Private hosted zone**

#### Conceptos

- **Private DNS —** contiene records que se resuelven únicamente desde las VPC asociadas.
- **Asociación —** una Private Hosted Zone puede asociarse a una o más VPC.
- **VPC DNS —** `enableDnsHostnames` y `enableDnsSupport` deben estar habilitados.
- **No pública —** los records privados no se obtienen consultando los name servers de Route 53 desde Internet.

> **Nota —** Public Hosted Zone y Private Hosted Zone pueden utilizar el mismo dominio para implementar **split-view DNS**.

**Docs —**  
[Working with private hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zones-private.html)

**Idea visual —** icono oficial de **Amazon Route 53** con una `Private Hosted Zone` dentro de una VPC. Una EC2 de la VPC puede resolver `db.interno.ejemplo.com`; un usuario desde Internet no.

### Slide 4 — Route 53 Resolver

**Título en slide —** ROUTE 53 RESOLVER

#### Nombres en portal y examen

> **Route 53 VPC Resolver** — **inbound endpoint** — **outbound endpoint** — **Resolver rule**

#### Conceptos

- **Outbound endpoint —** permite que consultas originadas en una VPC se reenvíen hacia DNS resolvers de tu red on-premises.
- **Resolver rule —** indica qué dominios deben reenviarse y hacia qué DNS servers.
- **Inbound endpoint —** permite que DNS resolvers on-premises consulten nombres que Route 53 puede resolver dentro de AWS.
- **Conectividad —** el entorno on-premises debe poder llegar a la VPC mediante mecanismos como AWS Site-to-Site VPN o AWS Direct Connect.

> **Nota —** Memoriza la dirección mental — **Outbound = AWS → on-premises**. **Inbound = on-premises → AWS**.

**Docs —**  
[What is Route 53 VPC Resolver?](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver.html)  
[Resolving DNS queries between VPCs and your network](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver-overview-DSN-queries-to-vpc.html)

**Idea visual —** icono oficial de **Route 53 Resolver** si está disponible en draw.io. VPC a la izquierda y datacenter on-premises a la derecha. Flecha `Outbound` desde AWS hacia el DNS on-premises y flecha `Inbound` desde on-premises hacia Route 53 Resolver.

## Sesión 8.2 — Políticas

### Slide 1 — Simple, Weighted y Failover

**Título en slide —** SIMPLE · WEIGHTED · FAILOVER

#### Nombres en portal y examen

> **Simple routing** — **Weighted routing** — **Failover routing**

#### Conceptos

- **Simple —** utiliza un recurso que realiza una función determinada para el dominio.
- **Weighted —** reparte las respuestas entre varios recursos según los **pesos relativos** que configuras.
- **Canary —** Weighted puede enviar una proporción pequeña de tráfico hacia una versión nueva.
- **Failover —** patrón active-passive con un recurso primary y otro secondary.

> **Nota —** En Failover, Route 53 necesita información de salud para decidir cuándo dejar de responder con el primary. Puede utilizar un **Route 53 health check** o, para determinados Alias targets, **Evaluate Target Health**.

**Docs —**  
[Choosing a routing policy](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy.html)

**Idea visual —** icono de **Amazon Route 53** frente a tres esquemas — `Simple → A`, `Weighted → 90 / 10` y `Failover → Primary / Secondary`.

---

### Slide 2 — Multivalue, IP-based y health

**Título en slide —** MULTIVALUE · IP-BASED · HEALTH

#### Nombres en portal y examen

> **Multivalue answer routing** — **IP-based routing** — **health check**

#### Conceptos

- **Multivalue —** Route 53 puede devolver hasta **8 records saludables** seleccionados al azar.
- **Health check —** permite excluir de determinadas respuestas un endpoint que no está saludable.
- **IP-based —** responde según los rangos CIDR desde los que se originan las consultas.
- **Control —** IP-based sirve cuando conoces tu base de usuarios o redes y quieres decidir explícitamente qué endpoint recibe cada rango.

> **Nota —** Multivalue no sustituye a un load balancer. Es routing DNS con health awareness.

**Docs —**  
[Multivalue answer routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-multivalue.html)  
[IP-based routing](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-ipbased.html)

**Idea visual —** icono de **Amazon Route 53**. A la izquierda, una consulta devuelve varias IP saludables. A la derecha, dos rangos CIDR distintos se dirigen hacia endpoints diferentes.

---

### Slide 3 — Latency, Geolocation y Geoproximity

**Título en slide —** LATENCY · GEOLOCATION · GEOPROXIMITY

#### Nombres en portal y examen

> **Latency routing** — **Geolocation routing** — **Geoproximity routing**

#### Conceptos

- **Latency —** dirige al recurso que ofrece la mejor latencia para el usuario.
- **Geolocation —** responde según la ubicación geográfica del usuario, como país o continente.
- **Geoproximity —** considera la ubicación de usuarios y recursos y permite modificar el área atendida mediante un **bias**.
- **Bias —** desplaza tráfico hacia un recurso o lo aleja de él.

> **Nota —** “Usuarios de Europa deben ir siempre al endpoint europeo” apunta a **Geolocation**. “Enviar al recurso con mejor tiempo de respuesta” apunta a **Latency**. “Aumentar o reducir manualmente el área geográfica que recibe un recurso” apunta a **Geoproximity**.

**Docs —**  
[Choosing a routing policy](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy.html)

**Idea visual —** tres columnas. `Latency` con un cronómetro; `Geolocation` con un país marcado; `Geoproximity` con dos recursos y un área que cambia de tamaño mediante `Bias`.

## Sesión 8.3 — Arquitectura, failover

### Slide 1 — Primary y Secondary

**Título en slide —** ARQUITECTURA, PRIMARY Y SECONDARY

#### Conceptos

- Route 53 recibe la consulta DNS para el nombre de la aplicación.
- Mientras el primary está saludable, responde con ese destino.
- Si la comprobación de salud falla, Route 53 puede responder con el secondary.
- El destino secundario puede encontrarse en otra AWS Region.

> **Nota —** Route 53 decide qué respuesta DNS entregar. No mueve las conexiones que ya estaban abiertas y los resolvers pueden conservar respuestas anteriores hasta que expire su TTL.

**Idea visual —**

1. Usuario → icono oficial de **Amazon Route 53**.
2. Route 53 → **ALB Primary** mediante una flecha sólida.
3. Un `Health Check` vigila el primary.
4. **ALB Secondary** en otra Region mediante flecha punteada.
5. Primary aparece unhealthy.
6. La flecha sólida cambia hacia el secondary.
7. No dibujar por dentro los ALB; ya fueron estudiados en M6.

3. A startup has built a new web application that lets users complete a risk assessment survey for COVID-19 symptoms through a self-administered questionnaire. Using Amazon Route 53, the startup purchased the domain covid19survey.com. The web development team wants to create an Amazon Route 53 record so that all traffic for covid19survey.com is routed to www.covid19survey.com.

As a solutions architect, which of the following is the MOST cost-effective solution you would recommend to the web development team?

A) For covid19survey.com, create an MX record that routes traffic to www.covid19survey.com

B) For covid19survey.com, create a CNAME record that routes traffic to www.covid19survey.com

C) For covid19survey.com, create an NS record that routes traffic to www.covid19survey.com

D) For covid19survey.com, create an alias record that routes traffic to www.covid19survey.com

✅ **Respuesta —** D

💡 **Explanation —** `covid19survey.com` is the **zone apex**, where a CNAME record cannot be created. A Route 53 **Alias record** can be created at the zone apex and can route queries to another compatible record in the same hosted zone. Alias queries also avoid the additional Route 53 query charge associated with using a CNAME.

4. A healthcare company is building a secure internal web portal on AWS, and that application must communicate with legacy systems that still reside in the company's on-premises data centers. Those data centers are already connected to AWS by a site-to-site VPN. Amazon Route 53 is the company's DNS solution, and the application has to resolve private DNS records for the on-premises services from inside its Amazon VPC.

What is the MOST secure and appropriate way to meet these DNS resolution requirements?

A) Configure a Route 53 Resolver inbound endpoint and create a DNS forwarding rule. Enable recursive DNS resolution in the VPC so on-premises services can be reached

B) Create a Route 53 Resolver outbound endpoint. Define a forwarding rule that routes DNS queries for on-premises domains to the on-premises DNS server, and associate the rule with the VPC

C) Create a Route 53 private hosted zone for the on-premises domain and associate the hosted zone with the VPC so the application can resolve DNS names of the on-premises services

D) Create a hybrid connectivity gateway and attach the on-premises DNS servers to Route 53 as authoritative zones for the internal domains

✅ **Respuesta —** B

💡 **Explanation —** The DNS query originates **inside the VPC** and must be resolved by DNS servers **on premises**. A **Route 53 Resolver outbound endpoint** provides that path. A forwarding rule identifies the on-premises domain and sends matching DNS queries through the outbound endpoint to the on-premises DNS resolver over the existing VPN.

5. A retail company has linked its on-premises data center to the AWS Cloud with AWS Direct Connect. The company needs to resolve Domain Name System (DNS) queries for any resources in the on-premises network from the AWS VPC, and it also needs to resolve any DNS queries for resources in the AWS VPC from the on-premises network.

As a solutions architect, which of the following solutions can be combined to address this use case? (Select two)

A) Create an inbound endpoint on Amazon Route 53 Resolver so that DNS resolvers on the on-premises network can forward DNS queries to Amazon Route 53 Resolver through that endpoint

B) Create an inbound endpoint on Amazon Route 53 Resolver so that Amazon Route 53 Resolver can conditionally forward queries to resolvers on the on-premises network through that endpoint

C) Create an outbound endpoint on Amazon Route 53 Resolver so that Amazon Route 53 Resolver can conditionally forward queries to resolvers on the on-premises network through that endpoint

D) Create an outbound endpoint on Amazon Route 53 Resolver so that DNS resolvers on the on-premises network can forward DNS queries to Amazon Route 53 Resolver through that endpoint

E) Create a universal endpoint on Amazon Route 53 Resolver so that Amazon Route 53 Resolver can receive queries and forward them to resolvers on the on-premises network through that endpoint

✅ **Respuesta —** A y C

💡 **Explanation —** An **inbound Resolver endpoint** allows DNS resolvers in the on-premises network to send queries into Route 53 Resolver so they can resolve AWS private names. An **outbound Resolver endpoint**, together with forwarding rules, allows Route 53 Resolver to send selected DNS queries originating in the VPC toward DNS resolvers in the on-premises network. Using both endpoints provides bidirectional hybrid DNS resolution.
