## Sesión 16.1 — CloudWatch

### Slide 1 — Métricas

**Título en slide**

AMAZON CLOUDWATCH — MÉTRICAS

#### Nombres en portal y examen

> **Amazon CloudWatch**, **metric**

#### Conceptos

- Una **métrica** representa un valor numérico que cambia con el tiempo, como utilización de CPU, errores o profundidad de una cola.
- En Amazon EC2, basic monitoring publica determinadas métricas cada **5 minutos** y detailed monitoring las publica cada **1 minuto**.
- Los servicios AWS publican sus propias métricas y también puedes enviar custom metrics.
- Una métrica muestra qué está ocurriendo, pero no identifica por sí sola quién realizó una llamada a una API.

> **Nota**  
> Los intervalos de 5 y 1 minuto corresponden específicamente al monitoring de Amazon EC2. No todas las métricas de CloudWatch utilizan esa frecuencia.

**Docs**  
[CloudWatch metrics](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch_concepts.html)

> **Idea visual**

### Slide 2 — Logs

**Título en slide**

AMAZON CLOUDWATCH LOGS

#### Nombres en portal y examen

> **CloudWatch Logs**, **metric filter**, **subscription filter**

#### Conceptos

- **CloudWatch Logs** centraliza el texto generado por aplicaciones y servicios.
- Un **metric filter** busca un patrón dentro de los logs y lo convierte en una métrica de CloudWatch.
- Un **subscription filter** envía eventos de log en tiempo casi real hacia destinos como AWS Lambda, Amazon Kinesis Data Streams o Amazon Data Firehose.
- CloudWatch Logs también puede enviar datos hacia Amazon OpenSearch Service para analizarlos.

> **Nota**  
> Un metric filter crea números a partir de logs. Un subscription filter reenvía los eventos. No son la misma función.

**Docs**  
[Real-time processing of log data with subscriptions](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Subscriptions.html)  
[Create metrics from log events using filters](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html)

> **Logo** `recursos/aws/security/cloudwatch.svg`

> **Idea visual**  
> Icono oficial de **Amazon CloudWatch Logs** recibiendo líneas de texto. Un `Metric Filter` produce una métrica y un `Subscription Filter` envía logs hacia otro servicio.

### Slide 3 — Alarmas

**Título en slide**

AMAZON CLOUDWATCH ALARM

#### Nombres en portal y examen

> **CloudWatch alarm**, **threshold**

#### Conceptos

- Una **CloudWatch alarm** observa una métrica y cambia de estado cuando se cumplen las condiciones configuradas.
- La alarma puede notificar mediante Amazon SNS o iniciar acciones compatibles como Auto Scaling.
- Para Amazon EC2 también existen acciones como reboot, stop, terminate y recover cuando el escenario y la instancia lo permiten.
- Los cambios de estado de las alarmas también pueden utilizarse desde Amazon EventBridge.

> **Nota**  
> La alarma no almacena el dato. Evalúa una métrica y actúa cuando su estado cambia.

> **Logo** `recursos/aws/security/cloudwatch.svg`

> **Idea visual**  
> Icono oficial de **Amazon CloudWatch**. Un gráfico cruza una línea de threshold y la alarma envía una notificación hacia el icono oficial de **Amazon SNS**.

### Slide 4 — EC2 Recovery

**Título en slide**

CLOUDWATCH — EC2 RECOVERY

#### Conceptos

- Una CloudWatch alarm puede iniciar la recuperación de una instancia compatible cuando falla `StatusCheckFailed_System`.
- La recuperación intenta mover la instancia hacia hardware funcional sin cambiar su identidad.
- Se conservan el instance ID, las IP privadas, Elastic IP addresses, la IPv4 pública y los volúmenes EBS adjuntos.
- La memoria RAM se pierde durante el proceso y una instancia terminada no puede recuperarse.
- En CloudWatch action-based recovery, los datos almacenados en instance store volumes se pierden.

> **Nota**  
> La documentación actual permite CloudWatch action-based recovery en determinados tipos de instancia que utilizan instance store. Por eso ya no es correcto memorizar que recovery exige siempre una instancia exclusivamente EBS-backed.

**Docs**  
[Automatic instance recovery](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-recover.html)

> **Logo** `recursos/aws/security/cloudwatch.svg`

> **Idea visual**  
> Una instancia EC2 sobre un host con fallo pasa mediante `Recover` hacia otro host. El instance ID y las IP permanecen iguales. Una pequeña etiqueta muestra `RAM lost`.

## Sesión 16.2 — Quién hizo qué, y qué quedó

### Slide 1 — AWS CloudTrail

**Título en slide**

AWS CLOUDTRAIL

#### Nombres en portal y examen

> **AWS CloudTrail**, **management event**, **trail**

#### Conceptos

- **AWS CloudTrail** registra actividad de API y ayuda a responder quién hizo una acción, cuándo, desde dónde y sobre qué recurso.
- Event history permite consultar los últimos **90 días** de management events dentro de una Region.
- Para conservar un historial continuo puedes crear un trail y entregar sus eventos a Amazon S3.
- CloudTrail también puede enviar eventos hacia CloudWatch Logs para analizarlos y crear metric filters.

> **Nota**  
> CloudTrail registra actividad de AWS. No sustituye al log que escribe tu aplicación.

**Docs**

### Slide 2 — AWS Config

**Título en slide**

AWS CONFIG

#### Nombres en portal y examen

> **AWS Config**, **configuration history**, **AWS Config rule**

#### Conceptos

- **AWS Config** registra la configuración de recursos y permite consultar cómo esa configuración cambió con el tiempo.
- Las **AWS Config rules** evalúan si los recursos cumplen condiciones definidas.
- Una regla puede detectar, por ejemplo, un bucket público o una configuración que dejó de cumplir una política.

> **Nota**

### Slide 3 — Amazon GuardDuty

**Título en slide**

AMAZON GUARDDUTY

#### Nombres en portal y examen

> **Amazon GuardDuty**, **finding**, **threat detection**

#### Conceptos

- **Amazon GuardDuty** analiza continuamente actividad de AWS para detectar comportamientos sospechosos y amenazas.
- Sus fuentes fundamentales incluyen **AWS CloudTrail management events**, **VPC Flow Logs** y **Route 53 Resolver DNS query logs**.
- GuardDuty utiliza threat intelligence y técnicas de detección para generar security findings.
- Otros protection plans pueden incorporar fuentes adicionales para servicios y workloads específicos.

> **Nota**  
> Para una pregunta del examen sobre las fuentes fundamentales de GuardDuty, recuerda el trío CloudTrail management events, VPC Flow Logs y DNS logs.

**Docs**  
[GuardDuty foundational data sources](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_data-sources.html)

## Sesión 16.3 — Rastro, parche y consejo

### Slide 1 — AWS X-Ray

**Título en slide**

AWS X-RAY

#### Nombres en portal y examen

> **AWS X-Ray**, **trace**, **segment**

#### Conceptos

- **AWS X-Ray** permite seguir una petición mientras atraviesa los componentes de una aplicación distribuida.
- Un trace ayuda a identificar cuánto tiempo se consume en cada servicio y dónde aparece un error o una latencia anormal.
- Puede mostrar, por ejemplo, el recorrido entre una API, una función y una base de datos.
- X-Ray no sustituye a las métricas de CloudWatch ni al contenido completo de los logs.

> **Nota**  
> AWS recomienda actualmente OpenTelemetry para nueva instrumentación que envía trazas hacia X-Ray. Para el examen, el concepto importante sigue siendo reconocer X-Ray como el servicio de distributed tracing.

**Docs**  
[AWS X-Ray](https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html)
