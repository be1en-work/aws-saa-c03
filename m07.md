## Sesión 7.1 — RDS

### Slide 1 — Amazon Relational Database Service

**Título en slide —** AMAZON RELATIONAL DATABASE SERVICE (AMAZON RDS)

#### Nombres en portal y examen

> **Amazon Relational Database Service (Amazon RDS)**

#### Conceptos

- **Amazon RDS —** servicio administrado para ejecutar bases de datos relacionales.
- **AWS administra —** infraestructura, instalación del motor, backups automáticos y tareas comunes de mantenimiento.
- **Tú administras —** datos, esquema, usuarios, consultas y las configuraciones que expone el motor.
- **Frente a EC2 —** una base autogestionada sobre EC2 ofrece más control, pero también más responsabilidad operativa.

> **Nota —** Si el escenario exige entrar al sistema operativo o realizar una personalización que RDS normal no permite, puede ser necesario otro modelo. No elijas EC2 solo por costumbre.

**Docs —**  
[What is Amazon RDS?](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Welcome.html)

**Idea visual —** icono oficial de **Amazon RDS** como elemento central. A un lado, RDS con infraestructura y motor administrados por AWS. Al otro, una base instalada sobre **Amazon EC2**, con el sistema operativo y el motor del lado del cliente.

### Slide 2 — Multi-AZ y Read Replica

**Título en slide —** MULTI-AZ NO ES READ REPLICA

#### Nombres en portal y examen

> **Multi-AZ deployment** — **standby** — **read replica**

#### Conceptos

- **Multi-AZ DB instance —** replica de forma síncrona hacia un standby en otra Availability Zone.
- **Standby —** existe para alta disponibilidad y no atiende lecturas en el despliegue Multi-AZ tradicional.
- **Read replica —** replica de forma asíncrona y descarga consultas de lectura.
- **Cross-Region —** una read replica puede existir en otra Region para lecturas cercanas o recuperación.

> **Nota —** Una read replica puede llevar retraso respecto a la primary. Si la pregunta busca continuidad de escritura y failover automático, piensa en **Multi-AZ**, no en una read replica.

**Docs —**  
[Amazon RDS Multi-AZ deployments](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.html)  
[Working with DB instance read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)

**Idea visual —** icono oficial de **Amazon RDS**. En `AZ a`, una primary. En `AZ b`, un standby unido mediante una flecha `Synchronous`, sin clientes. A un lado, una **Read Replica** con flecha `Asynchronous` y consultas `SELECT`.

### Slide 3 — Multi-AZ DB Cluster

**Título en slide —** MULTI-AZ DB CLUSTER

#### Nombres en portal y examen

> **Multi-AZ DB cluster**

#### Conceptos

- **Tres AZ —** utiliza un writer y dos reader DB instances distribuidas entre tres Availability Zones.
- **Lecturas —** los readers sí pueden atender consultas.
- **Failover —** uno de los readers puede convertirse en el nuevo writer.
- **Motores —** está disponible para RDS for MySQL y RDS for PostgreSQL.

> **Nota —** No confundas este modelo con el **Multi-AZ DB instance deployment** tradicional. En el tradicional, el standby no atiende lecturas.

**Docs —**  
[Multi-AZ DB cluster deployments](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/multi-az-db-clusters-concepts.html)

**Idea visual —** icono oficial de **Amazon RDS** sobre tres Availability Zones. Una instancia marcada `Writer` y dos marcadas `Reader`, cada una en una AZ diferente.

### Slide 4 — Endpoint y failover

**Título en slide —** EL ENDPOINT SOBREVIVE AL FAILOVER

#### Conceptos

- **Endpoint —** la aplicación se conecta mediante un nombre DNS, no directamente a la instancia física.
- **Failover —** RDS promueve el standby cuando la primary deja de estar disponible.
- **DNS —** el mismo endpoint pasa a resolver hacia la nueva primary.
- **Aplicación —** no necesita cambiar manualmente su cadena de conexión por el ID de otra DB instance.

> **Nota —** El failover no significa que todas las conexiones existentes sobrevivan. La aplicación debe ser capaz de reconectar cuando cambia la instancia detrás del endpoint.

**Idea visual —** aplicación → `db.example...rds.amazonaws.com`. Debajo, el endpoint apunta primero a la primary de `AZ a`; tras un fallo, la flecha cambia hacia la nueva primary de `AZ b`.

### Slide 5 — Mantenimiento en Multi-AZ

**Título en slide —** MANTENIMIENTO EN MULTI-AZ

#### Conceptos

- **OS maintenance —** RDS puede mantener primero el standby, hacer failover y después mantener la antigua primary.
- **Engine upgrade —** una actualización de versión del motor requiere downtime.
- **Multi-AZ DB instance —** primary y standby pueden actualizarse simultáneamente durante un engine version upgrade.
- **Planificación —** realiza upgrades durante una maintenance window y prueba primero la compatibilidad de la aplicación.

> **Nota —** No confundas un parche del sistema operativo con un **database engine version upgrade**. No siguen necesariamente el mismo proceso.

**Docs —**  
[Maintaining a DB instance](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_UpgradeDBInstance.Maintenance.html)

**Idea visual —** dos secuencias. `OS maintenance` — standby → failover → antigua primary. `Engine upgrade` — primary + standby en mantenimiento con una ventana de downtime.

### Slide 6 — Cifrado y autenticación

**Título en slide —** CIFRADO E IAM DB AUTHENTICATION

#### Nombres en portal y examen

> **Encryption at rest** — **IAM database authentication**

#### Conceptos

- **Encryption at rest —** protege almacenamiento, snapshots, backups y otros recursos derivados de una DB cifrada.
- **DB sin cifrar —** snapshot → copia cifrada → restore para crear una nueva DB cifrada.
- **En tránsito —** utiliza TLS para proteger las conexiones.
- **IAM DB authentication —** en motores compatibles, la aplicación puede utilizar un token temporal en lugar de guardar una contraseña de base de datos.

> **Nota —** Las AWS KMS keys utilizadas para el cifrado se estudian más adelante. Compartir determinados recursos cifrados puede requerir también acceso a la KMS key correspondiente.

### Slide 7 — Storage autoscaling

**Título en slide —** RDS STORAGE AUTOSCALING

#### Nombres en portal y examen

> **Storage autoscaling**

#### Conceptos

- **Crecimiento automático —** RDS puede aumentar el almacenamiento cuando detecta poco espacio disponible.
- **Maximum storage threshold —** defines hasta dónde puede crecer.
- **Sin cambio de motor —** ampliar almacenamiento no exige migrar a otro motor.
- **No scale-down —** el almacenamiento asignado no disminuye automáticamente después.

> **Nota —** Storage autoscaling escala **capacidad de almacenamiento**. No añade read replicas ni aumenta automáticamente la clase de la DB instance.

**Docs —**  
[Managing capacity automatically with Amazon RDS storage autoscaling](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIOPS.Autoscaling.html)

**Idea visual —** icono oficial de **Amazon RDS** conectado a un disco que crece de `100 GiB` a `150 GiB`. Una flecha únicamente hacia arriba indica que el almacenamiento no reduce automáticamente su tamaño.

## Sesión 7.2 — Aurora y el proxy

### Slide 1 — Amazon Aurora

**Título en slide —** AMAZON AURORA

#### Nombres en portal y examen

> **Amazon Aurora** — **Aurora MySQL** — **Aurora PostgreSQL**

#### Conceptos

- **Aurora —** motor relacional administrado compatible con MySQL y PostgreSQL.
- **Storage distribuido —** mantiene los datos de forma redundante entre tres Availability Zones.
- **Cluster —** el writer y las Aurora Replicas utilizan el mismo almacenamiento distribuido.
- **Read scaling —** añadir una Aurora Replica no significa copiar un disco completo independiente.

> **Nota —** Aurora Multi-Master dejó de estar disponible. La arquitectura actual utiliza un writer por cluster y Aurora Replicas que pueden promocionarse durante un failover.

**Título en slide —** WRITER, READER Y CUSTOM ENDPOINT

#### Nombres en portal y examen

> **Writer endpoint** — **Reader endpoint** — **Custom endpoint**

#### Conceptos

- **Writer endpoint —** dirige conexiones hacia la instancia que actualmente acepta escrituras.
- **Reader endpoint —** distribuye conexiones de lectura entre las Aurora Replicas.
- **Custom endpoint —** apunta a un subconjunto específico de instancias.
- **Failover —** los endpoints evitan que la aplicación tenga que conocer qué instancia física ocupa cada rol.

> **Nota —** Si demasiadas consultas `SELECT` afectan al writer, añade Aurora Replicas y dirige las lecturas mediante el **Reader endpoint**.

### Slide 4 — Aurora Global Database

**Título en slide —** AURORA GLOBAL DATABASE

#### Nombres en portal y examen

> **Aurora Global Database**

#### Conceptos

- **Multi-Region —** utiliza un primary DB cluster en una Region y secondary clusters en otras.
- **Local reads —** usuarios globales pueden leer desde una Region cercana.
- **Replicación —** los cambios del primary cluster se replican hacia los secundarios.
- **Regional failure —** un secondary cluster puede convertirse en el nuevo primary durante una recuperación.

> **Nota —** Aurora Global Database replica **clusters completos**, no tablas individuales dentro del mismo cluster. Las estrategias de disaster recovery se estudian más adelante.

### Slide 5 — Amazon RDS Proxy

**Título en slide —** AMAZON RDS PROXY

#### Nombres en portal y examen

> **Amazon RDS Proxy** — **connection pooling**

#### Conceptos

- **Connection pooling —** reutiliza conexiones hacia la base en lugar de abrir una nueva por cada cliente.
- **Escalado —** protege la base cuando muchas aplicaciones o funciones abren conexiones simultáneamente.
- **Failover —** ayuda a reducir el impacto de cambios de instancia durante determinados failovers.
- **No es caché —** no almacena resultados de consultas y no sustituye una read replica.

> **Nota —** Si la base se queda sin conexiones cuando la aplicación escala, piensa en **RDS Proxy**. Si el problema son lecturas repetidas, piensa en read replicas o caché.

**Docs —**  
[Amazon RDS Proxy](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html)

**Idea visual —** icono oficial de **Amazon RDS** con una caja `RDS Proxy` delante. Muchas EC2 o funciones llegan al proxy y desde él salen pocas conexiones reutilizadas hacia RDS o Aurora.

**Título en slide —** AMAZON ELASTICACHE

#### Nombres en portal y examen

> **Amazon ElastiCache** — **Valkey** — **Redis OSS** — **Memcached**

#### Conceptos

### Slide 2 — Valkey / Redis OSS frente a Memcached

**Título en slide —** VALKEY / REDIS OSS FRENTE A MEMCACHED

#### Conceptos

- **Valkey / Redis OSS —** estructuras de datos avanzadas, replicación y opciones de alta disponibilidad.
- **Multi-AZ —** puede utilizar replicas en distintas AZ y failover automático.
- **Memcached —** caché distribuida simple y multithreaded.
- **Sin replicación —** los nodos Memcached no mantienen replicas entre sí; si el dato desaparece, la aplicación debe reconstruirlo.

> **Nota —** Bancos antiguos suelen decir únicamente **Redis**. En documentación actual de ElastiCache también aparece **Valkey**.

### Slide 3 — Lazy loading y write-through

**Título en slide —** LAZY LOADING Y WRITE-THROUGH

#### Nombres en portal y examen

> **Lazy loading** — **cache-aside** — **write-through**

#### Conceptos

- **Lazy loading —** ante un cache miss, la aplicación consulta la base y guarda el resultado en caché.
- **Ventaja —** solo se cachean datos que realmente se leen.
- **Write-through —** una escritura actualiza la fuente de datos y también el caché.
- **Trade-off —** write-through mantiene datos más frescos en caché, pero añade trabajo a cada escritura.

> **Nota —** Una estrategia puede combinarse con TTL para limitar cuánto tiempo permanece un valor dentro del caché.

**Idea visual —** icono de **Amazon ElastiCache** entre aplicación y RDS. A la izquierda, `Cache miss → RDS → Cache`. A la derecha, `Write → RDS + Cache`.

### Slide 4 — Sesión fuera de EC2

**Título en slide —** SESSION STORE

#### Conceptos

- **Sesión —** se guarda en un almacén compartido en lugar del disco local de una EC2.
- **Cualquier instancia —** otra EC2 puede atender la siguiente solicitud del usuario.
- **TTL —** permite expirar sesiones que ya no deben mantenerse.
- **Sticky sessions —** dejan de ser necesarias para conservar la sesión cuando el estado ya está externalizado.

> **Nota —** Sacar la sesión de EC2 permite que las instancias de M6 sigan siendo stateless y puedan reemplazarse sin perder el estado del usuario.

**Idea visual —** tres iconos **Amazon EC2** apuntando al mismo **Amazon ElastiCache**. Un usuario cambia de EC2 entre dos solicitudes y la sesión continúa porque vive en el caché.

1. Tras incorporarse a un equipo de desarrollo, un nuevo ingeniero DevOps quiere comprender las capacidades de replicación de RDS Multi-AZ, así como las de RDS Read-replicas.

¿Cuál de las siguientes opciones resume correctamente estas capacidades para la base de datos dada?

A) La replicación asíncrona es la que sigue Multi-AZ, y abarca una zona de disponibilidad dentro de una única región. Las réplicas de lectura siguen la replicación síncrona y pueden situarse dentro de una zona de disponibilidad, entre zonas o entre regiones

B) La replicación síncrona es la que sigue Multi-AZ, y abarca al menos dos zonas de disponibilidad (AZ) dentro de una misma región. Las réplicas de lectura siguen la replicación asíncrona y pueden situarse dentro de una zona de disponibilidad, Cross-AZ o Cross-Region

C) La replicación asíncrona es la que sigue Multi-AZ, y abarca al menos dos zonas de disponibilidad (AZ) dentro de una misma región. Las réplicas de lectura siguen la replicación síncrona y pueden situarse dentro de una zona de disponibilidad, Cross-AZ o Cross-Region

Dependiendo del motor, puede crearse en la misma AZ, otra AZ o incluso otra AWS Region.

2. Un clúster Amazon Aurora recibe muchas consultas de lectura y el writer empieza a sufrir presión de I/O. El equipo añade varias Aurora Replicas y quiere que la aplicación distribuya automáticamente las consultas `SELECT` entre ellas.

A) Writer endpoint

B) Reader endpoint

C) Instance endpoint del writer

El Writer endpoint envía conexiones hacia la instancia que acepta escrituras, mientras que RDS Proxy resuelve principalmente problemas de administración y reutilización de conexiones.

4. Toda la pila tecnológica de una empresa de juegos, incluida la aplicación insignia que se conecta a una base de datos de Amazon Aurora, está desplegada hoy en Estados Unidos. La empresa planea ampliar sus operaciones a Europa y Asia. La tabla games debe quedar accesible de forma global, mientras que las tablas users y games_played deben seguir siendo solo regionales.

¿De qué modo implementarías esto con una refactorización mínima de la aplicación?

A) Para la tabla games, utiliza una base de datos global de Amazon Aurora y, para las tablas users y games_played, utiliza Amazon Aurora

B) Para la tabla games, utiliza una base de datos global de Amazon Aurora y, para las tablas users y games_played, utiliza tablas DynamoDB

C) Para la tabla games, utiliza una tabla global de DynamoDB y, para las tablas users y games_played, utiliza Amazon Aurora

D) Para la tabla games, utiliza una tabla global de DynamoDB y, para las tablas users y games_played, utiliza tablas DynamoDB

✅ **Respuesta —** A

💡 **Explicación —** Entre las opciones disponibles, mantener los datos relacionales en **Amazon Aurora** implica menos refactorización que mover parte del modelo a DynamoDB. La información que necesita alcance global puede colocarse en un **Aurora Global Database**, mientras que los datos regionales permanecen en un cluster Aurora regional. Importante — Aurora Global Database replica un **DB cluster completo**, no una tabla individual, por lo que `games` tendría que separarse en el cluster que participa en la global database.
