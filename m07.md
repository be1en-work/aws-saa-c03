## Sesión 7.1 — RDS

### Slide 1 — Amazon Relational Database Service

**Título en slide —** AMAZON RELATIONAL DATABASE SERVICE (AMAZON RDS)

#### Nombres en portal y examen

> **Amazon Relational Database Service (Amazon RDS)**

#### Conceptos

- **Amazon RDS —** servicio administrado para ejecutar bases de datos relacionales.
- **AWS administra —** aprovisionamiento, infraestructura subyacente, backups y tareas comunes de mantenimiento.
- **Tú administras —** esquema, datos, usuarios, consultas y configuración disponible del motor.
- **Frente a EC2 —** si necesitas controlar directamente el sistema operativo o instalar componentes no permitidos por RDS, una base autogestionada en EC2 ofrece más control.

> **Nota —** RDS soporta varios motores. En el examen normalmente importa el requisito del escenario, no memorizar el catálogo completo.

**Docs —** Amazon RDS User Guide — What is Amazon RDS?

**Idea visual —** icono oficial de **Amazon RDS** como elemento principal. A la izquierda, RDS con la infraestructura administrada por AWS. A la derecha, una base instalada sobre **Amazon EC2**, mostrando que el sistema operativo queda del lado del cliente.

### Slide 2 — Multi-AZ y Read Replica

**Título en slide —** MULTI-AZ NO ES READ REPLICA

#### Nombres en portal y examen

> **Multi-AZ deployment** — **standby** — **read replica**

#### Conceptos

- **Multi-AZ DB instance —** replica de forma síncrona hacia un standby en otra AZ para alta disponibilidad.
- **Standby —** no recibe tráfico de lectura en el despliegue Multi-AZ tradicional de una sola instancia.
- **Read replica —** replica de forma asíncrona y sirve para descargar consultas de lectura.
- **Cross-Region —** una read replica puede utilizarse en otra Region para lecturas cercanas o estrategias de recuperación.

> **Nota —** En un failover Multi-AZ, RDS promueve el standby y actualiza el DNS del endpoint. La aplicación continúa utilizando el mismo endpoint.

**Docs —** Amazon RDS User Guide — Multi-AZ deployments  
**Docs —** Amazon RDS User Guide — Read replicas

**Idea visual —** icono oficial de **Amazon RDS**. En `AZ a`, una primary. En `AZ b`, un standby conectado con flecha `Synchronous` y sin clientes. A un lado, una **Read Replica** conectada con flecha `Asynchronous` y recibiendo consultas `SELECT`.

### Slide 3 — Multi-AZ DB Cluster

**Título en slide —** MULTI-AZ DB CLUSTER

#### Nombres en portal y examen

> **Multi-AZ DB cluster**

#### Conceptos

- **Tres AZ —** un writer y dos reader instances en tres Availability Zones.
- **Lecturas —** las dos réplicas pueden atender tráfico de lectura.
- **Alta disponibilidad —** una réplica puede convertirse en el nuevo writer si falla el actual.
- **Motores —** esta arquitectura está disponible para RDS for MySQL y RDS for PostgreSQL.

> **Nota —** No confundas este diseño con el **Multi-AZ DB instance deployment** clásico. En el clásico, el standby no atiende lecturas; en un Multi-AZ DB cluster, los readers sí.

**Docs —** Amazon RDS User Guide — Multi-AZ DB cluster deployments

**Idea visual —** icono oficial de **Amazon RDS** en tres AZ. Una instancia marcada `Writer` y dos marcadas `Reader`, cada una en una zona diferente.

### Slide 4 — Mantenimiento y failover

**Título en slide —** MANTENIMIENTO EN MULTI-AZ

#### Conceptos

- **Mantenimiento del sistema —** RDS puede actualizar primero el standby, hacer failover y después mantener la antigua primary.
- **Engine upgrade —** una actualización de versión del motor puede dejar primary y standby indisponibles durante el proceso.
- **Failover —** la aplicación mantiene el endpoint; cambia el destino detrás del DNS.
- **Read replica —** no sustituye al standby cuando el requisito es continuidad de escritura.

> **Nota —** No mezcles mantenimiento del sistema operativo con un **database engine version upgrade**. El comportamiento y el downtime no son iguales.

**Docs —** Amazon RDS User Guide — Maintaining a DB instance

**Idea visual —** dos AZ con primary y standby. Primera secuencia — mantenimiento del standby → promoción → mantenimiento de la antigua primary. Segunda secuencia — `Engine upgrade` afectando ambas con una ventana de downtime.

### Slide 5 — Cifrado, autenticación y storage autoscaling

**Título en slide —** CIFRADO, IAM AUTH Y STORAGE AUTOSCALING

#### Conceptos

- **Encryption at rest —** protege storage, logs, automated backups, read replicas y snapshots de una DB cifrada.
- **Base existente sin cifrar —** snapshot → copia cifrada → restore para obtener una nueva DB cifrada.
- **IAM DB authentication —** MariaDB, MySQL y PostgreSQL pueden utilizar un token temporal en lugar de una contraseña de base de datos.
- **Storage autoscaling —** aumenta automáticamente el almacenamiento cuando queda poco espacio.
- **No scale-down —** el almacenamiento asignado no disminuye automáticamente después.

> **Nota —** Las AWS KMS keys que protegen el cifrado se estudian en M17. Una snapshot cifrada compartida puede requerir también acceso a la customer managed KMS key correspondiente.

**Docs —** Amazon RDS User Guide — Encrypting Amazon RDS resources  
**Docs —** Amazon RDS User Guide — IAM database authentication  
**Docs —** Amazon RDS User Guide — Storage autoscaling

**Idea visual —** icono oficial de **Amazon RDS** en el centro. Tres ramas — candado `Encryption`, token `IAM DB Authentication` y disco creciendo mediante `Storage Autoscaling`.

### Slide 6 — RDS Custom

**Título en slide —** AMAZON RDS CUSTOM

#### Nombres en portal y examen

> **Amazon RDS Custom**

#### Conceptos

- **Más control —** permite acceso privilegiado al sistema operativo y al entorno de la base.

## Sesión 7.2 — Aurora y el proxy

### Slide 1 — Amazon Aurora

**Título en slide —** AMAZON AURORA

#### Nombres en portal y examen

> **Amazon Aurora** — **Aurora MySQL** — **Aurora PostgreSQL**

#### Conceptos

- **Aurora —** motor relacional administrado compatible con MySQL y PostgreSQL.
- **Storage distribuido —** los datos se mantienen de forma redundante entre tres Availability Zones.
- **Cluster —** writer y Aurora Replicas utilizan el mismo almacenamiento distribuido.
- **Read scaling —** añadir una Aurora Replica no significa crear una copia completa independiente del volumen.

> **Nota —** Aurora Multi-Master dejó de estar disponible en 2023. La arquitectura vigente utiliza un writer por cluster y Aurora Replicas que pueden promocionarse durante un failover.

**Docs —** Amazon Aurora User Guide — What is Amazon Aurora?

### Slide 2 — Endpoints de Aurora

**Título en slide —** WRITER, READER Y CUSTOM ENDPOINT

#### Nombres en portal y examen

> **Writer endpoint** — **Reader endpoint** — **Custom endpoint**

#### Conceptos

- **Writer endpoint —** dirige las conexiones hacia la instancia que actualmente acepta escrituras.
- **Reader endpoint —** distribuye conexiones de lectura entre las Aurora Replicas disponibles.
- **Custom endpoint —** apunta a un subconjunto específico de instancias.
- **Failover —** los endpoints evitan que la aplicación tenga que conocer qué instancia física ocupa cada rol.

> **Nota —** Si el problema es que demasiadas consultas `SELECT` afectan al writer, añade readers y envía las lecturas al **Reader endpoint**.

**Docs —** Amazon Aurora User Guide — Aurora endpoints

**Título en slide —** AURORA SERVERLESS V2

#### Nombres en portal y examen

> **Aurora Serverless v2** — **Aurora Capacity Unit (ACU)**

#### Conceptos

- **Capacidad automática —** compute y memoria aumentan o disminuyen según la carga.
- **ACU —** unidad utilizada para medir la capacidad disponible.
- **Rango —** defines una capacidad mínima y una máxima.
- **Carga variable —** encaja cuando la demanda cambia y no quieres dimensionar una instancia fija para el pico.

> **Nota —** Algunas versiones compatibles pueden configurarse para bajar hasta `0 ACU` y auto-pausar cuando no existe actividad. No asumas que todos los clusters soportan ese mínimo.

### Slide 4 — Aurora Global Database

**Título en slide —** AURORA GLOBAL DATABASE

#### Nombres en portal y examen

> **Aurora Global Database**

#### Conceptos

- **Multi-Region —** una primary Region y clusters secundarios de solo lectura en otras Regions.
- **Local reads —** usuarios globales pueden leer desde una Region cercana.
- **Replicación —** Aurora replica los cambios hacia las Regions secundarias mediante infraestructura dedicada.
- **Regional failure —** una Region secundaria puede promocionarse cuando se necesita recuperar de una caída regional.

> **Nota —** Aurora Global Database replica el **cluster**, no una tabla individual dentro del mismo cluster. Las estrategias completas de disaster recovery se estudian en M20.

### Slide 5 — Amazon RDS Proxy

**Título en slide —** AMAZON RDS PROXY

#### Nombres en portal y examen

> **Amazon RDS Proxy** — **connection pooling**

#### Conceptos

- **Connection pooling —** reutiliza conexiones hacia la base en lugar de abrir una nueva por cada cliente.
- **Escalado —** protege la base cuando muchas aplicaciones o funciones abren conexiones al mismo tiempo.
- **Failover —** puede ayudar a que las aplicaciones gestionen cambios de base con menos interrupción.
- **No es caché —** no guarda resultados de consultas ni reemplaza una read replica.

> **Nota —** Si el problema es **“la base se queda sin conexiones cuando la aplicación escala”**, piensa en RDS Proxy. Si el problema es exceso de lecturas repetidas, piensa en caché o read replicas.

**Docs —** Amazon RDS User Guide — Amazon RDS Proxy

**Idea visual —** icono oficial de **Amazon RDS Proxy** disponible en draw.io como elemento central. Muchas EC2 o funciones llegan al Proxy y desde él salen pocas conexiones reutilizadas hacia **Amazon RDS / Aurora**.

## Sesión 7.3 — ElastiCache

### Slide 1 — Amazon ElastiCache

**Título en slide —** AMAZON ELASTICACHE

#### Nombres en portal y examen

> **Amazon ElastiCache** — **Valkey** — **Redis OSS** — **Memcached**

#### Conceptos

- **ElastiCache —** almacén en memoria administrado para datos que necesitan acceso de muy baja latencia.
- **Database cache —** evita repetir consultas costosas contra la base.
- **Session store —** permite sacar la sesión del disco de las instancias EC2.
- **TTL —** los datos temporales pueden expirar automáticamente.

> **Nota —** ElastiCache no sustituye la base durable. Normalmente se coloca delante de ella para reducir latencia y carga.

**Docs —** Amazon ElastiCache User Guide

**Idea visual —** icono oficial de **Amazon ElastiCache** como elemento central. A la izquierda, varias EC2; a la derecha, Amazon RDS. ElastiCache queda entre ambos como capa rápida de acceso.

---

### Slide 2 — Valkey, Redis OSS o Memcached

**Título en slide —** VALKEY / REDIS OSS FRENTE A MEMCACHED

#### Conceptos

- **Valkey / Redis OSS —** soportan replicación, estructuras de datos avanzadas y opciones de alta disponibilidad.
- **Multi-AZ —** puede distribuir réplicas entre AZ y promover una réplica automáticamente si falla la primary.
- **Memcached —** caché distribuida simple, multithreaded y sin mecanismo de replicación entre nodos.
- **Pérdida aceptable —** Memcached encaja cuando el dato puede reconstruirse desde su fuente original.

> **Nota —** AWS utiliza actualmente **Valkey** además de Redis OSS. Bancos antiguos pueden decir simplemente “Redis”.

**Docs —** Amazon ElastiCache User Guide — Valkey and Redis OSS replication  
**Docs —** Amazon ElastiCache User Guide — Reliability

**Idea visual —** icono oficial de **Amazon ElastiCache** con dos caminos. `Valkey / Redis OSS` muestra primary + replicas en varias AZ. `Memcached` muestra nodos independientes sin flechas de replicación.

---

### Slide 3 — Cache patterns y sesión

**Título en slide —** LAZY LOADING, WRITE-THROUGH Y SESSION STORE

#### Nombres en portal y examen

> **Lazy loading** — **cache-aside** — **write-through**

#### Conceptos

- **Lazy loading —** ante un cache miss, la aplicación consulta la base y guarda el resultado en caché.
- **Write-through —** una escritura actualiza la fuente de datos y también el caché.
- **Session store —** la sesión vive fuera de EC2 para que cualquier instancia pueda atender al usuario.
- **TTL —** limita cuánto tiempo permanece un dato temporal dentro del caché.

> **Nota —** Si la sesión ya está centralizada en ElastiCache, no necesitas sticky sessions para que el usuario vuelva siempre a la misma EC2.

**Idea visual —** icono oficial de **Amazon ElastiCache** entre varias EC2 y Amazon RDS. Un flujo `Cache miss → RDS → Cache` representa lazy loading. Otro `Write → RDS + Cache` representa write-through.

4. An e-commerce application uses an Amazon Aurora Multi-AZ deployment for its database. While analyzing the performance metrics, the engineering team has found that the database reads are causing high input/output (I/O) and are adding latency to the write requests against the database.

5. The DevOps team at a major financial services company uses a Multi-Availability Zone (Multi-AZ) deployment for its MySQL Amazon RDS database in order to automate database replication and to augment data durability. For the coming weekend, the DevOps team has scheduled a maintenance window for a database engine level upgrade.

Which of the following is the correct outcome during the maintenance window?

A) Any database engine level upgrade for an Amazon RDS database instance with Multi-AZ deployment triggers both the primary and standby database instances to be upgraded at the same time. This does not cause any downtime until the upgrade is complete, however

B) Any database engine level upgrade for an Amazon RDS database instance with Multi-AZ deployment triggers the standby database instance to be upgraded first, and the upgrade of the primary database instance follows. This does not cause any downtime for the duration of the upgrade

C) Any database engine level upgrade for an Amazon RDS database instance with Multi-AZ deployment triggers the primary database instance to be upgraded first, and the upgrade of the standby database instance follows. This does not cause any downtime for the duration of the upgrade

D) Both the primary and the standby database instances are upgraded at the same time when any database engine level upgrade runs on an Amazon RDS database instance with Multi-AZ deployment. This causes downtime until the upgrade is complete

✅ **Respuesta —** D

💡 **Explanation —** For a **database engine version upgrade** on a traditional Amazon RDS Multi-AZ DB instance deployment, RDS upgrades the primary and standby DB instances at the same time. Both instances are unavailable during the engine upgrade, so the database experiences downtime until the operation finishes. This differs from certain operating system maintenance events, where RDS can maintain the standby first, fail over, and then maintain the former primary.
