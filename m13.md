## Sesión 13.1 — Lambda

### Slide 1 — AWS Lambda

**Título en slide**

AWS LAMBDA

#### Nombres en portal y examen

> **AWS Lambda** — **execution role** — **synchronous invocation** — **asynchronous invocation**

#### Conceptos

- **AWS Lambda** ejecuta código cuando recibe una invocación o un evento sin que tengas que aprovisionar ni parchear servidores.
- En una invocación **síncrona**, quien llama espera la respuesta de la función.
- En una invocación **asíncrona**, Lambda coloca el evento en una cola interna y el productor no espera a que termine la ejecución.
- Una ejecución de Lambda puede durar como máximo **15 minutos**.
- El **execution role** entrega a la función los permisos que necesita para llamar a otros servicios AWS.

> **Nota**  
> Si un trabajo necesita ejecutarse durante más de 15 minutos, Lambda no es la opción. Un contenedor sobre ECS con Fargate o una instancia EC2 puede manejar procesos más largos.

**Docs**  
[AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html)  
[Invoking Lambda functions](https://docs.aws.amazon.com/lambda/latest/dg/lambda-invocation.html)

### Slide 2 — Reintentos asíncronos

**Título en slide**

REINTENTOS Y DESTINATIONS

#### Conceptos

- Si una invocación asíncrona falla por un error de la función, Lambda vuelve a intentarla de forma automática.
- Por defecto, Lambda realiza **dos reintentos adicionales** cuando el código devuelve un error.
- Una **dead-letter queue** puede conservar eventos que no pudieron procesarse mediante Amazon SQS o Amazon SNS.
- Los **Lambda destinations** pueden registrar el resultado de una invocación asíncrona y enviarlo hacia destinos compatibles cuando termina correctamente o falla.

> **Nota**  
> El comportamiento de una función invocada desde una SQS queue es diferente. En ese caso, un event source mapping lee la cola y la política de redrive de SQS controla cuándo el mensaje termina en una DLQ.

**Docs**

### Slide 3 — Concurrency

**Título en slide**

RESERVED Y PROVISIONED CONCURRENCY

#### Nombres en portal y examen

> **Reserved concurrency** — **provisioned concurrency** — **cold start**

#### Conceptos

- **Reserved concurrency** garantiza capacidad para una función y, al mismo tiempo, limita cuántas ejecuciones concurrentes puede alcanzar.
- Esa capacidad deja de estar disponible para las demás funciones de la cuenta.
- **Provisioned concurrency** mantiene entornos de ejecución inicializados para reducir la latencia de los cold starts.
- Reserved concurrency no tiene un cargo adicional, mientras provisioned concurrency sí genera coste.
- Si utilizas ambas, la provisioned concurrency no puede superar la reserved concurrency configurada.

> **Nota**  
> Reserved concurrency no precalienta la función. Si el objetivo es reducir cold starts, la característica relevante es provisioned concurrency.

**Docs**  
[Lambda concurrency](https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html)

**Logo** `recursos/aws/compute/lambda.svg`

**Idea visual**  
Icono oficial de **AWS Lambda** con una cuota compartida. `Reserved` separa una parte de esa capacidad para una función. `Provisioned` muestra varios execution environments ya preparados antes de recibir tráfico.

### Slide 4 — Lambda en una VPC

**Título en slide**

LAMBDA DENTRO DE UNA VPC

#### Conceptos

- Una función puede conectarse a una VPC cuando necesita acceder a recursos privados como una base de datos.
- Conectar Lambda a una **public subnet** no le entrega automáticamente acceso a Internet.
- Para acceder a Internet mediante IPv4 desde una VPC, la función puede utilizar private subnets cuya ruta salga mediante un **NAT Gateway**.
- Para servicios AWS compatibles, un VPC endpoint puede evitar que el tráfico tenga que salir hacia Internet.

> **Nota**  
> El NAT Gateway y los VPC endpoints se estudian en profundidad en networking. Aquí importa reconocer que una función conectada a una VPC no obtiene salida pública automáticamente.

**Docs**

LAMBDA CON AMAZON EFS

### Slide 6 — Event Source Mapping

**Título en slide**

EVENT SOURCE MAPPING

#### Nombres en portal y examen

> **Event source mapping**

#### Conceptos

- Un **event source mapping** lee registros o mensajes desde determinados servicios y después invoca la función.
- Amazon SQS utiliza este mecanismo para entregar lotes de mensajes hacia Lambda.
- **DynamoDB Streams** también utiliza event source mappings para procesar cambios de una tabla.
- El mapping controla aspectos como el tamaño del batch y el comportamiento de lectura del origen.

> **Nota**  
> La cola o el stream no necesita invocar directamente a Lambda. El event source mapping es quien consulta el origen y administra las invocaciones.

### Slide 7 — Versions y Aliases

**Título en slide**

VERSION Y ALIAS

#### Nombres en portal y examen

> **Version** — **alias**

#### Conceptos

- Una **published version** representa una copia inmutable del código y la configuración de una función.
- Un **alias** es un nombre como `dev`, `test` o `prod` que apunta hacia una versión.
- La aplicación puede invocar el alias sin conocer el número de versión que está detrás.
- Mover el alias hacia otra versión permite cambiar el código que recibe el tráfico sin modificar al cliente.

## Sesión 13.2 — API Gateway

### Slide 1 — Amazon API Gateway

**Título en slide**

AMAZON API GATEWAY

#### Nombres en portal y examen

> **Amazon API Gateway** — **REST API** — **HTTP API** — **WebSocket API**

#### Conceptos

- **Amazon API Gateway** expone endpoints administrados para aplicaciones y servicios.

### Slide 2 — REST API frente a HTTP API

**Título en slide**

REST API O HTTP API

#### Conceptos

- Una **HTTP API** ofrece un conjunto más simple de características y normalmente tiene menor coste.
- Una **REST API** incorpora funciones adicionales como API keys, usage plans, request validation y caché administrada.
- Si el escenario necesita las características avanzadas de REST API, el ahorro de una HTTP API deja de ser el criterio principal.
- Si solo necesitas una API HTTP sencilla con integraciones y autorización compatibles, HTTP API puede reducir complejidad y coste.

> **Nota**  
> La caché administrada de API Gateway está disponible para **REST APIs**, no para HTTP APIs.

**Docs**

### Slide 4 — Edge-optimized, Regional y Private

**Título en slide**

EDGE-OPTIMIZED — REGIONAL — PRIVATE

#### Conceptos

- Un endpoint **edge-optimized** de una REST API utiliza la red de CloudFront administrada por API Gateway para clientes distribuidos geográficamente.
- Un endpoint **Regional** mantiene la API en la Region seleccionada y puede ser apropiado cuando los clientes están cerca de esa Region.
- Una **Private REST API** solo puede invocarse desde una VPC mediante un interface VPC endpoint.
- Las HTTP APIs son Regional y no ofrecen los tipos edge-optimized o private.

> **Nota**  
> Para un custom domain edge-optimized, el certificado de AWS Certificate Manager debe estar en `us-east-1`. Para un Regional custom domain, el certificado debe estar en la misma Region que la API.

**Título en slide**

CACHE Y RESOURCE POLICY

#### Conceptos

- Una REST API puede guardar temporalmente respuestas en un **API cache** para reducir llamadas al backend y mejorar latencia.

- Una **resource policy** puede controlar quién tiene permiso para invocar una API.
- La policy puede utilizar condiciones como cuentas AWS, VPC endpoints o rangos de IP según el escenario.

> **Nota**  
> La caché de API Gateway no es Amazon CloudFront. Son capas diferentes y pueden existir en arquitecturas distintas.

## Sesión 13.3 — DynamoDB

### Slide 1 — Amazon DynamoDB

**Título en slide**

AMAZON DYNAMODB

#### Nombres en portal y examen

> **Amazon DynamoDB** — **partition key** — **sort key** — **on-demand** — **provisioned**

#### Conceptos

- **Amazon DynamoDB** es una base NoSQL administrada de tipo key-value y document.
- La tabla distribuye automáticamente los datos entre infraestructura de varias Availability Zones dentro de una Region.
- En **on-demand capacity mode** pagas por las solicitudes realizadas y DynamoDB adapta la capacidad automáticamente.
- En **provisioned capacity mode** defines capacidad de lectura y escritura mediante RCU y WCU.
- DynamoDB está diseñado para ofrecer latencias de milisegundos de un solo dígito a escala.

> **Nota**  
> Si el escenario necesita un modelo relacional con JOINs y relaciones complejas, piensa primero en una base relacional. DynamoDB sí soporta transacciones, pero su modelo sigue siendo NoSQL.

**Docs**  
[What is Amazon DynamoDB?](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html)

**Título en slide**

DYNAMODB ENCRYPTION AT REST

#### Conceptos

- DynamoDB cifra los datos en reposo de forma predeterminada y el cifrado no puede deshabilitarse.
- La opción predeterminada utiliza una **AWS owned key** administrada por DynamoDB.

- Una customer managed key ofrece control directo sobre la key policy y las operaciones de AWS KMS pueden auditarse.

> **Nota**

### Slide 3 — PITR y backups

**Título en slide**

PITR Y ON-DEMAND BACKUP

#### Nombres en portal y examen

> **Point-in-time recovery (PITR)** — **on-demand backup** — **deletion protection**

#### Conceptos

- **Point-in-time recovery** mantiene backups continuos y permite recuperar la tabla a un punto elegido dentro de la ventana configurada.
- La ventana de PITR puede configurarse hasta un máximo de **35 días**.
- Un restore de PITR crea una **nueva tabla** y no sobrescribe directamente la tabla original.
- Un **on-demand backup** conserva un snapshot explícito de la tabla hasta que lo eliminas.
- **Deletion protection** evita eliminar accidentalmente la tabla, pero no reemplaza un backup.

> **Nota**  
> Si descubres datos corruptos y necesitas regresar justo al momento anterior al error, PITR es la opción diseñada para ese escenario.

**Docs**  
[Point-in-time recovery for DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/PointInTimeRecovery_Howitworks.html)

**Logo** `recursos/aws/database/dynamodb.svg`

**Idea visual**  
Icono oficial de **Amazon DynamoDB** sobre una línea temporal. Se selecciona un instante anterior al error y desde allí nace una nueva tabla restaurada.

### Slide 4 — GSI frente a LSI

**Título en slide**

GSI FRENTE A LSI

#### Nombres en portal y examen

> **Global secondary index (GSI)** — **Local secondary index (LSI)**

#### Conceptos

- Un **GSI** puede utilizar una partition key y una sort key diferentes de las de la tabla base.
- Los GSIs pueden crearse después de que la tabla ya exista.
- Las lecturas desde un GSI son siempre **eventually consistent**.
- Un **LSI** conserva la misma partition key de la tabla y utiliza una sort key diferente.
- Los LSIs deben definirse cuando se crea la tabla y pueden utilizar strongly consistent reads.

> **Nota**  
> Si necesitas añadir posteriormente una nueva forma de acceso basada en otra partition key, piensa en un **GSI**.

**Docs**  
[DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html)

**Logo** `recursos/aws/database/dynamodb.svg`

**Idea visual**  
Tabla principal con `PK = UserID`. Un GSI al lado utiliza otra partition key y muestra `Can add later`. Un LSI debajo conserva `UserID` y muestra `Create with table`.

### Slide 5 — DynamoDB Streams

**Título en slide**

DYNAMODB STREAMS

#### Nombres en portal y examen

> **DynamoDB Streams**

#### Conceptos

- **DynamoDB Streams** registra los cambios de items de una tabla en near real time.
- Puede registrar inserts, updates y deletes según la configuración seleccionada.
- Los stream records permanecen disponibles durante **24 horas**.
- AWS Lambda puede procesarlos mediante un event source mapping.
- Si necesitas una retención más larga o un modelo de streaming con más consumidores, DynamoDB también puede integrarse con **Kinesis Data Streams for DynamoDB**.

> **Nota**  
> DynamoDB Streams es un registro de cambios. No es una read replica de la tabla.

### Slide 6 — DynamoDB Accelerator

**Título en slide**

DYNAMODB ACCELERATOR (DAX)

#### Nombres en portal y examen

> **DynamoDB Accelerator (DAX)**

#### Conceptos

- **DAX** es una caché administrada en memoria diseñada específicamente para Amazon DynamoDB.
- Puede reducir lecturas eventually consistent desde milisegundos a microsegundos.

> **Nota**  
> DAX acelera el acceso a DynamoDB. Amazon ElastiCache sigue siendo una solución más general para otros patrones de caché, como sesiones de una aplicación.

### Slide 7 — Global Tables

**Título en slide**

DYNAMODB GLOBAL TABLES

#### Nombres en portal y examen

> **Global tables** — **multi-Region eventual consistency (MREC)** — **multi-Region strong consistency (MRSC)**

#### Conceptos

- **Global Tables** replica una tabla DynamoDB entre varias AWS Regions.
- Cada replica puede atender solicitudes locales y reduce la distancia entre usuarios y datos.
- El modelo **MREC** utiliza replicación multi-Region con consistencia eventual entre Regions.
- DynamoDB también ofrece **MRSC** para strong consistency entre Regions dentro de los conjuntos de Regions compatibles.
- MRSC tiene restricciones adicionales y no está disponible para cualquier combinación de Regions.

> **Nota**  
> En preguntas tradicionales de SAA, Global Tables suele aparecer como una solución multi-Region active-active con lectura y escritura local. MRSC es una capacidad más reciente que conviene reconocer sin asumir que está disponible en todas las Regions.

**Docs**  
[Using DynamoDB global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-global-table-design.html)

**Logo** `recursos/aws/database/dynamodb.svg`

**Idea visual**  
Dos AWS Regions contienen el mismo icono oficial de **Amazon DynamoDB** y flechas bidireccionales representan la replicación. Una etiqueta muestra `MREC`, y una segunda opción pequeña indica `MRSC — supported Region sets`.

### Slide 8 — TTL

**Título en slide**

DYNAMODB TIME TO LIVE (TTL)

#### Nombres en portal y examen

> **Time to Live (TTL)**

#### Conceptos

- **TTL** permite definir en cada item una fecha de expiración mediante un atributo almacenado en Unix epoch time.
- Cuando el timestamp vence, DynamoDB marca el item para eliminación automática.
- La eliminación no ocurre necesariamente en el segundo exacto de expiración y normalmente se completa durante los días siguientes.
- El proceso de TTL no consume write throughput para la eliminación original en la tabla donde expira el item.

> **Nota**  
> TTL sirve para eliminar datos que ya no son necesarios. No crea una copia ni sustituye un backup.

**Docs**  
[Using time to live in DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html)

**Logo** `recursos/aws/database/dynamodb.svg`

**Idea visual**  
Un item de DynamoDB contiene `expiresAt = epoch`. Al pasar el reloj por esa fecha, el item queda marcado como expirado y posteriormente desaparece.

**Título en slide**

ARQUITECTURA, API, FUNCIÓN, TABLA

#### Conceptos

- El cliente envía una solicitud síncrona hacia Amazon API Gateway.
- API Gateway invoca AWS Lambda y espera su respuesta.
- La función utiliza su execution role para leer o escribir en Amazon DynamoDB.
- La arquitectura no necesita instancias EC2.

> **Nota**  
> Este es el camino síncrono del módulo. El cliente espera a que la operación termine y reciba una respuesta.

**Idea visual**

1. Cliente → icono oficial de **Amazon API Gateway**.
2. API Gateway → icono oficial de **AWS Lambda**.
3. Lambda → icono oficial de **Amazon DynamoDB**.
4. Sobre la flecha Lambda → DynamoDB aparece `Execution Role`.
5. No aparece Amazon EC2.

### Slide 2 — Cola que llama a la función

**Título en slide**

ARQUITECTURA, COLA Y FUNCIÓN

#### Conceptos

- Un productor deja un mensaje en una Amazon SQS queue y continúa sin esperar a que el trabajo termine.
- Un event source mapping lee mensajes de la cola e invoca AWS Lambda en batches.
- La función procesa los mensajes y SQS vuelve a mostrar los que no se eliminan correctamente.
- Después de suficientes fallos, la redrive policy puede mover el mensaje hacia una DLQ.

> **Nota**  
> Este es el camino asíncrono del módulo. Amazon API Gateway no es necesario en este dibujo.

**Idea visual**

1. Productor → icono oficial de **Amazon SQS**.
2. SQS → `Event Source Mapping` → icono oficial de **AWS Lambda**.
3. La cola tiene una segunda flecha hacia una `DLQ`.
4. Amazon API Gateway no aparece.

2. Una startup ha detectado, a través de su equipo de producto, una necesidad de mercado para admitir comunicaciones cliente-servidor con estado y sin estado en las API desarrolladas con su plataforma. Te contratan como arquitecto de soluciones para cubrir esa necesidad con Amazon API Gateway.

¿Cuál de las siguientes identificarías como correcta?

A) API Gateway crea API RESTful que permiten la comunicación cliente-servidor sin estado y, además, crea API WebSocket que siguen el protocolo WebSocket, el cual permite la comunicación dúplex completa con estado entre cliente y servidor

B) API Gateway crea API RESTful que permiten la comunicación cliente-servidor sin estado y, además, crea API WebSocket que siguen el protocolo WebSocket, el cual permite la comunicación sin estado y full-duplex entre cliente y servidor

C) API Gateway crea API RESTful que permiten la comunicación cliente-servidor con estado y, además, crea API WebSocket que siguen el protocolo WebSocket, el cual permite la comunicación con estado y dúplex completo entre cliente y servidor

D) API Gateway crea API RESTful que permiten la comunicación cliente-servidor con estado y, además, crea API WebSocket que siguen el protocolo WebSocket, el cual permite la comunicación sin estado y full-duplex entre cliente y servidor

✅ **Respuesta** A

💡 **Explicación**  
Las APIs RESTful siguen normalmente un modelo **stateless** en el que cada request contiene la información necesaria para procesarse. Una **WebSocket API** mantiene una conexión abierta y permite comunicación bidireccional full-duplex entre cliente y servidor, por lo que soporta interacciones con estado durante la conexión.

En el rol de arquitecto de soluciones, ¿qué base de datos recomiendas para estos requisitos?

4. Como arquitecto de soluciones te han contratado para asesorar a una empresa sobre los distintos mecanismos de autenticación y autorización que ofrece AWS para autorizar una llamada a la API dentro de API Gateway. La empresa preferiría una solución que ofrezca gestión de usuarios integrada.

¿Cuál de las siguientes soluciones sugerirías como la más adecuada para el caso de uso planteado?

A) Utilizar la autorización AWS_IAM

B) Utilizar Amazon Cognito User Pools (Grupos de usuarios de Amazon Cognito)

C) Utilizar los Pools de Identidad de Amazon Cognito

D) Utilizar el autorizador Lambda de API Gateway

✅ **Respuesta** B

💡 **Explicación**  
Un **Amazon Cognito User Pool** proporciona un directorio de usuarios administrado con capacidades de registro, inicio de sesión y emisión de tokens. API Gateway puede validar esos tokens para autorizar llamadas a una API. Un identity pool tiene otro propósito y entrega credenciales temporales de AWS después de que el usuario ya cuenta con una identidad autenticada.

El equipo de desarrollo del fabricante descarta cualquier opción que obligue a aprovisionar la capacidad a mano, porque no desea reaccionar de forma manual ante los volúmenes cambiantes de datos de los sensores.

Con estas restricciones, ¿cuál de las siguientes soluciones es la MEJOR para desarrollar ese servicio de coche como sensor?

A) Ingerir los datos del sensor en Kinesis Data Streams sondeado por una aplicación que se ejecuta en una instancia EC2, y escribir esos datos en una tabla DynamoDB autoescalada para el procesamiento posterior

B) Ingerir los datos del sensor en Kinesis Data Firehose para que escriba los datos directamente en una tabla DynamoDB autoescalada destinada al procesamiento posterior

1. A data analytics company manages an application that stores user data in an Amazon DynamoDB table. The development team has observed that, once in a while, the application writes corrupted data into the Amazon DynamoDB table. As soon as the issue is detected, the team needs to remove the corrupted data as early as possible.

What do you recommend?

A) Use Amazon DynamoDB Streams to restore the table to the state just before the corrupted data was written

B) Use Amazon DynamoDB point-in-time recovery to restore the table to the state just before the corrupted data was written

C) Configure the Amazon DynamoDB table as a global table, and point the application to the table in another AWS Region that has no corrupted data

D) Use Amazon DynamoDB on-demand backup to restore the table to the state just before the corrupted data was written

✅ **Respuesta** B

💡 **Explanation**  
**Amazon DynamoDB point-in-time recovery** maintains continuous backups and lets the team restore the table to a selected second within the available recovery window. This makes it possible to create a restored table representing the state immediately before the corrupted write occurred. DynamoDB Streams records changes but does not provide a direct table rollback mechanism.

Which of the following would you identify as correct?

A) Amazon API Gateway creates RESTful APIs that enable stateful client-server communication, and Amazon API Gateway also creates WebSocket APIs that adhere to the WebSocket protocol, which enables stateful, full-duplex communication between client and server

5. A leading carmaker wants to build a new car-as-a-sensor service from fully serverless components that AWS provisions and manages automatically. The development team at the carmaker does not want a design that requires capacity to be provisioned manually, because the team does not want to respond manually when the volume of sensor data changes.

Given these constraints, which solution is the BEST fit for developing this car-as-a-sensor service?

A) Ingest the sensor data into Amazon Kinesis Data Firehose, which writes the data directly into an auto-scaled Amazon DynamoDB table for downstream processing

B) Ingest the sensor data into an Amazon Simple Queue Service (Amazon SQS) standard queue. An AWS Lambda function polls that queue in batches and writes the data into an auto-scaled Amazon DynamoDB table for downstream processing

C) Ingest the sensor data into Amazon Kinesis Data Streams. An application running on an Amazon EC2 instance polls the stream and writes the data into an auto-scaled Amazon DynamoDB table for downstream processing

D) Ingest the sensor data into an Amazon Simple Queue Service (Amazon SQS) standard queue. An application running on an Amazon EC2 instance polls that queue and writes the data into an auto-scaled Amazon DynamoDB table for downstream processing

✅ **Respuesta** B

💡 **Explanation**  
The **Amazon SQS + AWS Lambda + Amazon DynamoDB** combination avoids EC2 instances and keeps the processing layer fully managed. Lambda polls SQS through an event source mapping and processes messages in batches, while DynamoDB provides a managed NoSQL data store that can adapt to changing workload volumes.
