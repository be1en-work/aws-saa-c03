## Sesión 14.1 | Elegir motor

### Slide 1 | Antes de un motor nuevo

**Título en slide**

ANTES DE UN MOTOR NUEVO

#### Conceptos

- Antes de elegir un motor especializado, comprueba si el dato ya encaja en RDS, Aurora, DynamoDB, S3 o ElastiCache.
- Los servicios de este módulo aparecen cuando el escenario necesita patrones como streaming, documentos, grafos, Cassandra, SQL sobre S3 o análisis OLAP.

| El enunciado sugiere | Hogar habitual |
|---|---|
| SQL, JOIN, transacciones OLTP | RDS o Aurora |
| Clave-valor, cualquier ritmo, millones de peticiones | DynamoDB |
| Objeto, data lake, archivo, informe estático | S3 |
| Sesión de usuario o caché de lectura caliente | ElastiCache |
| Stream masivo, varios consumidores, replay | Kinesis Data Streams (este módulo) |
| Cargar stream en S3/Redshift/OpenSearch sin código consumidor | Data Firehose (este módulo) |
| SQL ad hoc sobre archivos en S3 sin clúster | Athena (este módulo) |
| Data warehouse OLAP, BI pesado | Redshift (este módulo) |

- Elegir Redshift o EMR para una consulta puntual sobre un archivo en S3 suele añadir infraestructura y costo innecesarios.

> **Nota**  
> La tabla conserva los nombres del material original. **Kinesis Data Firehose** se denomina actualmente **Amazon Data Firehose**.

> **Idea visual**  
> Servicios ya conocidos a la izquierda y motores especializados a la derecha. Flecha `si ya encaja → no cambies de motor`.

## Sesión 14.3 | Ingesta en tiempo real

### Slide 1 | Kinesis Data Streams en analítica

**Título en slide**

KINESIS DATA STREAMS EN ANALÍTICA

#### Nombres en portal y examen

> **Amazon Kinesis Data Streams**  
> **Shard**  
> **Partition key**  
> **Replay**

#### Conceptos

- Kinesis Data Streams ya apareció como alternativa a colas y temas. Aquí importa su uso como fuente para **varios consumidores y analítica en tiempo real**.
- Los registros permanecen disponibles durante **24 horas por defecto** y la retención puede ampliarse hasta **365 días**.
- Leer un registro no lo elimina y los consumidores pueden volver a posiciones anteriores mientras los datos sigan retenidos.
- Una misma partition key mantiene el orden relativo de sus registros dentro del stream.

> **Nota numérica**  
> El tamaño máximo actual del payload de un registro es de **10 MiB**. Los registros entre **1 MiB y 10 MiB** están pensados para cargas grandes ocasionales.

> **Idea visual**  
> Stream central → Lambda, Flink y aplicación propia leyendo simultáneamente.

### Slide 2 | Kinesis Provisioned

**Título en slide**

KINESIS PROVISIONED

#### Nombres en portal y examen

> **Provisioned mode** / **Modo aprovisionado**  
> **Shard**

#### Conceptos

- En Provisioned mode defines el número de **shards** y eres responsable de ajustar la capacidad cuando cambia el tráfico.
- Cada shard admite hasta **1 MB/s o 1000 registros/s de escritura** y hasta **2 MB/s de lectura**.
- El throughput total del stream aumenta al incrementar el número de shards.
- Superar la capacidad disponible puede generar `ProvisionedThroughputExceededException`.

> **Operación importante**  
> `UpdateShardCount` permite aumentar o reducir el número de shards de un stream provisioned.

> **Idea visual**  
> Tres shards con etiquetas `1 MB/s write`, `1000 records/s` y `2 MB/s read`.

---

### Slide 3 | Kinesis On-Demand

**Título en slide**

KINESIS ON-DEMAND

#### Nombres en portal y examen

> **On-demand mode** / **Modo bajo demanda**

#### Conceptos

- On-demand elimina la planificación manual de shards y Kinesis ajusta automáticamente la capacidad según la demanda.
- Un stream nuevo comienza con hasta **4 MB/s de escritura y 8 MB/s de lectura**.
- Puede absorber hasta aproximadamente **2 veces el pico de escritura observado durante los últimos 30 días**.
- Si el tráfico supera más del doble del pico previo en menos de **15 minutos**, puede existir throttling temporal mientras el stream escala.

> **Nota numérica**  
> Un stream puede cambiar entre Provisioned y On-demand hasta **2 veces dentro de 24 horas**.

> **Idea visual**  
> Gráfica irregular con capacidad creciendo automáticamente alrededor del tráfico.

### Slide 4 | Consumidores Kinesis

**Título en slide**

CONSUMIDORES KINESIS

#### Nombres en portal y examen

> **Shared throughput** / **Throughput compartido**  
> **Enhanced fan-out**  
> `GetRecords`  
> `SubscribeToShard`

#### Conceptos

- Los consumidores tradicionales utilizan `GetRecords` y comparten hasta **2 MB/s de lectura por shard**.
- **Enhanced fan-out** proporciona hasta **2 MB/s por shard dedicados a cada consumidor registrado**.
- Enhanced fan-out utiliza `SubscribeToShard` y evita que varias aplicaciones compitan por el mismo throughput.
- Los streams Provisioned y On-demand Standard admiten hasta **20 consumidores registrados**.

> **Nota**  
> Enhanced fan-out resulta especialmente útil cuando varias aplicaciones necesitan procesar el mismo flujo de forma independiente.

> **Idea visual**  
> Throughput compartido en una sola tubería frente a una tubería independiente para cada consumidor EFO.

### Slide 5 | Amazon Data Firehose

**Título en slide**

AMAZON DATA FIREHOSE

#### Nombres en portal y examen

> **Amazon Data Firehose**  
> **Firehose stream**  
> **Kinesis Data Firehose** / **Nombre anterior**

#### Conceptos

- **Amazon Data Firehose** entrega datos de streaming hacia destinos sin que tengas que desarrollar y escalar un consumidor propio.
- Puede cargar información en Amazon S3, Amazon Redshift, Amazon OpenSearch Service, Splunk y endpoints HTTP compatibles.
- AWS Lambda puede transformar registros antes de la entrega y Firehose puede convertir formatos para determinados destinos.
- Firehose utiliza buffering y entrega los datos cuando se alcanza el tamaño o el intervalo configurado.

> **Nota numérica**  
> Para destinos como S3, Redshift y OpenSearch, el intervalo de buffering puede configurarse entre **0 y 900 segundos** y el valor predeterminado habitual es **300 segundos**.

> **Nota de transformación**  
> Cuando Firehose utiliza Lambda para transformación, el intervalo de buffering admite entre **0 y 900 segundos** y normalmente utiliza **60 segundos** por defecto.

> **Logo** `recursos/aws/otros/data-firehose.svg`

> **Idea visual**  
> Productores o Data Streams → Amazon Data Firehose → S3, Redshift y OpenSearch.

### Slide 6 | Data Streams frente a Firehose

**Título en slide**

DATA STREAMS VS FIREHOSE

#### Nombres en portal y examen

> **Amazon Kinesis Data Streams**  
> **Amazon Data Firehose**

#### Conceptos

| | Data Streams | Data Firehose |
|---|---|---|
| Rol | Recoger y **retener** stream; **tú** programas consumidor | **Cargar** stream hacia S3, Redshift, OpenSearch, HTTP, terceros |
| Gestión consumidor | Código / Lambda / Flink | **Totalmente gestionado**, sin consumidor tuyo |
| Tiempo | **Tiempo real** | **Casi** tiempo real (buffer por tamaño/tiempo) |
| Almacén en el servicio | Hasta **365 días** | **Sin** almacén largo en Firehose |
| Replay | **Sí** | **No** |
| Escalado | Shards aprovisionados u on-demand | **Automático**, serverless |

- Si varias aplicaciones necesitan consumir el mismo flujo o volver a procesar registros anteriores, la opción es **Kinesis Data Streams**.
- Si el objetivo es cargar continuamente el flujo en un destino con mínima administración, utiliza **Amazon Data Firehose**.

> **Nota**  
> La tabla se mantiene exactamente como en el MD original. El nombre actual de Kinesis Data Firehose es **Amazon Data Firehose**.

> **Idea visual**  
> Dos caminos desde un productor. Uno hacia aplicaciones consumidoras y otro hacia almacenamiento analítico.

### Slide 5 | Rendimiento en Athena

**Título en slide**

ATHENA Y DATOS ESCANEADOS

#### Nombres en portal y examen

> **Partitioning** / **Particionamiento**  
> **Apache Parquet**  
> **Apache ORC**

#### Conceptos

- Athena cobra según los datos escaneados cuando utilizas el modelo por consulta, por lo que reducir los bytes leídos disminuye costo y latencia.

- Particionar los objetos por fecha, región u otra clave evita escanear datos que no forman parte de la consulta.
- Compresión y evitar `SELECT *` también ayudan a reducir la cantidad de información procesada.

> **Ejemplo**

### Slide 8 | Redshift Multi-AZ y snapshots

**Título en slide**

REDSHIFT MULTI-AZ Y SNAPSHOTS

#### Conceptos

- Los clusters provisionados **RG o RA3 compatibles** pueden utilizar un despliegue Multi-AZ con cómputo activo en **2 Availability Zones**.
- El data warehouse utiliza un único endpoint y puede continuar procesando workloads si una de las Availability Zones falla.
- La retención de snapshots automáticos para tipos compatibles puede configurarse entre **1 y 35 días**.
- Los snapshots pueden copiarse a otra región cuando el diseño necesita recuperación ante un fallo regional.

> ⚠️ **Nota de vigencia**  
> Material antiguo puede indicar que Amazon Redshift no dispone de Multi-AZ. Esa afirmación ya no es correcta.

> **AWS Quick Sight**  
> **Amazon QuickSight** / **Nombre histórico**  
> **SPICE**

#### Conceptos

- **AWS Quick Sight** es la capacidad de business intelligence y visualización incluida actualmente dentro de AWS Quick.
- Permite crear dashboards y análisis utilizando fuentes como Athena, Redshift, RDS, Aurora y OpenSearch.
- **SPICE** es su motor en memoria para acelerar cálculos y visualizaciones sobre datasets importados.
- Quick Sight visualiza y analiza información, pero no sustituye el motor que consulta o almacena originalmente los datos.

> ⚠️ **Nota de vigencia**  
> Amazon Quick pasó a llamarse **AWS Quick el 9 de noviembre de 2026** y Amazon Quick Sight pasó a llamarse **AWS Quick Sight**.  
> El SAA-C03 y bancos anteriores todavía pueden mostrar **Amazon QuickSight**.

> **Logo** `recursos/aws/analytics/quicksight.svg`

> **Idea visual**  
> Athena y Redshift → SPICE → dashboards de AWS Quick Sight.

## Sesión 14.5 | Arquitecturas

### Slide 1 | Ingesta hacia S3 y Athena

**Título en slide**

INGESTA A S3 Y ATHENA

#### Conceptos

- Amazon Data Firehose recibe datos de streaming y los entrega de forma administrada hacia un bucket Amazon S3.
- AWS Glue Data Catalog describe los archivos y Amazon Athena permite consultarlos mediante SQL sin mantener un clúster.
- Formatos columnares, compresión y particionamiento disminuyen los datos que Athena necesita escanear.
- AWS Quick Sight puede añadirse cuando el escenario requiere dashboards sobre los resultados analíticos.

> **Idea visual**
>
> 1. Productores → Amazon Data Firehose.
> 2. Data Firehose → Amazon S3.
> 3. AWS Glue crawler → Glue Data Catalog.
> 4. Amazon Athena → Amazon S3.
> 5. AWS Quick Sight en gris como capa opcional de BI.

### Slide 2 | Stream con varios consumidores

**Título en slide**

STREAM CON VARIOS CONSUMIDORES

#### Conceptos

- Los productores escriben eventos en Amazon Kinesis Data Streams utilizando partition keys apropiadas.
- Varias aplicaciones pueden leer los mismos registros sin eliminarlos para los demás consumidores.
- Enhanced fan-out proporciona hasta **2 MB/s por shard y consumidor registrado** cuando cada aplicación necesita throughput dedicado.
- La retención permite volver a procesar eventos anteriores mientras continúen disponibles en el stream.

> **Idea visual**
>
> 1. Productores → Kinesis Data Streams.
> 2. Data Streams → AWS Lambda.
> 3. Data Streams → Amazon Managed Service for Apache Flink.
> 4. Data Streams → aplicación custom.
> 5. Los tres consumidores reciben el mismo flujo.

---

### Slide 3 | Analítica en tiempo real con Flink

**Título en slide**

STREAM Y APACHE FLINK

#### Conceptos

- Amazon Kinesis Data Streams recibe los eventos y conserva el flujo para uno o varios consumidores.
- Amazon Managed Service for Apache Flink ejecuta ventanas, agregaciones y procesamiento con estado sobre esos eventos.
- El resultado puede escribirse en un datastore que una aplicación consulte posteriormente con baja latencia.
- Si únicamente necesitas entregar el flujo hacia S3 con mínima lógica propia, Amazon Data Firehose ofrece un diseño más simple.

> **Idea visual**
>
> 1. Productores → Kinesis Data Streams.
> 2. Data Streams → Amazon Managed Service for Apache Flink.
> 3. Flink → almacén de resultados.
> 4. API o aplicación → almacén de resultados.

¿Qué servicios de AWS utilizarías para crear la solución más rentable con el MENOR mantenimiento de la infraestructura?

A) Ingerir los datos en Kinesis Data Firehose y, con una función Lambda intermedia, filtrar y transformar el flujo entrante antes de volcar la salida en S3

2. A big data consulting firm needs to set up a data lake on Amazon S3 for a Health-Care client. The data lake is split into raw and refined zones. For compliance reasons, the source data has to be kept for a minimum of 5 years. Source data arrives in the raw zone and is then processed by an AWS Glue based extract, transform, and load (ETL) job into the refined zone. Business analysts run ad-hoc queries only on the data in the refined zone, using Amazon Athena. The team is concerned about storage cost in both the raw and refined zones, because the data is increasing at a rate of 1 terabyte daily in each zone.

As a solutions architect, which of the following would you recommend as the MOST cost-optimal solution? (Select two)

A) Set up a lifecycle policy that transitions the raw zone data into Amazon S3 Glacier Deep Archive after 1 day of object creation
B) Create a job based on an AWS Lambda function to delete the raw zone data after 1 day
C) Set up a lifecycle policy that transitions the refined zone data into Amazon S3 Glacier Deep Archive after 1 day of object creation
D) Use an AWS Glue ETL job to write the transformed data in the refined zone in CSV format
E) Use an AWS Glue ETL job to write the transformed data in the refined zone in a compressed file format

✅ **Respuesta:** A,E

💡 **Explanation**  
The raw data must remain available for at least **5 years**, so moving it to a lower-cost archival storage class preserves the required retention. Compressing refined data reduces both storage and the amount of data that Athena needs to scan.
