## Sesión 10.1 — Amazon CloudFront

### Slide 1 — Amazon CloudFront

**Título en slide**

AMAZON CLOUDFRONT

#### Nombres en portal y examen

> **Amazon CloudFront**  
> **Content Delivery Network (CDN)** / **Red de entrega de contenidos**  
> **Edge location** / **Ubicación de borde**

#### Conceptos

- **Amazon CloudFront** acerca contenido a los usuarios mediante edge locations distribuidas globalmente.
- El primer acceso puede llegar al origen y guardar el objeto en caché. Los siguientes pueden responder desde el borde.
- Trabaja con contenido servido mediante **HTTP y HTTPS**.
- Reduce latencia y solicitudes repetidas hacia el origen.
- También puede acelerar APIs y contenido dinámico aunque no todo tenga que almacenarse en caché.
- **AWS Shield Standard** aporta protección DDoS básica sin coste adicional.

> **Nota**  
> CloudFront no sustituye Route 53. Route 53 resuelve DNS y CloudFront entrega contenido desde la red de borde.

### Slide 2 — Orígenes y rutas

**Título en slide**

ORÍGENES Y RUTAS

#### Nombres en portal y examen

> **Origin** / **Origen**  
> **Cache behavior** / **Comportamiento de caché**  
> **Custom origin** / **Origen personalizado**  
> **VPC origin** / **Origen en VPC**

#### Conceptos

- Un bucket **Amazon S3** puede funcionar como origen para contenido estático.
- Un origen HTTP(S) puede ser un ALB, NLB, EC2 o un servidor externo.
- Un **VPC origin** permite utilizar ALB, NLB o EC2 en subredes privadas.
- Un servidor on-premises puede utilizarse como custom origin si dispone de un nombre DNS público resoluble.
- Una distribución puede usar varios orígenes mediante rutas como `/static/* → S3` y `/api/* → ALB`.
- S3 CRR replica objetos entre Regions. CloudFront los cachea cerca de los usuarios.

> **Nota**  
> Un bucket S3 configurado como **website endpoint** se trata como custom origin. Ese endpoint no admite OAC ni OAI.

### Slide 3 — Caché, TTL e invalidación

**Título en slide**

CACHÉ, TTL E INVALIDACIÓN

#### Nombres en portal y examen

> **Cache hit** / **Acierto de caché**  
> **Cache miss** / **Fallo de caché**  
> **Time to Live (TTL)** / **Tiempo de vida**  
> **Cache invalidation** / **Invalidación de caché**

#### Conceptos

- En un **cache hit**, CloudFront responde desde el edge sin consultar el origen.
- En un **cache miss**, solicita el objeto al origen y puede guardarlo en caché.
- El Default TTL predeterminado es **86 400 s, 24 horas** cuando no existe otra configuración aplicable.
- El Maximum TTL predeterminado es **31 536 000 s, 365 días**.
- Si Minimum TTL, Default TTL y Maximum TTL están en `0`, la caché queda deshabilitada.
- Las primeras **1 000 rutas de invalidación al mes** por cuenta AWS son gratuitas.

> **Nota**  
> Una ruta con wildcard como `/images/*` cuenta como **1 ruta de invalidación**, aunque elimine miles de objetos de la caché.

> **Logo** `recursos/aws/networking/cloudfront.svg`

> **Idea visual**  
> Edge con caché. Flecha `Hit` hacia el usuario y `Miss` hacia S3. Al lado `Default TTL · 86 400 s` y una escoba sobre `/images/*`.

### Slide 4 — Origin Group

**Título en slide**

ORIGIN GROUP

#### Nombres en portal y examen

> **Origin group** / **Grupo de orígenes**  
> **Primary origin** / **Origen primario**  
> **Secondary origin** / **Origen secundario**

#### Conceptos

- Un **origin group** utiliza **2 orígenes**, uno primario y otro secundario.
- Si el primario falla durante un cache miss, CloudFront puede enviar la solicitud al secundario.
- Puedes activar el failover para códigos `400`, `403`, `404`, `416`, `429`, `500`, `502`, `503` y `504`.
- El failover solo funciona para solicitudes **GET, HEAD y OPTIONS**.
- El usuario continúa utilizando la misma distribución CloudFront.
- No es un failover DNS de Route 53.

> **Nota**  
> Cada nueva solicitud intenta primero el origen primario. CloudFront no convierte permanentemente al secundario en primario después de un fallo.

> **Logo** `recursos/aws/networking/cloudfront.svg`

> **Idea visual**  
> Usuario → CloudFront → `Primary Origin`. El primario aparece con una X y CloudFront reintenta hacia `Secondary Origin`. Utilizar iconos oficiales de S3 o ALB según el ejemplo.

### Slide 5 — Restricción geográfica

**Título en slide**

RESTRICCIÓN GEOGRÁFICA

#### Nombres en portal y examen

> **Geographic restriction / Geo-restriction** / **Restricción geográfica**  
> **Allow list** / **Lista de permitidos**  
> **Deny list** / **Lista de bloqueo**

#### Conceptos

- CloudFront puede permitir o bloquear contenido según el **país** del usuario.
- Una allow list permite únicamente los países definidos.
- Una deny list bloquea países concretos y permite el resto.
- Un usuario bloqueado recibe una respuesta HTTP **403 Forbidden**.
- La restricción geográfica integrada se aplica al contenido de la distribución a nivel de país.
- CloudFront utiliza una base Geo-IP para determinar la ubicación.

> **Nota**  
> Route 53 Geolocation envía al usuario hacia otro endpoint. CloudFront geo-restriction bloquea o permite la petición.

> **Logo** `recursos/aws/networking/cloudfront.svg`

> **Idea visual**  
> Mapa con países permitidos y bloqueados. Un usuario bloqueado llega al edge y recibe `403`, sin flecha hacia el origen.

### Slide 6 — OAC y OAI

**Título en slide**

OAC Y OAI

#### Nombres en portal y examen

> **Origin Access Control (OAC)** / **Control de acceso al origen**  
> **Origin Access Identity (OAI)** / **Identidad de acceso al origen**

#### Conceptos

- El patrón recomendado usa un bucket S3 **privado** detrás de CloudFront.
- **OAC** permite que CloudFront acceda al bucket mediante una bucket policy.
- OAC es el mecanismo recomendado para diseños nuevos.
- Soporta escenarios como **SSE-KMS** y solicitudes dinámicas hacia S3.
- **OAI** es el mecanismo anterior y todavía puede aparecer en bancos y arquitecturas legacy.
- El usuario accede al dominio de CloudFront y no directamente al bucket.

> **Nota**  
> OAC y OAI no funcionan con un **S3 website endpoint**. Para OAC utiliza el bucket S3 como origen, no su endpoint de sitio web.

> **Logo** `recursos/aws/networking/cloudfront.svg`

> **Idea visual**  
> Usuario → CloudFront → `OAC` → icono oficial de Amazon S3 privado. La flecha Usuario → S3 aparece tachada.

### Slide 7 — Signed URL y Signed Cookies

**Título en slide**

SIGNED URL Y SIGNED COOKIES

#### Nombres en portal y examen

> **Signed URL** / **URL firmada**  
> **Signed cookies** / **Cookies firmadas**  
> **Trusted key group** / **Grupo de claves de confianza**

#### Conceptos

- Las firmas permiten restringir contenido privado entregado mediante CloudFront.
- Una **signed URL** encaja cuando quieres autorizar archivos individuales.
- Las **signed cookies** encajan cuando un usuario necesita acceder a varios archivos restringidos.
- CloudFront recomienda utilizar **trusted key groups** para verificar las firmas.
- Los trusted signers basados en pares de claves de una cuenta AWS son el modelo anterior.
- OAC protege el camino **CloudFront → S3**. Las firmas protegen **usuario → CloudFront**.

> **Nota**  
> Una CloudFront signed URL no es una presigned URL de S3. La primera utiliza la CDN y la segunda permite acceso directo autorizado a S3.

> **Logo** `recursos/aws/networking/cloudfront.svg`

### Slide 8 — CloudFront Functions y Lambda@Edge

**Título en slide**

CLOUDFRONT FUNCTIONS Y LAMBDA@EDGE

#### Nombres en portal y examen

> **CloudFront Functions**  
> **Lambda@Edge**  
> **Viewer request / response** / **Solicitud / respuesta del usuario**  
> **Origin request / response** / **Solicitud / respuesta del origen**

#### Conceptos

| Característica | CloudFront Functions | Lambda@Edge |
|---|---|---|
| Eventos | Viewer request y response | Viewer y origin request/response |
| Lenguaje | JavaScript | Node.js y Python |
| Duración | Submilisegundo | Hasta **30 s** |
| Escala | Millones de solicitudes/s | Hasta **10 000 solicitudes/s por Region** |
| Memoria | **2 MB** | **128 MB** en viewer y hasta **10 240 MB** en origin |
| Código | Hasta **10 KB** | Hasta **50 MB** |
| Body | No | Sí |
| Red | Muy limitada | Acceso de red |

- **CloudFront Functions** encaja en redirects, rewrites, headers y normalización de la cache key.
- **Lambda@Edge** encaja cuando necesitas body, librerías, filesystem o lógica más pesada.
- Una función Lambda@Edge debe crearse en **us-east-1, N. Virginia**.
- No puedes combinar ambas tecnologías en el mismo evento viewer de un mismo cache behavior.

> **Nota**  
> Cursos antiguos describen CloudFront Functions simplemente como “sin red”. Actualmente su acceso sigue siendo muy limitado y no sustituye la conectividad general disponible en Lambda@Edge.

> **Logo** `recursos/aws/networking/cloudfront.svg`

> **Idea visual**  
> CloudFront Functions pegada al usuario. Lambda@Edge muestra los **4 eventos** viewer request, origin request, origin response y viewer response.

### Slide 9 — Cifrado a nivel de campo

**Título en slide**

CIFRADO A NIVEL DE CAMPO

#### Nombres en portal y examen

> **Field-Level Encryption (FLE)** / **Cifrado a nivel de campo**

#### Conceptos

- CloudFront puede cifrar campos sensibles de una solicitud antes de enviarla al origen.
- Utiliza una clave pública **RSA de 2 048 bits**.
- Solo la aplicación que posee la clave privada correspondiente puede descifrar esos campos.
- Puedes cifrar hasta **10 campos** de datos en una solicitud.
- Está pensado para datos sensibles concretos, no para cifrar todo el contenido de la distribución.
- HTTPS sigue protegiendo el transporte de la solicitud completa.

> **Nota**  
> En el examen, un campo sensible concreto que debe permanecer cifrado dentro de la aplicación apunta a Field-Level Encryption, no a “poner KMS en CloudFront”.

> **Logo** `recursos/aws/networking/cloudfront.svg`

> **Idea visual**  
> Formulario HTTPS → CloudFront. El campo `card` se transforma en ciphertext antes de llegar al ALB. Mostrar `RSA · 2 048 bits`.

## Sesión 10.2 — AWS Global Accelerator

### Slide 1 — AWS Global Accelerator

**Título en slide**

AWS GLOBAL ACCELERATOR

#### Nombres en portal y examen

> **AWS Global Accelerator**  
> **Anycast IP** / **IP anycast**

#### Conceptos

- **AWS Global Accelerator** mejora el camino de red entre usuarios globales y aplicaciones desplegadas en AWS.
- El cliente entra por un punto de presencia cercano y continúa por la red global de AWS.
- Un accelerator IPv4 entrega **2 direcciones IPv4 estáticas anycast**.
- En dual-stack entrega **4 direcciones**, **2 IPv4 + 2 IPv6**.
- Los listeners de un standard accelerator soportan **TCP y UDP**.
- No almacena HTML, imágenes ni respuestas en caché.

> **Nota**  
> CloudFront es una CDN HTTP(S). Global Accelerator mejora conectividad TCP/UDP sin convertirse en una caché.

> **Logo** `recursos/aws/otros/global-accelerator.svg`

> **Idea visual**  
> Mostrar `2 IPv4` o `2 IPv4 + 2 IPv6`. Usuarios globales → edge AWS → red global AWS → ALB en una Region. No dibujar ningún disco de caché.

### Slide 2 — Destinos y salud

**Título en slide**

DESTINOS Y SALUD

#### Nombres en portal y examen

> **Listener** / **Escucha**  
> **Endpoint group** / **Grupo de endpoints**  
> **Endpoint** / **Destino**  
> **Health check** / **Comprobación de estado**

#### Conceptos

- Los endpoints pueden ser **ALB, NLB, instancias EC2 o Elastic IP**.
- Cada endpoint group pertenece a **1 AWS Region**.
- Los listeners admiten puertos entre **1 y 65 535** con TCP o UDP.
- Los health checks admiten intervalos de **10 s o 30 s**. El valor predeterminado es **30 s**.
- El threshold predeterminado es **3** y admite valores entre **1 y 10**.
- Global Accelerator puede retirar un endpoint unhealthy y realizar failover regional en **menos de 1 minuto**.

> **Nota**  
> Para endpoints ALB y NLB, Global Accelerator utiliza la información de salud del load balancer. Los health checks configurables se aplican directamente a endpoints como EC2 y Elastic IP.

> **Logo** `recursos/aws/otros/global-accelerator.svg`

> **Idea visual**  
> Global Accelerator → Endpoint Group Region A con ALB sano y Endpoint Group Region B. Un endpoint unhealthy aparece en gris. Mostrar `30 s · threshold 3`.

### Slide 3 — Pesos y Traffic Dial

**Título en slide**

PESOS Y TRAFFIC DIAL

#### Nombres en portal y examen

> **Endpoint weight** / **Peso del endpoint**  
> **Traffic dial** / **Control de tráfico regional**

#### Conceptos

- Un endpoint puede recibir un peso entre **0 y 255** dentro de su endpoint group.
- El peso predeterminado es **128**.
- Peso `0` permite dejar un endpoint fuera del reparto normal.
- El **traffic dial** controla qué porcentaje del tráfico destinado a una Region acepta ese endpoint group.
- Traffic dial admite valores entre **0 % y 100 %** y utiliza **100 %** de forma predeterminada.
- Pesos y traffic dial permiten despliegues graduales o blue-green sin depender de cachés DNS.

> **Nota**  
> El peso reparte tráfico entre endpoints de una misma Region. Traffic dial reduce o aumenta el tráfico que recibe una Region.

> **Logo** `recursos/aws/otros/global-accelerator.svg`

> **Idea visual**  
> Region A `Traffic dial 80 %` y Region B `20 %`. Dentro de Region A dos endpoints con pesos `128` y `64`.

### Slide 4 — Casos de uso típicos

**Título en slide**

CASOS DE USO TÍPICOS

#### Conceptos

- Juegos, voz, IoT y aplicaciones propietarias que utilizan **UDP o TCP** encajan en Global Accelerator.
- Las IP anycast estáticas ayudan cuando un partner necesita una **allowlist** estable.
- Los clientes continúan usando las mismas IP aunque cambien los endpoints o Regions.
- Blue-green puede repartir tráfico mediante pesos y traffic dial sin esperar a que expire una caché DNS.
- Los health checks permiten mover tráfico hacia endpoints sanos entre Regions.
- También puede acelerar APIs HTTP cuando el objetivo es la ruta de red y no almacenar respuestas en caché.

> **Nota**  
> S3 Transfer Acceleration acelera transferencias hacia un bucket S3. AWS Global Accelerator acelera tráfico hacia endpoints de aplicaciones.

### Slide 5 — CloudFront o Global Accelerator

**Título en slide**

CLOUDFRONT O GLOBAL ACCELERATOR

#### Conceptos

| El enunciado pide | Servicio |
|---|---|
| HTML, imágenes, vídeo HTTP, caché, menos carga al origen | **Amazon CloudFront** |
| URL o cookies firmadas para contenido privado en la CDN | **Amazon CloudFront** |
| TCP o UDP sin caché | **AWS Global Accelerator** |
| IP estática anycast y allowlist estable | **AWS Global Accelerator** |
| Failover regional rápido sin depender del DNS del cliente | **AWS Global Accelerator** |
| Elegir destino por DNS, peso, latencia o geolocalización | **Amazon Route 53** |

- CloudFront y Global Accelerator utilizan la red global de AWS, pero resuelven problemas diferentes.
- S3 CRR replica datos. No sustituye una CDN para lecturas masivas globales del mismo contenido.

The current infrastructure and design are unable to cope with the traffic, and the application freezes on most of the pages.

Which of the following is a cost-optimal solution that does not need provisioning of infrastructure?

A) Configure AWS Lambda with an Amazon RDS database so that a serverless architecture is provided

B) Use Amazon CloudFront with Amazon DynamoDB so that static assets are accessed with greater speed and low latency

C) Use AWS Lambda with Amazon ElastiCache and Amazon RDS so that static assets are served at high speed and low latency

D) Use Amazon CloudFront, with Amazon S3 as the storage solution, for the static assets

✅ **Respuesta** D

💡 **Explanation**  
**Amazon S3** stores the static assets without provisioning servers, while **Amazon CloudFront** caches those assets at edge locations closer to users. This reduces load on the application and provides low-latency global delivery in a cost-effective way.

A couple of years ago, an IT training company hosted its website on Amazon S3. Because of COVID-19 related travel restrictions, the training website has suddenly gained traction. With an almost 300% increase in the requests served per day, Amazon S3 outbound data costs alone have caused the company's AWS costs to sky-rocket.

As a Solutions Architect, can you suggest an alternate method that reduces costs while keeping the latency low?

A) Host the application on an Amazon EC2 instance and store the data on a connected Amazon EBS volume in order to reduce Amazon S3 cost

B) Store AWS Cloud or on-premises data with Amazon EFS, a shared, scalable, fully managed elastic NFS file system

C) Lower the number of calls to Amazon S3 buckets by using Amazon S3 Batch Operations to read the data in bulk in a single pass

D) Distribute the data hosted on Amazon S3 in a cost-effective way by configuring Amazon CloudFront

✅ **Respuesta** D

💡 **Explanation**  
**Amazon CloudFront** caches the S3 content at edge locations and serves repeated requests closer to users. This reduces the number of requests that must reach Amazon S3 and provides low-latency delivery, which is useful after the almost **300% increase** in daily requests.

A video conferencing platform serves users worldwide from a globally distributed deployment of Amazon EC2 instances behind Network Load Balancers (NLBs) in several AWS Regions. In the current architecture, clients can connect to any Region through public endpoints, depending on how DNS resolves. Users in regions far from the load balancers often see high latency and slow connection times, especially while a session is starting. The company wants a better experience for global users by cutting end-to-end latency and load time, while the existing NLBs and the EC2-based application infrastructure stay in place.

Which solution will best meet these requirements?

A) Deploy a standard accelerator in AWS Global Accelerator and register the existing regional NLBs as endpoints. Route user requests through the accelerator, using AWS’s global edge network, to the closest healthy Regional NLB

B) Replace every Network Load Balancer (NLB) with an Application Load Balancer (ALB) in each Region. Register the EC2 instances as targets behind the ALBs and turn on cross-zone load balancing to distribute latency

C) Configure Amazon Route 53 with latency-based routing policies so users are sent to the Region with the lowest response time. Use health checks to fail over to another Region if a specific NLB becomes unhealthy

D) Deploy Amazon CloudFront with HTTP caching enabled in front of the NLBs. Serve user requests from CloudFront edge locations so responses are faster and the load on the backend EC2 instances is lower

✅ **Respuesta** A

💡 **Explanation**  
**AWS Global Accelerator** can use the existing regional NLBs as endpoints and route users through the AWS global network toward the closest healthy endpoint. It improves network performance without requiring the company to replace the NLBs or depend solely on DNS-based routing.

A gaming company wants to improve the availability and performance of its global flagship application. The application uses User Datagram Protocol and must support fast regional failover if an AWS Region goes down. The company also wants to keep using its own custom Domain Name System (DNS) service.

Which of the following AWS services represents the best solution for this use-case?

A) Amazon Route 53

B) Amazon CloudFront

C) AWS Global Accelerator

D) AWS Elastic Load Balancing (ELB)

✅ **Respuesta** C

💡 **Explanation**  
**AWS Global Accelerator** supports UDP, provides static anycast IP addresses and can move traffic toward healthy endpoints when a Region or endpoint becomes unavailable. It does not require the company to replace its existing custom DNS service.

As a Solutions Architect, can you suggest a cost-effective serverless solution for its flagship application, which has both static and dynamic content?

A) Host both the static and dynamic content of the web application on Amazon S3, and use Amazon CloudFront for distribution across diverse regions/countries

B) Host the static content on Amazon S3. For the serverless web application that handles dynamic content, use AWS Lambda with Amazon DynamoDB. Amazon CloudFront will sit in front of AWS Lambda for distribution across diverse regions

C) Host both the static and dynamic content of the web application on Amazon EC2, with Amazon RDS as the database. Amazon CloudFront should be configured to distribute the content across geographically disperse regions
